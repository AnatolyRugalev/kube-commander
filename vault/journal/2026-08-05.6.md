## Why the modal's answer was the wrong one here, and how the tests say so

BOX-01 clamped the modal's message and put `… (truncated)` on the last row. Reaching for the
same shape here was the obvious move and it is wrong for a reason worth writing down: the
modal's reader *cannot* get at the elided text — there is no gesture for it, so naming the
loss is the whole of the remedy. The panel's reader can. `j`/`k` walk the list; what they
lack is not access but knowledge that there is more. Truncation would have given them the
opposite of what they need — a box that looks complete, ends without a marker anywhere near
the cursor, and hides the row `enter` is about to stop.

That distinction is not rhetorical, and the mutation proves it. Swapping `forwardsWindow`'s
`m.forwardsSel` for a constant `0` — i.e. exactly the truncate-the-tail fix — leaves
`TestForwardsPanelFitsTheCanvas` green. The box is the right height, the footer is there, the
border is there, and the panel is still broken: with the cursor on the sixteenth of twenty
forwards the screen shows the first six and no indication of where the selection went. Only
`TestForwardsPanelWindowFollowsTheCursor` fails. A leg that had written the height test alone
would have shipped that.

## The window has no offset, which is a choice and not an omission

`table` keeps an `offset` field and a `scrollToCursor`, and it needs to: it is long, and a
reader who scrolls and then moves the cursor by one expects the viewport to stay put. The
panel is a handful of rows and its cursor is the only way to move, so a window derived from
`m.forwardsSel` is indistinguishable from a sticky one in use, and it removes three
maintenance obligations the offset would have created — a resize would have to re-clamp it,
`handleForwardDone` removing an entry would have to re-clamp it (next to `clampForwardsSel`,
which already exists for exactly this hazard), and `stopAll` would have to reset it. None of
those would be caught by a test that does not think to look, which is the same shape as the
bug this leg is fixing.

The one behavioural consequence: scrolling to the bottom and stopping a forward re-derives
the window from the new cursor, so the list can jump by a row. That is correct — the entry
under the cursor is gone.

## Where the counter lives, and the three sizes that shaped the degradation order

`(11–16 of 20)` is in the title rather than on a row of its own because a marker row has to be
taken from the list it describes: on a six-row budget that is a sixth of the content spent
saying content is missing. The title renders unconditionally, so the count is free. It also
stays out of the way when it has nothing to say — a panel showing every forward reads
`Port-forwards`, which keeps the counter evidence rather than furniture (the same property
`clampLines` has, returning the block untouched when it fits).

Rendering it at every size is what turned up the degradation order D221 pt 3 records. Three
budgets are interesting and none of them is a size anyone would type into a test by accident:

- `bodyHeight` 6 (a 8-row terminal): two rows and a footer. Fine.
- `bodyHeight` 4: one row, and the footer *must* drop — `rows >= 2` is the guard. Without it
  the box would list its three keys and zero forwards, which is a panel that has forgotten
  what it is for.
- `bodyHeight` 3: title only, and `forwardsWindow` returns an empty range. That is why
  `forwardsPanelTitle` has an `end <= start` case: the range formatting would otherwise read
  `(1–0 of 20)`. It renders `Port-forwards (20)` — the count with no slice, since no slice is
  on screen.

Below that (`bodyHeight <= 2`) `forwardsPanelView` returns `""` and `overlayCenter` short-
circuits to the base view. A box that is nothing but a clipped border is not more honest than
no box; the panel is still open and still routing keys, and the hint line one row down is what
tells the reader that.
