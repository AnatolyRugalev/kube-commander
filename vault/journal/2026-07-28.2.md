# 2026-07-28 — LOGS-04c: jump-to-latest in the logs view

- Agent: claude-opus-5

- Did: Took the cheapest of the three LOGS-04 slices. `nav.bottom` (`G`) in the logs view
  now re-arms following as well as scrolling, so a reader who scrolled back has one key
  that catches up **and** keeps tailing. The board asked whether `G` should do it or a new
  action should; `G` won. → D147.
- The argument for overloading `G` is that **the end of a live buffer is a state, not a
  position**. The newest line keeps moving, so the old behaviour — jump, stay paused — was
  true for exactly one frame and then drifted upward as lines arrived: the reader ends up
  looking at "the newest line" from a minute ago while the header honestly says `[paused]`.
  Resuming is what makes the jump mean what the key says.
- The other half of the leg is the line it does **not** cross: incremental downward
  movement (`nav.down`, half/full page down) still leaves following off, even when it lands
  on the last line. Stepping to the end is browsing, not a statement about the tail, and a
  reader parked at the bottom of a paused view has to be able to stay there. So the model
  is a clean pair — any *upward* movement leaves the stream, the *explicit* jump to the end
  rejoins it — and a view resumes only by being asked, never by arriving somewhere. Both
  halves have a test; the one that matters asserts the line appended *after* the jump is
  still on screen, since landing on the newest line proves nothing on its own.
- A no-new-key change was the point: a second "jump to latest" binding would compete with
  `G` for the same intent and cost a hint slot in a logs hint line that D146 already found
  full. Nothing was added to `HelpLogs` — the header flipping to `[following]` the moment
  `G` is pressed is the announcement.
- **The one thing I tried and reverted is the durable finding.** I first widened the
  registry description to "Jump to bottom (logs: catch up + resume follow)" so `?` and the
  generated doc would carry it — and `internal/tui/help` went red: the full-help overlay
  lays actions out in columns sized by their **longest description**, so a longer nav
  description widened that column until the next one (the one holding `Quit`) no longer fit
  at the test's width. A registry description is *global*; per-view behaviour must not ride
  in it. Reverted to the plain "Jump to bottom", left the doc unregenerated, and documented
  the behaviour in the README and `knowledge/keybindings.md` instead. That is D147 pt 3 and
  a constraint on every future leg tempted to explain a view inside a description.
- Decisions: D147 — an explicit jump to the end of a streaming view rejoins the stream
  (incremental movement does not); prefer overloading the existing nav key and let the view
  announce the difference; a registry description is global and sizes a help column.
