## The bug is small; the reason it survived four milestones is the interesting part

`internal/version` has been correct since M0: three vars, a doc comment on each saying it is
overridden at release time, and `Info()` printing all three. `.goreleaser.yml` has been
half-wired since M0-06 (D27). Nothing in between could notice, because **both files are
individually right** — the mistake lives in the agreement between them, and `-X` paths are
strings the Go compiler never validates. A wrong package path, a renamed var, a renamed
module: all of them build, run, test green, and quietly ship placeholders.

That is why this leg is not a one-line YAML edit. The edit takes a minute; the reason M5-PLAN
had to *find* this by reading, rather than something failing, is a gap in the gate. So the
leg adds the gate: `TestGoreleaserSetsAllVersionVars` parses `version.go` with `go/ast` for
its exported package-level vars, parses `.goreleaser.yml` for each build's ldflags, and
requires every var to be set, non-empty, under `<module>/internal/version`. The module path
comes from `go.mod`, not a constant, so a module rename fails here too.

This is deliberately the M2-01e/D51 shape — the keybindings doc drift guard — reused for
release config. Configuration that only executes on a path nobody runs (a tag push) is
exactly where a test earns the most, because the alternative feedback loop is a published
artifact.

## Verification: three levels, and only two of them are worth much

1. `make check` green. Necessary, and the weakest: it proves the guard agrees with the
   config, which is nearly tautological the moment both were written together.
2. **The negative check.** `sed -i '/version.Commit=/d' .goreleaser.yml` → the test fails
   with `build "kubecom": ../../.goreleaser.yml does not set Commit`. Worth doing on any
   guard test, because a guard that cannot fail is decoration; this one was written, run
   green, *then* broken on purpose and restored.
3. **A real build with the real flags.** The `-X` path is the only part of this change that
   can be silently wrong in a way no amount of YAML review catches, so it was compiled:
   `go build -ldflags "-s -w -X …Version=1.2.3 -X …Commit=$(git rev-parse HEAD) -X …Date=…"`
   and then run. `kubecom version` reports the injected values, which proves the package path
   and all three symbol names. The templates themselves (`{{ .Version }}`, `{{ .FullCommit }}`,
   `{{ .Date }}`) are goreleaser's, documented, and the dry run below exercises them.

## The dry run, and a finding M5-03 needs

`goreleaser` is not in the sandbox image (M5-PLAN said so), but it is a Go tool, so it
installs: `go install github.com/goreleaser/goreleaser/v2@<ver>`. The first attempt pinned
**v2.5.1** and it refused to start:

```
⨯ release failed after 0s   error=yaml: unmarshal errors:
  line 34: field ids not found in type config.Archive
  line 37: field formats not found in type config.Archive
```

That is not a problem with this leg's change — `archives[].ids` and `archives[].formats` are
newer schema than v2.5.1 knows — but it is a fact M5-03 must have: **the committed config
cannot be run by an old goreleaser at all**, so the version the CI action pins is
load-bearing, not cosmetic. It fails at parse time, before building anything, which is the
failure mode you want; it just has to be recognised as "your goreleaser is stale" rather than
"the config is broken". Recorded as D175 pt 2 so M5-03 does not rediscover it by watching a
tag build fail.

Under **v2.17.1** the same command runs clean: `release succeeded after 3m47s`, four binaries
built, four `.tar.gz` archives plus four bare binaries, checksums written. And the artifact
itself is the assertion that matters —
`dist/kubecom_linux_amd64_v1/kubecom version` prints
`kubecom v0.0.0-next (commit cc877ead5de6…, built 2026-07-30T06:39:42Z, go1.24.7)`, so the
three templates resolved and the three `-X` paths hit their symbols through goreleaser's own
build, not just a hand-written `go build`. That is the strongest gate available without
credentials (D173 pt 4) and it is now known to pass.

Note this was a ~4-minute cross-compile of four targets in the sandbox; M5-03's dry-run job
should expect that order of runtime rather than CI-cache speed.

## Why `-s -w` moved onto its own line

The ldflags list is joined with spaces, so one long string and four short ones are identical
to the linker. Four lines means adding a var is a one-line diff that reads as one thought,
and a missing var is visible in a `git diff` instead of buried in a 240-column line. The
comment above the block states the rule and names the guard, so the next person to edit it
learns about the test from the file the test constrains.
