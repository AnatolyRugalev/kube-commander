## The confirm modal was the open question, and the answer was already in the keymap

The board flagged this slice's one unknown: the confirm modal's keys live in a separate key
context (D132), so "its hint cannot be sourced from the browse registry the way every other
context is". That turned out to be true of *resolution* and false of *rendering*.

`Keymap.bindings` is one map from action to sequences; only the reverse indexes are split per
context (`bySeq` / `confirmBySeq`), because a context is what makes `n` → `confirm.decline` and
`n` → `app.searchNext` not a collision. `Keys()` and therefore `Binding()` read `bindings`, so
`Binding(ActionConfirmAccept)` renders `y/enter · Accept the confirm dialog` with no new
plumbing, and a user who rebinds accept sees their own key. The alternative I was ready to
write — a hint set that spells `y`/`n` for the one context the registry "cannot" serve — would
have been the first hard-coded key in a help surface and a silent D11 violation the moment
someone rebound it. D217 pt 2 exists so the next context-scoped action is not rebuilt from
that wrong premise.

`q` is left out of the confirm set even though it dismisses the modal. Two entries that mirror
the question in the box (`y accept · n decline`) are the whole point of the line there, the
decline entry already names a way out, and a modal that lists three ways to say no reads as an
inventory rather than a promise — the same call every other context makes about paging.

## Prompt before confirm, because one predicate is a subset of the other

`modal.Active()` is true while the modal is prompting, so the two cases are ordered rather than
disjoint — exactly as `Update` orders them (`routeModalPromptKey` before
`routeModalConfirmKey`). Getting it backwards is not a cosmetic bug: the prompt would advertise
`y accept · n decline` over a text field that types both letters, which is the precise failure
D143 pt 1 names, on the surface where it is most misleading (the reader is being asked for a
replica count). The mutation test pins the order rather than the state, because the state is
right for the wrong reason if the cases are swapped and the modal happens to be in confirm mode.

The prompt's set is the browse `enter`/`esc` pair for the same reason `HelpPickerFilter` is:
`routeModalPromptKey` acts only on a mapped key with `Text == ""`, so what survives an open
field is exactly the no-text control keys. Two text fields, one rule.

## The overlay is hinted even though it does almost nothing

The keybindings overlay was the case I nearly left out: it swallows navigation, it does not
scroll, and its own body already lists every binding in the app — so the honest set is three
ways to close it, and "show nothing" felt equally honest.

It is not. `ShortHelpContext` falls back to the focus-agnostic browse set for an unknown
context, so *not* writing a case does not produce an empty line — it produces the browse hint,
which is the lie. And the reader most likely to be looking at the bottom of the screen while a
full-screen table of keybindings is up is the one trying to get out of it. Hence D217 pt 1:
the fallback is for unknown contexts, never for a surface nobody wrote a case for.

## Two liars left, and they were found by reading the router rather than the board

Writing the cases in `Update`'s order made the gaps obvious, because the order *is* the list.
Between the pickers and the modals sits `m.filtering` — the browse filter field, which captures
text exactly like the logs grep and is still hinted with the table set, so `/`, `n`, `s`, `a`,
`?` and `q` are all advertised and all type a character. After the viewer sits `m.forwardsPanel`,
which swallows everything but its own keys.

Both are HINT-03 rather than this leg: the four named surfaces are one reviewable change, and
the filter field deserves its own set decided against `routeFilterKey` (its esc has two
meanings — clear the query, then close — which is a sentence of thought this diff did not need).
D217 pt 1 names them so the next agent inherits a bounded list rather than re-deriving it, and
so a *third* uncovered surface reads as what it would be: a surface added without a hint case.
