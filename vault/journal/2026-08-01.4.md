## Why this slice first, and not the palette shell

The feedback proposed its own slicing and put "palette shell + fuzzy verb list" first. This
leg took a different first slice deliberately, for three reasons worth recording since the
next leg inherits the ordering:

1. **It is the pain the feedback actually names.** Its own diagnosis — "the specific pain
   that prompted this is that the namespace and resource pickers do not filter as you type
   the way the palette does, so muscle memory does not transfer between them" — is fixed by
   this slice alone, in every picker, today. The palette is the larger idea; this is the
   part a user feels on the next keypress.
2. **The palette is a picker.** PAL-02's verb list is `picker.Model` over verbs. Building
   the shell first would have meant either giving the palette a typing behaviour the other
   pickers do not have (the exact divergence the feedback is complaining about, just
   relocated) or doing this work anyway, inside a bigger leg.
3. **It settles the ranking question before anything depends on it.** The feedback was
   specific that the palette must reuse `internal/kube/search.go` rather than grow a second
   matcher. Exporting the matcher *and* putting it to work in a surface that already exists
   proves the seam fits before three more slices are written against it. D194 pt 1 then
   turns "reuse it" into a standing prohibition, because the tempting shortcut for a future
   leg — a ten-line `strings.Contains` scorer, local to the palette — is much easier to
   write than to notice in review.

## The keystroke that changed, and the two that did not

The honest cost of an always-open field is D140 pt 1's, already paid twice (the search
query, the logs grep): **every text-carrying key types**. In a picker that now means `j`
and `k` type rather than navigate — the arrows do that — and `/` types a `/`.

Swallowing `/` was considered and rejected. It would have preserved the muscle memory of
"press `/` first" harmlessly, but an OpenShift context name is literally
`namespace/api-host:port/user`, so the context picker needs `/` as text; a key that types
in one picker and is eaten in another is worse than a key that always types. What the
reader sees instead is the query line with `/` in it and an empty list, which at least says
what happened.

Two things deliberately did not move. **`esc` still means "back one step"**: with a query it
empties the query, with an empty query it cancels, so esc-esc dismisses exactly as before.
And **no binding changed** — this leg touches no `defaultBindings` entry, which is why the
generated `docs/keybindings.md` is untouched. The keybinding *consequence* the feedback
asked to have recorded is D194 pt 2/pt 4: the letter keys keep their meanings, and only
PAL-05 may re-express them.

## The one API change worth knowing about

`picker.Show()` now returns a `tea.Cmd` (the field's cursor blink), matching
`searchview.Show()`, which has returned one since it was written. Every call site had to
either return it or batch it with the async load it was already issuing. That is also why
several tests changed shape: opening a picker now produces a `tea.BatchMsg`, so a test that
wanted the namespace listing had to stop reading `cmd()` directly. The `pickerMsgs`/
`pickerMsg` helpers in `tui_test.go` drop the blink and hand back the rest, which keeps the
assertions about *what a picker open actually does* readable rather than spelling out batch
walking at eight call sites.

## Dogfood note

No human task was raised for this. The behaviour is fully covered hermetically — the
component tests type into a picker and assert what is listed and in what order, and the
shell tests do it through the real key routing — so there is no claim here that a sandbox
cannot substantiate. What a real terminal would add is taste: whether a list that re-ranks
on every keystroke reads as helpful or as jumpy, especially in the namespace picker where
the all-namespaces sentinel is pinned first only while the query is empty. If it grates,
the cheapest fix is to keep seed order and use the matcher purely as a filter — the ranking
lives in one function (`applyFilter`) precisely so that stays a one-line decision. Worth a
sentence in the next feedback file if the maintainer notices it while dogfooding.
