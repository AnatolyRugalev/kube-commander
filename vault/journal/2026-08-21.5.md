# 2026-08-21 — STORY-06j-3: the newest-first log order, weighed

- Agent: claude-opus-5
- Milestone: M5
- Did: A decision leg, not a code leg. The S03 feedback
  `2026-08-15-logs-newest-first-order.md` asked the newest-first (grafana/datadog)
  log order to be **considered**, not done. Considered, and **declined** — no
  reversal, and no config option for one. Recorded as D289; the feedback file is
  deleted (D69) and STORY-06j is closed.
- Why (the short form; D289 carries it in full):
  1. Half the ask is already true. The filter field renders directly under the
     header, *above* the body (`logsview.View`), and `New`/`Restream` open the
     view following with the cursor on the newest line — so a tailing full-screen
     pane shows the fresh line first without a gesture, and the input already sits
     over the newest screenful rather than a wall of old lines. The residual pain
     the web UIs answer (a stream that silently froze) is what D147, D281 and the
     STORY-06j-1 `[following]` badge already answer, more cheaply.
  2. It would invert the *direction* of every nav key in exactly one view — `j`
     backwards in time, `G` to the oldest line. Goals principle 6 makes vim the
     primary path and D147 pt 3 already draws the line: a view may add an effect
     to a shared nav key (the header announces it), not redefine the movement set,
     since the registry description, the `?` overlay, the generated keybindings doc
     and the README are all global.
  3. The load-bearing objection is representation, not muscle memory: grafana
     reverses *events* (each an ordered block); this buffer is line-granular over a
     raw byte stream (D242 pt 1) with no grouping available, so a reversal prints
     every stack trace / pretty-printed JSON record from its last line to its first.
  4. It would split the screen from the clipboard (D242 pt 4 — a yank matches what
     is shown), and the direction is encoded across `trim` + the `[trimmed]` marker
     ("there was more above this"), `atNewest`, `scrollDown`, `placeCursor`,
     `showCursor`, `shownIdx`, the selection range and the wrapped row arithmetic
     (D242 pt 6). An opt-in setting is the worst of the three options: it makes all
     of that a permanent two-branch problem on the most intricate component in the
     tree and still leaves the docs unable to state what a key does.
- Reopen condition, recorded rather than left implicit: event grouping. If the view
  ever gains records instead of lines (a structured/JSON log mode folding a
  multi-line entry into one addressable unit), objection 3 dissolves and a later leg
  may supersede D289 — but should not bolt an order flag onto the line-granular pager.
- Decisions: D289 — the logs view stays oldest-first; newest-first declined, reopens
  only on event grouping.
