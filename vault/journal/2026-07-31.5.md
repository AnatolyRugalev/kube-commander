## How M1-INT-c splits

Its own note predicted a split "by verb group", and the verbs are the wrong axis: five of
the seven actions are the same RFC 7386 merge patch with a different two-key body. What
actually differs is **how the fake lies about each one**, and that is what a live test
exists to correct:

| slice | what the fake does instead | what only a server can show |
| --- | --- | --- |
| c-1 Delete | discards `DeleteOptions` entirely | the UID precondition and the propagation policy do anything at all |
| c-2 Scale | patches the object body | the `scale` subresource is a separate endpoint with its own schema |
| c-3 the merge patches | merges into the tracked object, unvalidated | `spec.unschedulable` / `spec.suspend` / the pod-template annotation type-check, and an added annotation leaves its siblings alone |
| c-4 Update | enforces no optimistic concurrency | a stale `resourceVersion` is a real Conflict (D129's whole promise) |

Delete goes first because its gap is the widest: for the other three the fake at least
exercises *a* code path, whereas `DeleteOptions` had never been transmitted to anything.

## The one assertion this test is for

`Delete` sets a UID precondition because a table row is a snapshot. Between the list that
drew the row and the keypress that acts on it, the object can be deleted and a different
one created under the same name — and a delete by name alone then removes the object the
user never saw. That is not a hypothetical: it is what a `Deployment`'s pods do all day.

Staging it needs no timing, which is the pleasant surprise here. Create, delete through the
typed client, recreate under the same name, then call `Delete` from the stale ref:

```
delete from a stale row succeeded; the UID precondition never reached the server
```

is what you get with the precondition removed, and with it in place the server answers
`Precondition failed: UID in precondition: 9c8…, UID in object meta: 4f1…` — a 409 that
`Classify` already maps to `KindConflict`, so the chain the TUI depends on (server →
apierrors → the `fmt.Errorf` wrap → `Classify` → "the row is stale, re-list") is proven end
to end rather than assumed at the boundary.

The subtest after it is the control, and it is the more interesting one to read: the same
race with the UID dropped from the ref **succeeds**, destroying the recreated object. That
is correct — a row with no UID is degraded metadata and deleting by name is the only thing
left to do (principle 3) — and it is what proves the Conflict above came from the
precondition rather than from anything else about the staged situation.

## Foreground deletion, and the plane that never finishes it

The propagation policy is the other field the fake drops, and it needed a different kind of
evidence: unlike the precondition it does not fail loudly, it just silently does nothing.
What makes it observable is that envtest runs no controller-manager, so no garbage
collector ever clears a `foregroundDeletion` finalizer — the object sits there with its
`deletionTimestamp` set for the life of the plane. The assertion is that state.

That is also a trap worth writing down (`stack.md`), because it is invisible until it costs
someone an hour: any later slice that deletes foreground and then waits for the object to
disappear will wait forever, on a plane where the equivalent background delete is instant.

## Watched fail, twice

1. **Neuter the precondition** (`if false && ref.UID != ""` in `withUIDPrecondition`) →
   the stale-row subtest fails on the message above. This is the assertion the slice
   exists for, and it had a specific way of passing vacuously: if the delete failed for
   *any* reason the Conflict check would be satisfied, which is why the subtest also
   asserts the replacement is still there afterwards, by UID.
2. **Namespace everything** (`if true || r.Namespaced` in `resourceInterface`) → the
   cluster-scoped subtest fails with `deleting nodes "worker": the server could not find
   the requested resource`. Worth having because this is a live-only failure: the fake
   tracker is content to be handed a namespace for a cluster-scoped object, while a real
   apiserver is being asked for a different URL entirely and 404s.

## One plane, five subtests

The watch and isolation tests take a control plane each because they wreck cluster-global
state or need the apiserver configured. Deleting objects leaves nothing behind, so this
test runs its five cases as subtests over one plane with distinct object names: ~5 s for
the function instead of ~5 s per assertion, which is what keeps the gated suite (now six
tests, 31 s) a per-leg command. c-2/c-3/c-4 should follow the same shape.

The `Resource` each action addresses comes from a real `discoverFresh` pass rather than
being built inline. It costs one round trip and buys the thing a hand-written stand-in
quietly removes: if discovery ever hands the menu a wrong GVR or `Namespaced` flag, the
action test fails instead of passing against a value that was correct by construction.
