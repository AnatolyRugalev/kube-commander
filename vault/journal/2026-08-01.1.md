## The one that changes a board item

CRD-01 has been the blocked item since 2026-07-29, and the whole DIAG line was built to
obtain its error text. The answer is that the text cannot be obtained and does not need to
be:

| | reporting cluster | fresh dogfood install |
| --- | --- | --- |
| served versions | `v1beta1` **and** `v1` | `v1` only (`v1beta1` `served=false`) |
| `spec.conversion.strategy` | `Webhook` → `external-secrets-webhook` | `None` |
| kubecom | errors on open | lists normally, nothing in the log file |

A CRD with more than one served version and a webhook conversion strategy routes every LIST
of that kind through the webhook. If the webhook is down, unreachable or serving a bad cert,
the apiserver fails the LIST — and `kubectl get externalsecrets` fails with it. That is the
"kubecom is right, degrade more legibly" branch the old board note listed as one of four
plausible causes, and it is now the only one with evidence behind it.

So the re-scoped CRD-01 is a *UI* leg, not a kube-layer one: an empty table that says why,
where the reader is looking, instead of the 5-second toast DIAG-01 (D159) already writes to
the log file. DISC-01/D187 covers the neighbouring case — a *discovery* group half-failing —
but a conversion failure is per-LIST and surfaces later, so the two are not the same fix.

D191 pt 1 is written as a prohibition rather than a description because the tempting future
leg is obvious: CRD-01's title survives in the git history and in journal entries, and a leg
that reads "opening the `ExternalSecret` CRD errors out" without the closure will go looking
for a bug in `internal/kube/table.go`. There isn't one.

## The two that close clean, and are quieter than they look

**Logs throughput.** ~1,900 lines/sec (5,684 lines in a 3-second `kubectl logs -f` against a
busybox firehose), no degradation, keys responsive. The summary in the maintainer's commit
reads "the incremental-render fix this task pre-authorised is NOT needed" — and that is the
one thing worth correcting, because the dates do not line up that way:

- 2026-07-25 — task raised, against a build where `logsview.render()` re-joined the whole
  buffer per appended line. It pre-authorised the incremental render *as the fix*.
- 2026-07-29 — **LOGS-05b/D162 landed exactly that fix.** The rendered body became a cache
  an append extends, and the pump began draining the channel so a burst is one render.
  `BenchmarkStreamLines*` measured ~131 ms → ~2 ms on the 1000-line open.
- 2026-08-01 — the measurement above, on the post-fix build.

So the run is the eyes-on confirmation D162 never had, not a finding that the fix was
unnecessary. Recorded as D191 pt 3 because the misreading has teeth: D162 pt 2 tells the
*next* streaming surface not to re-join its buffer, and "we measured that it doesn't matter"
would quietly repeal it. What genuinely remains untested is depth rather than rate — nobody
has left a stream running for hours.

**Fuzzy search.** `strfrnt` scoped to `shop` → 6 hits, all real `storefront` objects, no junk
tail. The abbreviation case the subsequence fallback exists for works. But the maintainer's
own note is careful and the fold keeps it: every hit was a true positive, so there was
nothing to rank, and the question the score floor would answer — is the fuzzy tail noise? —
did not arise. Short queries, `ctrl+a`/`ctrl+w` and the exact-above-fuzzy band gap (D152 pt
3/D153) were not probed. `searchScatteredShare = limit/4` is still a guess; D191 pt 2 says so
in both directions, since "the dogfood was clean" is as bad an argument for tuning it as for
freezing it.
