# 2026-07-25 — SEARCH-03b: search progress + cap surfacing, and a search hint context

- Did: Closed the SEARCH-03 split by rendering what SEARCH-03a made expressible. The
  searchview header now carries a fan-out state — `searching 4/11 kinds…` while a search
  is in flight, `first 200 matches — narrow the query` when the cap truncated it — and
  the wiring feeds it from kube's `SearchKindDone` / `SearchDone{Capped}` events. The

  `keymap.HelpSearch` context. → D143.
- Four choices worth naming. (1) **The view owns the counters, the wiring pushes them.**
  `StartProgress(total)` / `MarkKindDone()` / `SetCapped(b)` mirror the existing
  `SetSearching` shape, so no client leaks into the component and the app keeps no second
  copy of state the header renders. The denominator can only come from the wiring — the
  scope is derived from what discovery currently offers (D141 pt 5) — so `StartProgress`
  is called at the launch, which is the first moment the kind count exists. (2) **The
  reset lives in `clearHits`.** Progress and cap describe the results on screen, so they
  go stale at exactly the moment those results are dropped; putting the re-zero in the one
  function that drops hits means a keystroke, `nav.back`'s clear and `Reset` all reset
  them for free, and no caller has to remember. (3) **Four header states, cap first.**
  Capped outranks the progress count even while the remaining kinds drain, because it is
  the only state the reader must act on, and it survives completion (the counters do not).
  A `kindsTotal` of 0 means "in flight, count unknown" — the debounce window — and still
  renders the bare `searching…`, so a keystroke is never followed by silence and never by
  a bogus `0/0`. (4) **`MarkKindDone` is clamped** at the total: kube promises exactly one
  per requested kind (D142 pt 2), and a clamp makes a stray event impossible to render as
  `12/11` rather than something to debug later.
- The hint bar was the unplanned half, and the interesting one. The search view replaces
  the browse body and captures every keypress, but `syncHints` only knew menu-vs-table
  focus — so the table hint stayed up, advertising `/` filter, `n` next-match, `s` sort,
  `a` actions, `?` help and `q` quit. Every one of those is a **text-producing key**, and
  the view's query field is always open (D140 pt 1), so all six type a character instead
  of firing. The fix is a third `HelpContext` whose curated set is only what the view
  honours — up, down, drill-in, back — and a `syncHints` case for it, called from
  `openSearch`/`closeSearch`. Help and quit are deliberately absent even though every
  browse context shows them: a hint entry is a promise (D143 pt 1). LOGS-02 lands the
  next full-screen mini-app and will want the same treatment.
- Per-kind failure stays silent (D131 pt 3): a `SearchKindDone{Failed}` advances the
  counter and renders nothing — asserted, because the progress line is exactly where a
  well-meaning future leg would be tempted to surface "1 kind failed".
- Decisions: D143 — a focus context's hint may only advertise keys that context actually
  honours; a full-screen capturing view owns a `HelpContext` (not a reused browse one, not
  hard-coded keys); `syncHints` is called wherever input ownership moves, not only on pane
  focus changes.
