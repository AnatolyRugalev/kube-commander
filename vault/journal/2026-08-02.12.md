## Why PAL-05 could not be one leg

The board wrote PAL-05 as a single item — four keys, "pre-typed palette lines" — and it
reads like a four-line change to `handleAction`. It is not, for a reason that only shows
up when you try: `default: standard` in `.golangci.yml` includes `unused`, so the moment a
key stops calling `openThemePicker`, that function, `themePicker`, `themePickerKind` and
`handleThemeSelected` are all dead code and the gate is red. The picker cannot be left
dormant for a later leg; it goes in the same commit as its key.

That turns each key into 20–52 references (`nsPicker` alone is 52 across 9 files) plus the
test file that drives it, so all four keys at once is a ~700-line diff — and a bad one,
because the four conversions are not the same shape. `T` needs no seam and no async load;
`R` carries the alias matching D203 built; `ctrl+n` and `C` fetch their values, so retiring
their pickers collapses the `dest` routing D199 added; and `a` has no argument word to
pre-type at all, which makes it a design question rather than a conversion. Four slices,
cheapest first.

The linter is the mechanism, not the argument. The argument is D197's: two surfaces for one
verb is what the feedback was about, and the dormant one is the one that drifts.

## What `T` actually gains and what it costs

Gains, all of them free because the stage is the palette's: the theme list filters with the
cluster-search matcher (PAL-01) instead of the plain substring the picker had; backspace
rewinds to the verb list; and the surface a reader learns for `T` is the surface they
already learned for `:`.

The cost is one keystroke: esc from a key-opened stage rewinds to the verbs, so leaving
takes two. I considered special-casing it — remember that the stage was opened by a key and
close outright on the first esc — and rejected it as the wrong trade. It needs a new piece
of model state ("how did this stage open") whose only purpose is to make two identical
surfaces behave differently, which is the exact thing this line exists to remove. And the
rewind is a feature at least as often as it is a cost: pressing `T` when you wanted `:theme`
was always the same key, but pressing `T` when you wanted the namespace switcher used to be
a dead end and is now one backspace from the whole verb list.

## The tests were the leg

The mechanism is nine lines. The rest was `theme_test.go`, and the interesting decision
there is that almost none of it was deleted. What the theme picker's tests pinned is not
"a picker opens" — it is that the marker names the theme on screen now and not the one the
shell launched with (D158's rule), that re-picking the current theme costs neither a
repaint nor a config write, that a failed write-back keeps the theme, and that a context
switch does not repaint the shell back to the launch palette. Every one of those is still
true and still worth pinning; only the surface underneath changed. So `openThemePicker()`
became `openThemeStage(t, m)` — which presses `T` — and the `SelectedMsg` Kinds became the
palette's. That is D207 pt 4, and it is the part of a conversion that is easy to get wrong
in a way no one notices: a leg that deletes the retired surface's tests along with it has
narrowed the guarantee while the diff looks like tidying.

Two tests genuinely changed meaning and were rewritten rather than re-pointed: the opener
test (now asserts the pre-typed line, and that `T` and `:theme ` render identically) and
the cancel test (rewind, then close).

## One thing left for the next slice

`applyPaletteArg` calls `closePalette()` before it reads `themeByLabel`, so `closePalette`
must **not** clear that map even though it is now palette-only state — the obvious tidy-up
breaks the apply. The same will be true of `ctxByLabel` when PAL-05c lands. Either leave
both alone or resolve the label before closing; do not add them to `closePalette` on the
grounds that they look like they belong there.
