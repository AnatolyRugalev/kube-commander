- Did: Split M3-14 (exec shell) into **M3-14a** (kube-layer primitive, this leg) and
  **M3-14b** (TUI wire), following the M1 verb-then-wire rhythm (D52) the port-forward
  and logs slices used. Landed the primitive: **`Clients.Exec(ctx, ref, ExecOptions)
  error`** in `internal/kube/exec.go`, the in-process equivalent of `kubectl exec` over an
  SPDY-upgraded POST to the pod's `exec` subresource via `remotecommand.NewSPDYExecutor`
  (no kubectl binary for the primary path, D2). It is a **blocking** call — unlike logs (a
  channel pump) or port-forward (a background handle), an interactive exec owns the
  terminal, so `Exec` runs synchronously and returns when the command exits; the TUI will
  drive it from a suspended terminal via `tea.Exec`, **off the update loop** (M3-14b). The
  public surface is **apimachinery-free** (D33): kubecom's own `ExecOptions` +
  `TerminalSize`/`TerminalSizeQueue` types, mapped to `remotecommand.StreamOptions` by
  `execStreamOptions` with a `sizeQueueAdapter` translating resizes, so the TUI never
  imports `remotecommand` (mirrors PortForward's `ForwardedPort`). With a **TTY** the
  primitive drops the separate Stderr stream (the server multiplexes it into Stdout —
  `StreamWithContext` rejects a TTY exec that also sets Stderr) and consults the size
  queue; a non-TTY exec keeps all three streams. Structured like the port-forward
  primitive: an **injectable `execFactory`** so `runExec` drives a `streamExecutor` seam
  in hermetic tests (D18); empty pod name / empty command rejected before any dial (#86);
  errors wrapped, the underlying `exec.CodeExitError` preserved in the chain. remotecommand
  is a subpackage of the already-pinned `client-go@v0.31.4`, so no go.mod change — an
  accidental bare `go get` was reverted (it pulled unrelated upgrades). → D124.
