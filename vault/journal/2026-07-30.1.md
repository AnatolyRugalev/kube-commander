## The test that can prove the fan-out is complete

The obvious test for a restyle — "render, restyle, assert it changed" — is close to
worthless here, and for the same reason M4-12a's was: a fan-out that misses one
component still changes the screen, because the fifteen it *did* reach all repainted.
The failure being guarded is a component silently left on the departed palette, and
"something changed" cannot see it.

`TestApplyStylesMatchesLaunchTimeTheme` gets a real oracle by borrowing the path
already known to reach every component. D170 pt 2 made `WithTheme` work by
constructing the components *from* the resolved palette, so a shell launched under
monokai is themed everywhere by construction. The invariant is therefore an equality:
for each surface, a shell built on the default palette and then restyled must render
**byte-identically** to one built with that theme from the start. A component missing
from `applyStyles` keeps drawing in default colors, and the two renders diverge.

That only works if the surfaces are seeded with content and cover the overlays, since
each component is on screen in exactly one of them — so `themeSurfaces` opens the
browse shell, a filtered and sorted table, the help overlay, a populated picker, the
viewer, a confirm modal, the cluster search view with hits, and the logs view with
lines. It was verified to fail before being kept: dropping `m.logsView.SetStyles(s)`
fails the `logs view` subtest and nothing else, which is exactly the diagnosis one
wants from it. The companion `TestApplyStylesChangesOnlyColors` asserts the other
half over the same surfaces — same glyphs, different escapes — so a "restyle" that
resized or re-created a component is caught too.

## Re-deriving, and the three places it bites

The rule that came out of writing these (D171 pt 2): **if `New` reads its `Styles`
argument for anything other than storing it, `SetStyles` has to redo that read.**
A `styles.Styles` is an immutable value that gets *copied* into whatever derives from
it, so the derived copy — not the field — is what draws.

- **Status bar.** `New` does `sp.Style = s.Spinner`. Assigning `m.styles` alone leaves
  a spinning discovery indicator in the old accent while the bar around it moves. The
  animation frame is deliberately preserved, so picking a theme mid-discovery does not
  make the spinner stutter.
- **Picker and search view.** Every row, including the cursor's Selection bar, is drawn
  by an `itemDelegate` holding a `Styles` copy handed to `list.New`. `list.SetDelegate`
  swaps it without touching the items, the cursor or the scroll page — so an *open*
  picker restyles under the reader without losing their place.
- **Logs view.** The worst of the three, because it is invisible in the common case:
  `shownLines` is a *painted* cache (LOGS-05b) — each kept line is stored with the
  `Match` escape sequences already wrapped around its matched spans. A field-only
  assignment leaves every highlight already on screen in the old theme's colors, and
  only lines streamed *after* the switch follow the new one. So `SetStyles` calls
  `render()`, the same O(n) rebuild a filter or timestamps change takes; a restyle is
  that same class of event (a reader gesture, not a stream event), so it costs an
  append nothing. Without an active grep there is nothing painted and the bug hides,
  which is why the component test types a query first.

Each of those three has its own package-level test (`TestSetStylesRestylesTheSpinner`,
`TestSetStylesRestylesRowsAndKeepsPlace`, `TestSetStylesRepaintsPaintedHighlights`),
and all three were confirmed to fail against a plain `m.styles = s` before being kept.
They are redundant with the shell-level equality test by construction — but they name
the trap in the package that contains it, which is where the next person editing that
component will look.

## Why `applyStyles` is a method with a test rather than a line in 12b-2

It would have been natural to write the fan-out inside the action that picks a theme.
Keeping it separate is what let the negative checks above exist at all (there is
something to call before any gesture reaches it), and it splits the risk: this leg is
sixteen small methods with an oracle, and 12b-2 is a picker plus a file write. It also
gives D171 pt 1 somewhere to live — the "add your component here" list is a single
function a reviewer can diff against `Model`'s fields.

## Notes for M4-12b-2

- **`applyStyles` takes a `styles.Styles`, not a `Theme`** — mirroring `styles.New(t)`
  at the one call site, as `WithTheme` does. The picker's selection is a theme *name*,
  so the route is `styles.ByName(name)` → `styles.New(theme)` → `applyStyles`.
  `ByName` is lenient about case/space but never fuzzy (D169 pt 2), and the picker only
  ever offers names it produced, so the not-found branch is a real degrade path only if
  a stale label survives somewhere.
- **The write-back is the leg's actual risk, not the restyle.** `Config.SaveFile`
  marshals the whole struct, so it must be `LoadFile` → set `Theme` → save, or the
  user's `keys:` section is deleted. Comments in a hand-edited config are lost by any
  save regardless — worth a README line.
- **Mark the active theme** the way the context picker marks the current context
  (D158), and read the order from `styles.Themes()` (default first, then sorted —
  D169 pt 4 makes that the one registry order every surface agrees on).
- **A restyle needs no resize or re-seed.** Every component keeps its size and state
  (D171 pt 3), so the action is: resolve, `applyStyles`, save, toast on a failed save.
  There is no "re-lay-out the shell" step to remember.
