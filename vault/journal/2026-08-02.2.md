## The key that had to move, and why the board's plan could not survive contact

The board and D194 pt 4 both assumed this slice would *widen what `:` opens* without moving
any key: `resources.switch` already owned `:` and already called itself a command palette in
`keymap.go`, so the plan read as a one-line change of what its handler opens. That is not
buildable as written, and the reason is worth recording because it is the sort of thing that
looks like a naming quibble until you try it:

- If `:` stays bound to `resources.switch` and opens the palette, then the action named
  "switch resource" is the action that opens a list of *every* verb, and the palette's own
  "Switch resource" entry would have to dispatch something other than the action it names —
  or recurse. The registry stops describing what the keys do, which is the one thing D11
  buys.
- So the palette is its own action, `app.palette`, and `:` is its key. That leaves
  `resources.switch` keyless, and **keyless is not a neutral state here**:
  `TestDefaultKeymapValid` asserts every registered action has a default binding, `FullHelp`
  drops disabled bindings from the `?` overlay entirely, and `docs/keybindings.md` renders
  an unbound action as an em dash. "Reachable only through the palette" would therefore have
  deleted the resource switch from both places a user goes looking for it, on the same day
  the palette started advertising it.

`R` is the mnemonic **R**esource, free in the browse context, not a reserved nav chord, and
it joins the capital-letter app-global family (`C` context, `T` theme, `M` mouse, `F`
forwards, `P` pods; lowercase `r` is secret.reveal). Nothing else moved: `ctrl+n`, `C`, `T`
and `a` are untouched, and D194 pt 4's substantive half — PAL-05 is the only slice allowed
to re-express a shortcut — still stands. D197 pt 3 supersedes only the "no key moves" clause.

## What the palette is, in one sentence, and the two things it is not

It is a `picker.Model` over `[]keymap.Action`, and both halves of each row come from the
registry: the label is `a.Describe()`, the pick is `handleAction(a)`.

It is **not** a second implementation. `handleCommandSelected` deliberately ends in
`handleAction` rather than in `openNamespacePicker`/`openSearch`/…, so a verb picked here
goes through every precondition its key goes through — the modal capture, the logs-view
capture, the help-overlay swallow, all of it. The tempting shortcut (a `switch` in the
palette that calls the same handlers the key dispatch calls) would work today and drift the
first time one of those handlers grows a guard.

It is **not** a live availability list. `:` with no cluster still offers "Switch namespace",
and picking it does what `ctrl+n` does — nothing at all. Filtering the list by what is
currently possible sounds strictly better and is not: for app-global verbs "available" is a
property of the whole app rather than of a selection, and a list whose rows appear and
disappear between openings is measurably harder to type into than one that does not. The
place availability *does* belong is PAL-04, where the verbs are row-scoped and the actions
menu already computes exactly that set per row.

## The verb list, and the one entry that is arguable

Thirteen verbs, in the order an empty query shows them: the four switchers (resource,
namespace, context, cluster search), the two panels (port-forwards, actions menu), then the
toggles (menu, theme, mouse, sort, clear sort), then help and quit. The rule is *app-global
only*: nothing scoped to the logs view, the port picker, the secret viewer or the confirm
modal, because those are meaningful only while a particular surface is up and the palette
cannot open over most of them anyway.

`actions.menu` is the arguable one — it is app-global as a *gesture* but its content is
row-scoped, so it is the one entry that is often inert. It is in because it is the only
route from the palette to the row verbs until PAL-04 lands, and out-of-scope entries are
cheaper to remove than missing ones are to discover. PAL-04 should reconsider it: once the
row verbs are offered directly, "Open actions menu for the selected row" is a second way to
reach a list the palette itself is showing.

## Two things noticed while wiring, left alone deliberately

- **The hint bar lies while any picker is open.** It keeps showing the browse hints
  (`j/down Move down • k/up Move up • …`) even though PAL-01 made every text key type into
  the picker's filter — so `j` types a `j` while the bar says it moves down. This is not new
  (it has been true for every picker since PAL-01) and it is exactly the class of promise
  D143 pt 1 forbids in the logs view, where the fix was a second `HelpContext`. A picker
  context is the same shape of fix and is a leg of its own, not a rider on this one. Worth
  picking up in PAL-03, which is already touching how the palette reads.
- **The screencast tape had a stale step.** Its browse sequence typed `:` then `/` then
  `pods` — the `/` being the opt-in filter key that PAL-01 removed, so as written the tape
  would have typed a literal `/` into an already-open filter and recorded a search for
  `/pods`. The keymap guard could not catch it (`/` is still bound to `app.filter`; only its
  *effect inside a picker* changed). Fixed here along with the palette step, so the recording
  the human still owes (`2026-07-30-record-screencast`) shows the new flow: `:` →
  `resource` → enter → `pods` → enter. No human task was raised for this leg beyond that one,
  which already exists: everything claimed above is covered hermetically.
