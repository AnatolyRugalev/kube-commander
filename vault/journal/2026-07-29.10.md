# 2026-07-29 — LOGS-05a: the logs view opens on now, not on boot

- Agent: claude-opus-5
- Milestone: — (feedback-driven, off the M4 line)
- Did: Triaged feedback `2026-07-29-logs-tail-and-perf` (high) into **LOGS-05a** (bound
  the fetch) and **LOGS-05b** (bound the per-line cost), and landed 05a: every `openLogs`
  now sets `TailLines: defaultLogTail` (1000), so the stream starts at the last 1000 lines
  and tails from there instead of replaying the container's whole log. Extracted the
  reconnect's option rewrite into a pure `kube.logOpenOptions` and pinned the rule that
  only became live today — an initial-read selector never survives a resume. → D160.

- **The feedback is two bugs wearing one title, and they split cleanly.** "Tail the last
  1k" bounds what is *fetched*; "rendering is slow" bounds what a fetched line *costs*.
  They are independent — the tail does nothing for a followed stream's buffer, which keeps
  growing past 1000 forever, and the render fix does nothing for the minutes a week-old
  pod spends replaying — and the feedback says so itself ("this needs to be fixed
  regardless"). Two slices, and this is the one whose whole diff is four lines of
  production code, so it goes first and cheapest. LOGS-05b is on the board with both
  candidate fixes named (batch the pump / cache the rendered body).
- **The number is a policy, and the policy belongs to the view.** `kube.LogOptions`
  deliberately mirrors `kubectl logs`, where the zero value means "everything"; that is
  the right shape for a primitive and the wrong default for a TUI whose logs gesture means
  "what is this doing now". So the kube layer is untouched semantically and
  `defaultLogTail` sits in `internal/tui/logs.go` beside the open that has the opinion
  (D160 pt 3). 1000 is more than any terminal can show — scrolling back has somewhere to
  go and a grep has a corpus — and bounded regardless of the container's age.
- **The real risk was in the code I did not have to write.** `TailLines` means "start N
  lines back from *now*", so it is correct exactly once: on the initial connect. The
  follow reconnect already cleared it (and `SinceSeconds`) in favour of the resume anchor
  — but that branch lived inside a closure over a `*Clientset`, so it had **no test**, and
  until this leg nothing in kubecom set `TailLines` on a followed stream, so it had never
  run in anger either. Left alone, the first transport blip on a busy pod would have
  re-served the last 1000 lines on top of what the reader was already looking at. Pulling
  it out as `logOpenOptions(opts, since)` costs nothing (it is the same code, by value)
  and buys three named tests, including one that the caller's own options are not mutated
  — a resume that cleared the tail *in place* would be invisible on the first reconnect
  and wrong on every later re-open.
- Verification note: both halves were mutation-checked. Dropping `TailLines` from
  `openLogs` fails `TestLogsStreamTailsRecentHistory`; replacing `opts.TailLines = nil` in
  the resume branch with a no-op fails `TestLogOpenOptionsResumeDropsInitialSelectors`.
  The tail test also asserts `Follow` and `Timestamps` are still set, because the tail is
  only correct in their company — a bound that cost the view its live tail or LOGS-04b's
  buffer would pass a narrower assertion.
- **No header marker, deliberately.** A reader who presses `gg` now lands on a line that
  is not the container's first, and nothing says so. A permanent `[tail 1000]` in the
  header would be on every row of every log forever to state something that never changes
  — the opposite of D146's rule that a marker names state the reader can *lose sight of*.
  It is also the universal convention: k9s tails silently, and `kubectl` gives no
  indication either. If a dogfood session says otherwise it is one line in `header()`.
- **Not made configurable.** `config.yaml` carries only `keys:` today, so a `logs.tail`
  knob means a new strictly-parsed section, launcher wiring, README docs and tests — a
  leg, for a number nobody has asked to turn. D160 pt 1 records the constraint that keeps
  that honest: the leg that wants it adds the config section rather than redefining the
  constant.
- Decisions: D160 — every logs open is bounded by `TailLines` (an unbounded replay is a
  bug, not a default); the bound is on the fetch, not the buffer; `kube.LogOptions` keeps
  kubectl's "zero value replays everything" semantics, with the policy living in the view;
  and initial-read selectors (`TailLines`/`SinceSeconds`) never survive a follow reconnect.

- Next: **LOGS-05b** — the other half of the same feedback, and the one the throughput
  dogfood predicted: `logsview.Append` calls `render()`, which re-scans and re-joins the
  entire buffer and hands the whole string to `viewport.SetContent`, for every single
  line. Appending n lines is O(n²), and LOGS-05a's own 1000-line opening burst is now the
  worst case that hits first. Two candidate fixes, either of which helps alone: drain what
  is already buffered on the log channel per pump Cmd and append the batch (one render per
  batch instead of per line, in `internal/tui/logs.go`), and/or keep the rendered body so
  an unfiltered append is an append rather than a re-join (in `logsview`). Then the
  `2026-07-29-logs-init-containers` feedback (normal), then M4-05.
