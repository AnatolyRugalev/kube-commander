## The feature could not have existed without a mode, and the view had refused to have one

The searchview package doc has said since SEARCH-02a that the query field is *always* open —
"the query is the view, not a mode within it" — and stated it as the thing that distinguishes
this view from the picker's filter and the logs view's grep, both of which are modes you enter
and leave. It is a good sentence and it was the design. It is also, exactly, the bug.

Once the field is unconditionally open, every rune is text, and the routing rule that follows
(`mapped && key.Text == ""` → action) is forced: `j` has text, so `j` types. There is no
implementation of "`hjkl` moves the results" that survives that premise. So the feedback is
not asking for a key binding, it is asking for the premise to be dropped, and no leg could have
delivered it by adding an arm to `Update`.

What made this legible was that the same sentence justified the *right* thing elsewhere. A
picker's filter is genuinely incidental to the picker — you open it to narrow a list you were
already navigating. The search view's query really is the view: there is nothing to navigate
until you have typed. Both halves of the design were about the *opening* state and both are
still true. The claim that quietly extended past its evidence is that the opening state is the
only state — which stops being true the moment results exist, which is the moment the reader
wants to move through them. D235 amends pt 1 rather than superseding it for that reason: the
field stays open (a committed query is still visible, still editable one esc away), it just
stops owning the keyboard.

## Two enters instead of one, and why that is the right trade

The cost is real and worth naming: typing `api` and opening the top hit used to be
`api`+enter and is now `api`+enter+enter. I considered making the first enter *both* commit
and open when there is exactly one hit, which would have made the common case free.

It is a trap. The hit count is a function of a fan-out that is still streaming — the "one
hit" you have when you press enter can be one of nine a moment later, and the whole point of
ranked streaming insertion (D152) is that the best answer may not have arrived yet. A key
whose meaning depends on how far a background sweep has got is a key that does something
different every time you press it, and the failure mode is the worst one available: it opens
a resource you did not choose. So the seam is unconditional on the *focus*, never on the
result count, and the one place the count is consulted is the refusal — with zero hits there
is nowhere to commit to, so enter does nothing rather than moving the reader into a mode with
no cursor.

The arrows keep working from the query field, which is what makes the extra keystroke
avoidable for anyone who already had the habit: down-down-enter still opens the third hit
without ever committing.

## Dropping unmapped text was the decision, not the obvious behaviour

The obvious design for "reader is on the results and types a letter" is to send it back to
the query — that is what a browser's find-in-page does, and it makes the mode feel weightless.
I wrote it that way first and then could not defend it.

The problem is that this view's navigation keys *are* letters. `j`, `k`, `g`, `G`, `d`/`u`
under their chords — the mapped set is letters, and the unmapped set is the rest of the
alphabet. "Resume typing on an unmapped letter" therefore means: `j` moves, `z` types, and
the reader has no way to know which is which except by trying. And the failure is not
symmetric — typing `z` does not just insert a character, it fires `QueryChangedMsg`, which
cancels the in-flight fan-out, clears every hit and re-runs a search for `apiz`. The reader
loses the result set they were standing on because they pressed a key that looked like the
one next to it.

Dropped is boring, and boring is the property: on the results, letters move or do nothing.
Esc is the way back to editing, it is one key, it is what esc already does everywhere else in
this app, and the README says so.

## The muted line, and the thing blur does not do

Blurring a textinput removes its cursor. That is the entire visual difference, and it is an
absence — nobody scans a screen and notices that something has stopped blinking, particularly
not while their attention has just moved to the list below. So the commit would have been
invisible: the reader presses enter, nothing appears to happen (no hit opened, no obvious
change), and their next keystroke behaves differently than the last one.

Rendering the query line through `styles.Subtle` while the results hold focus is one line of
code and it is the only standing signal there is. `TestCommittedQueryLineIsMuted` asserts the
frame changes *and* keeps its height, because the interesting failure of a style swap is not
"no visible difference" — it is a style with different padding quietly costing the list a row.

I deliberately did not add a `HelpSearchResults` hint context. The two focus states use the
same six actions (`HelpSearch`) and their descriptions are already accurate in both ("Open /
drill into selection" describes committing as fairly as it describes opening), so a second
context would duplicate the hint bar to say the same words.

## refocusQuery is unconditional, and that is the second version

The first `refocusQuery` short-circuited — `if m.focus == FocusQuery { return nil }` — which
is the obvious way to avoid emitting a redundant blink command. `TestResetReturnsFocusToTheQuery`
failed on it immediately: `Reset` runs after a commit blurred the field, so the short-circuit
saw `FocusQuery` (which `Reset` had just set) and left the textinput blurred. The view then
claimed query focus with a field that ignored every keypress.

That is exactly the disagreement between the flag and the widget that D235 pt 4 exists to
forbid, and it appeared inside the function written to prevent it. The unconditional version
costs one redundant `tea.Cmd` on the paths that were already focused, and removes the entire
class of caller-has-to-know-which-state-it-is-in bug. Reset now goes through it too, so there
is one way focus moves back and no second place to keep correct.
