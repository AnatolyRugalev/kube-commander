## Why the declaration is a column and not a set

The board filed PAL-06 with the cost attached: "nothing declares which actions confirm …
the marker needs a declared set beside the registry and a test pinning it to those call
sites, **or it is a fourth hand-maintained list that goes stale the way the prose it came
from did**." That sentence rules out the obvious implementation (a `map[rowAction]bool` next
to `rowActions`) unless something forces it to stay true.

Two things force it here, and they fail at different times:

1. **Compile time.** `rowActions` is an unkeyed composite literal. Adding a field means every
   row must state it, and a new action added tomorrow does not build until its author answers
   "does this ask first?". A separate map has no such property — a new action simply is not in
   it, and absent reads as `false`, which is the failure mode the board was warning about.
2. **Test time.** `TestRowActionConfirmsMatchesTheHandlers` dispatches every registered action
   over a real selected row and compares what the handler did against what the column claims.
   So the column cannot drift from `app.go` either — a `ShowConfirm` added to Cordon, or
   removed from Drain, fails it.

The second is where the leg's actual care went, because the naive version of it is worthless.

## Wiring every seam is the whole test

The negative half of the assertion — "these twelve do *not* confirm" — is trivially true for
an inert action. `openDeleteConfirm` returns early when `m.deleter == nil`; so do the rollout,
drain, exec, edit, port-forward and secret handlers. A test that opens a table with no seams
would pass all fifteen rows today and would keep passing after someone added a confirm to
Scale, because Scale's handler would never have run.

So `allActionSeams()` wires all fourteen fakes, and each action is dispatched over a kind it
applies to (`rowActionKinds`, which a new action must join or the test fails). That is what
makes the twelve `actsAtOnce` rows a claim rather than a tautology: each one's handler really
ran, really had its seam, and really opened no confirm.

## `(confirm)` rather than the ellipsis, and why that is a decision

The GUI convention for "this menu entry opens a dialog" is a trailing ellipsis, and `Delete…`
was the first thing tried. It is wrong here, and the reason is worth keeping (D228 pt 3):
**Scale and Port-forward also open a modal** — a `ShowPrompt` asking for replicas or ports.
If the ellipsis means "opens a dialog", the unmarked Scale asserts something false. If it
means "asks permission", it is a private meaning for a public convention.

The distinction the stage actually needs is between *asking what* and *asking whether*. A
prompt announces itself the moment it opens and cannot act without you typing something; a
confirm is the one that stands between a keystroke and an eviction. So the word marks only
that, and a leg that wants to mark prompts too adds a second marker rather than widening this
one. `TestConfirmMarkerIsNotAnEllipsis` exists because "tidy the wording into the convention"
is exactly the kind of change a later leg makes without knowing this paragraph exists.

## The marker is part of the label, which cost three test edits

`picker.SelectedMsg` carries the label, and the maps that resolve a pick are keyed by it
(D203 pt 3). Marking the label therefore re-keys `palRowByLabel`, and three existing tests
that asked for `"Delete"` and `"Drain"` by hand stopped finding them. They now ask through
`rowActionLabel(rowActionDelete)`, which is the honest fix: what they mean is "the label the
stage lists this action under", and spelling it that way means the next marker change does not
touch them at all.

The alternative — keeping the map keyed on the bare title and decorating only at render — was
rejected because the picker renders `Item.Label` and hands that same string back; a display-only
decoration would need a second field through `picker` and a lookup that strips the marker, i.e.
two representations of one label, which is the shape D203 pt 3 exists to prevent.
