## Why the write goes after the watch, not with the drill-in

The board asked for the record to happen "when a drill-in changes `m.current`", and there is
a line in `watchResource` that literally does that. Putting the write beside it is right,
but only just — and the reason is a few lines above it.

`watchResource` can fail. `m.watcher.Watch` returns an error for a kind whose LIST the API
server refuses, and CRD-01 made that path do real work: the pane gets `browseFailure`, the
credential diagnosis is armed, and the function returns *before* `m.current` is assigned.
So the code as written already records nothing on that path — but only because the
assignment happens to sit after the error return, which is an accident of how M2-07c was
written rather than a property anyone chose.

It is worth choosing, because the failure it prevents is self-perpetuating. Remember a kind
whose watch failed and every subsequent launch reopens the same failure, on a cluster where
the reader may have no idea why they keep landing on an error pane. `TestAFailedWatchRecordsNothing`
pins it, and the mutation that moves the record above the `Watch` call fails four tests —
which is the shape you want: the constraint is load-bearing enough that breaking it is loud.

The other half of the write point is the dedupe, and it is not an optimisation. The namespace
picker re-scopes by **re-selecting the current resource** (M2-08c) — `selectResource(m.current)`
with a new `m.namespace`. Without the dedupe, every namespace change rewrites the state file
to say exactly what it already said. That is an atomic write and a `SaveFile` per keystroke-ish
gesture, for nothing.

## Why the replay hangs off discovery, and what that costs on screen

The obvious place to restore is `handleClusterConnected`, right where `msg.state.Namespace`
is replayed. It is wrong for a specific reason: at that moment `resetCluster` has just
rebuilt the menu from the **seed**, and the seed is ~25 core kinds. A remembered
`externalsecrets` would be "not served here" on the cluster that serves it, every time —
the feature would work for `pods` and silently fail for exactly the kinds people pin.

So the restore is armed there and taken in `handleDiscovery`, after `Reconcile`, which is
already the moment the switch's stopwatch stops (CTX-WARM-01) because it is the moment the
new cluster becomes usable. Two things now hang off one point, and that is the right number.

The cost is visible and I could not measure it here: between the switch landing and the pass
completing, the reader sees the seed menu and the welcome pane, and *then* the table appears.
On the maintainer's own numbers that gap is the `discovery=` field in the switch log, and
nobody has pasted one yet (pt 7 of the context-switch dogfood is still unanswered). If it is
short it reads as the switch finishing; if it is long it reads as a flash of the wrong screen
followed by a jump. That is a legibility judgement a teatest cannot make, so it went to the
human task as item 8 with both possible fixes named — hold the transition, or restore a seed
kind immediately and upgrade when the pass lands — so whoever answers knows what the answer
decides. No `Blocks:` was added: the file is advisory and this changes nothing about that.

## The degrade is most of the design, and it has two routes

D240 pt 3 made "a miss is silent" a property of the line, and implementing it turned up that
"miss" is two different things:

1. **The kind is not listed.** The cluster does not serve it; discovery never produced a row.
2. **The kind is listed but unavailable.** `Reconcile` marks a row `Available: false` when its
   API group is in `result.Failed` — the group exists in the seed but the server could not
   load it (D187's group-granular case among them).

The second is the one that would have shipped broken. A naive lookup by GVR finds that row,
drills into it, and starts a watch against a group the server just said it cannot serve —
producing the CRD-01 error pane, unprompted, on every launch. Which is precisely the outcome
the whole degrade exists to prevent, arrived at through the code that implements it.
`menuIndexOfGVR` skips unavailable rows for that reason, and dropping the check fails
`TestARememberedKindInAFailedGroupIsSilent`.

The silence is asserted as an absence, not just as "no table": the test checks that the
returned `tea.Cmd` is **nil** (no toast is scheduled, no retry armed) and that the status bar
does not mention the kind. An error the reader never asked for is the failure mode here, and
"we didn't open a table" is a weaker claim than "we said nothing".

## Five mutations, and the one that found a test asserting nothing

1. Ignore `Available` in `menuIndexOfGVR` → 1 failure (the failed-group test).
2. Drop the `hasCurrent` guard in `restoreLastResource` → 1 failure.
3. Drop the dedupe in `recordResource` → 2 failures.
4. Never consume `restorePending` → **passed**.
5. Record before `Watch` is called → 4 failures.

Mutation 4 is the interesting one. `TestTheRestoreIsAttemptedOncePerCluster` as first written
restored successfully, moved the reader to another kind, then delivered a second discovery
pass — and it passed with the guard removed, because after a *successful* restore `hasCurrent`
is true and `hasCurrent` was doing all the work. The test was asserting a behaviour that a
different mechanism already provided, which is the same as asserting nothing.

The case where `restorePending` is the only guard is the one where the first restore **missed**:
the reader is left on the menu with no table open, so nothing else stops a later pass from
pulling them into one. Rewritten that way — first pass does not serve the kind, second pass
does — the test bites. It is also the more honest scenario: today `startDiscovery` runs only
at launch and at a switch, so a second pass on one cluster is a future leg's reconnect, and
this is the constraint that stops it becoming a jump-scare.

Worth stating plainly because it generalises past this leg: a guard that is masked by another
guard in the test's setup is untested, and the way to find out is to remove it and see whether
anything notices.

## What a restore is not allowed to be

Three invariants fell out and are each pinned by a test, because each is a thing a plausible
implementation gets wrong:

- **A restore does not write back.** The address came out of the state file; persisting it
  again on restore would be a no-op write on every launch and every switch. The restored
  namespace has followed this rule since M4-05 and the comment there says why; the kind now
  does too (`TestARestoreIsNotAWriteBack`).
- **A restore loses to the reader.** Discovery can land seconds after launch. If the reader
  has already drilled into something, the restore is skipped entirely — being yanked off the
  table you just chose is worse than not being restored at all.
- **A restore is a fresh watch, not a replay.** Nothing about the previous session's rows
  survives; `selectResource` runs exactly as if the keys had been pressed. This is D240 pt 2
  and it is what makes the whole feature safe to do at all — there is no stale data to
  refresh, because there is no data.

## A note for CTX-MEM-03

The pointer type on `State.LastResource` is load-bearing and easy to undo by accident. `sigs.k8s.io/yaml`
marshals through JSON, and `omitempty` does **not** omit a zero struct — so a value-typed field
would add `lastResource: {version: "", resource: ""}` to every existing state file the first
time kubecom wrote one, and `parseState` would then reject that file on the next read, costing
the namespace and the pins along with it. `TestStateNoLastResourceStaysEmpty` guards the
absence. Whatever CTX-MEM-03 adds beside it (a sort column, perhaps a row UID) wants the same
treatment: either a pointer, or a scalar that is genuinely empty when unset.
