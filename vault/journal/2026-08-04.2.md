## The rule was cheaper to write than the fifth conversion would have been

Three mechanical conversions were enough to make PAL-05's per-key notes read as a
backlog of instances rather than as a rule, and this leg is where the instances run out:
after `C` there is no standalone value picker left. So the leg's actual product is not
the five-character `handleAction` edit — it is D209, which says the thing the four
slices were each an example of, and says it forward: the next verb that takes an
argument gets a stage, and it gets it in `enterPaletteArg` where the key and the typed
line share one inertness check.

D209 pt 3 is the part that would otherwise be rediscovered. `actPicker`, `ctrPicker` and
`portPicker` are still modals, and a reader coming to this code after PAL-05 would
reasonably ask whether they are three conversions nobody got to. They are not, and the
distinction is not "we ran out of legs" — they list a *selected row's* own data (its
actions, its containers, its declared ports), reached from the row rather than from a
verb word. The test in the decision is the honest one: could you name the value on the
palette line before seeing the list? `:context prod` yes; "container 2 of this pod" no.

## What `C` carried that the other three did not

D158's marker rule: the `*` on a context row follows the **shell's live context**, not
the kubeconfig's `current-context`, because kubecom's switch is session-scoped and never
writes back — so after one switch the kubeconfig's idea of "current" is the context the
reader *left*. That is the one thing on this key that is wrong in a way you cannot see at
launch, when the two agree.

It moved nowhere, for the same reason D203's alias handling did not move in PAL-05b: it
lives in `contextPickerItems`, and the `:context ` stage was already seeded from that
function (PAL-03b). The conversion deleted the second surface those rows were rendered
into, not the rendering. The test that pins it is the one test in this file that did not
change a single assertion — only how it opens the surface.

## Two ways out of a stage, and only one of them was tested

`TestLateContextListIsDropped` used to test dismissal of a modal, which had exactly one
shape: the picker was hidden. The palette has two — backspace rewinds the line to the
verb list (the palette is still up, on a *different* stage) and a second esc closes it —
and the collapsed `dest` guard has to survive both. So the test is now two subtests, and
the rewind half is the one that would have been missed: the palette is still `Active()`,
so a `waiting` check written as "is the palette open?" rather than as
`awaitingPaletteArg` would pass the closed case and paint contexts over the verb list in
the rewound one. That is D208 pt 3 stated for the second and last time; it is now a
property of both fetched verbs, tested identically on each.

## The map that must outlive the surface

`applyPaletteArg` closes the palette *before* it resolves the picked label, so
`ctxByLabel` (like `themeByLabel`) cannot be cleared in `closePalette` — the apply is
about to read it. The board note carried this forward from PAL-05a as a warning, and it
is worth recording that the warning is now load-bearing in a way it was not then: with
the standalone picker gone, `closePalette` is the *only* teardown the context rows have,
so the tempting tidy-up ("closePalette should clear everything the palette owns") now
silently breaks the switch instead of being caught by the picker's own path. It fails
loudly under test — `switchContext` is never reached, no connect Cmd is issued — which
is why that mutation is recorded above rather than left to a comment.
