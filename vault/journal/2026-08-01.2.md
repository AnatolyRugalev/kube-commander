## What actually changed, and the one thing that did not

The old `lookupEditor` was called from `handleEditFetched`, i.e. at the moment the user
pressed `e`. That placement is what made the failure so unpleasant: you find out your
fallback is broken exactly when you wanted to change something. Resolution moved to the
launcher, beside the theme and menu resolution, so the answer exists — and is in the log
file — before the TUI even paints. The shell now holds a resolved `editorArgv` and does no
environment lookup at all; `Model` carries it rather than the `Cluster` bundle, because a
context switch changes nothing about which editors are installed.

What deliberately did not change: **PATH detection never overrides a variable the user
set.** `EDITOR=myed` on a host with `nvim` present still launches `myed` and still fails
if `myed` is missing. Substituting a working editor for the one that was asked for would
turn a legible error into a silent surprise, and the test table pins it
(`set variable beats a present candidate`). Flag-splitting and "an aborted edit never
mutates" are untouched — the no-editor branch returns before any write, joining the other
aborted-edit paths.

## Why the failure toast is at startup *and* at `e`

Two surfaces for one condition looks redundant, and it is not. The startup toast is the
point of the feedback ("say so clearly and early"), but it is a 5-second transient — a
user who launches, walks away, and comes back to press `e` has missed it. The press-time
toast is what is actually on screen when the action fails, and it carries the same
actionable text. The log line is the third and the durable one (D159).

The startup toast takes the **last** slot in the precedence chain (migration → menu →
theme → editor). Rationale: the other three all report something the user's own config
did, while this one reports something about the machine, and it is the only one of the
four that also re-announces itself at the point of use.
