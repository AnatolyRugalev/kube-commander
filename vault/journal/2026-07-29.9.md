# 2026-07-29 — DIAG-01: give the errors somewhere to be found

- Agent: claude-opus-5
- Milestone: — (feedback-driven, off the milestone line)
- Did: Triaged feedback `2026-07-29-external-secrets-crd-error` ("opening the
  `ExternalSecret` CRD errors out … need to find the actual error") and landed its
  prerequisite: a `WithLogger` seam on the shell, a log line in `surfaceError` — the
  single error funnel — and one in `handleDiscovery` for the failures that never reach a
  toast at all. The launcher passes the file logger `setupLogging` already installs. The

- **The feedback could not answer its own question, and that is the finding.** It asks to
  "find the actual error", and there was no way to: every failure in kubecom funnels into
  a status-bar toast that lives five seconds and is clipped to the terminal width, and
  then it is gone. The log file has existed since M2-RUN and the README has documented it
  since — but `grep slog internal/` returned **nothing**: only the launcher ever wrote to
  it (keymap warnings, menu-config, config migration, state file). The TUI owns the
  terminal, so a diagnostic has exactly two possible destinations and kubecom was using
  neither for the one thing a user needs. That is why this leg is the logging and not the
  CRD fix: the CRD fix has a prerequisite, and the prerequisite is one commit.
- **It goes in the funnel, not at the call sites.** `statusbar.SetError` is called in
  exactly one place — `surfaceError` — with ~25 call sites feeding it. Logging there makes
  "every surfaced error is recorded" a property of the funnel rather than a convention 25
  sites have to keep, and a future leg that surfaces a new error is covered without
  knowing this decision exists. D159 pt 1 states the constraint that keeps it true: a new
  error path goes *through* `surfaceError`, never around it.
- **Discovery is the other half, and it is the half that matters for a missing CRD.**
  Discovery's failures are the shell's one class that never toasts *by design*: a total
  failure keeps the seed menu, a per-group failure isolates that group and shows it as
  unavailable (#87/#76 — the original's central bug, fixed by staying quiet). Quiet on
  screen is right; quiet everywhere is how "why is this kind missing from the menu?"
  becomes unanswerable. `logDiscovery` splits the severities — a total failure is an
  ERROR and returns early (a pass that failed wholesale has nothing useful to say about
  individual groups), a per-group failure is a WARN naming the groupVersion. Menu
  behaviour is byte-for-byte unchanged.
- **Injected, defaulting to discard — not `slog.Default()` read in place.** The idiomatic
  Go move is to call the package-level `slog` and be done, and it is wrong here twice
  over: hermetic tests construct hundreds of models and drive error paths deliberately, so
  the default handler would turn the suite into noise, and a default handler still
  pointing at stderr under a running TUI is exactly the alt-screen corruption the
  stack.md logging rule forbids. `WithLogger` takes the sink, `NewWithKeymap` seeds
  `slog.New(slog.DiscardHandler)` so no call site needs a nil check, and the option
  ignores a nil argument so a launcher cannot un-seed it (`TestWithLoggerIgnoresNil`).
  The buffer a test injects is also what makes the log assertable at all.
- Verification note: every assertion was mutation-checked — removing the `surfaceError`
  log line fails three named tests, unwiring `logDiscovery` from `handleDiscovery` fails
  `TestDiscoveryReadyLogsThroughUpdate`, and dropping the early return fails
  `TestTotalDiscoveryFailureIsLoggedAsAnError` (whose result carries both an `Err` and a
  `Failed` entry precisely so that branch is not vacuous). `TestSurfacedErrorStillToasts`
  pins that the logging is additive.
- **Runtime-verified, not just hermetically.** Built the binary, ran it under a pty
  against a kubeconfig pointing at `http://127.0.0.1:1`, and read the real log file:
  `level=ERROR msg="discovery failed" kind=unreachable error="Get \"http://127.0.0.1:1/api…\": dial tcp … connection refused"`.
  That is the whole leg working end to end — classified kind, full underlying cause, in
  the file the README names.
- **What is deliberately not done:** the CRD bug. The sandbox has no cluster and no
  external-secrets CRDs, and the plausible causes (a conversion webhook the apiserver
  reports on LIST, a Table-conversion 406, an RBAC 403 on that group, a decode edge case
  in a printer column) are indistinguishable without the message and call for opposite
  fixes — one of them being "kubecom is correct, degrade more legibly". Choosing among
  them by guessing would be inventing a bug and shipping a fix for it (D79). CRD-01 sits
  in **Blocked** behind human task `2026-07-29-external-secrets-crd-error-log`, which asks
  for the log line plus two cheap discriminators (does `kubectl get externalsecrets` work
  at the same moment; do the sibling kinds in the group fail too).
- Decisions: D159 — every error the user is shown is also written to the log file; it is
  logged in the single `surfaceError` funnel (so new error paths must go through it), what
  is quiet on screen by design is loud in the log, only failures are written, and the sink
  is injected (`WithLogger`) with discard as the default.
