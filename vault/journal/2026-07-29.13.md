## Why the order around `resetCluster` is the whole implementation

`resetCluster` rebuilds the menu from the seed and folds in `m.menuExtras`, and it
clears the namespace scope. So the new extras have to be installed **before** it (or the
rebuilt menu is the departed context's), and the persister and restored namespace
**after** it (or the reset wipes them). That is the entire diff on the apply side —
three assignments split across one call — and it is why `resetCluster` was deliberately
left not touching either field back in M4-03.

Two smaller things worth knowing:

- A switch must not persist the namespace it restored. The scope came *out of* the state
  file it would be written back to, so persisting would be a no-op write on every switch
  and would defeat the point of a `-n` never touching stored state (D91). Only a pick
  persists; a test asserts neither persister was called by the switch itself.
- `LoadContextState` returns no error on purpose. Every failure mode it has (a missing
  file, a malformed one, an unresolvable path) already has a degrade at launch, and the
  shell owns the status bar in that frame with its "switched to …" notice — so the
  launcher logs and returns the degraded state, and the switch is never blocked by a
  config file. The nil-interface trap is guarded: the persister field is only set when
  the state path resolved, so it is never a typed nil.
