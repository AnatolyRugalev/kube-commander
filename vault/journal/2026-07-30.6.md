## What the leg had to decide: gate the tag, or trust that it was already green?

ci.yml triggers on `push: branches: [v1, main]` and PRs. A tag push matches none of those,
so before this leg the entire `make check` gate was **silently absent from the one push that
publishes**. Three ways to close that, and the choice is worth recording because it is the
kind that gets casually undone:

1. Add `tags: ['v*']` to ci.yml's push trigger. One line — and it does not gate anything:
   the two workflows would run in parallel, so a red `make check` and a successful publish
   are a normal outcome. Feedback without control is the wrong shape here.
2. Copy the check job into release.yml as a `needs:` dependency. It gates, and it duplicates
   the golangci-lint pin, the OS matrix, and the install snippet — in a repo that keeps a
   drift guard for `docs/keybindings.md` and another for `.goreleaser.yml`'s ldflags,
   introducing a hand-synced copy of the canonical gate would be a step backwards.
3. Make ci.yml reusable (`on: workflow_call`) and call it. Gates properly, no duplication.

Three costs two lines more than one and removes the duplication two would have created, so
it is what landed. The cost it does carry is a new coupling — ci.yml is now part of the
release path — which is exactly what D176 pt 2 exists to say out loud, because the failure
mode is invisible: rename ci.yml's `check` job and everything stays green until someone
pushes a tag.

## Why the dry run runs on every push and not just before a release

`make check` cannot see `.goreleaser.yml`. M5-02 added a guard for the one part of that file
expressible as a Go assertion (the `-X` paths), but the rest — archive templates, the goos ×
goarch matrix, the changelog filters, the snapshot version template — is only checked by
running goreleaser. Without a job, the first execution of the release config in CI is the
tag push, and D173 pt 1 says that run cannot be retried: the Go module proxy caches the
version permanently.

So the dry run is not a nicety, it is the release config's test suite, and it belongs where
tests belong — on every push. `--snapshot --clean` needs no tag, no secrets, and publishes
nothing (D173 pt 4). The observed cost is one job of a few minutes (M5-02's cold run took
3m47s for four cross-compiled targets; the warm re-run this leg did took 13s, so CI will sit
somewhere between depending on the Go build cache).

It also uploads `dist/*.tar.gz` + `checksums.txt` for 7 days. That is deliberate and aimed
at M5-10: D173 pt 1 hands a human the irreversible tag push, and asking them to install
goreleaser to see what the tag will produce is a poor trade when the workflow can just hand
them the archives. Bare binaries are excluded — same bits, twice the upload.

## The guard, and what it is actually protecting

`TestReleaseWorkflowPinsGoreleaser` asserts three things: `GORELEASER_VERSION` matches
`vX.Y.Z` exactly, every `goreleaser-action` step reads that env var rather than its own
literal, and a `--snapshot` invocation exists somewhere in the file.

The first two are D175 pt 2 made enforceable. That decision established that this config
**cannot be parsed** by an older goreleaser — v2.5.1 dies on `archives[].ids` before
building anything — which cuts both ways: a floating `latest` pin means a future v3 could
break the release path on a morning nobody touched the repo, and the failure would land on
the one run that matters. The third protects the previous section's argument from being
deleted as "a slow job on every push", which is precisely how it would be phrased.

All three were negative-checked rather than assumed: setting the pin to `latest`, deleting
`--snapshot` from the args, and hard-coding `v2.9.0` in one step each produce a distinct
failure naming the exact problem. A guard that has never been observed failing is decoration.

## What this leg cannot claim

The workflow has never executed. Nothing in a sandbox can run GitHub Actions, and the tag
half is reserved for a human regardless (D173 pt 1). What was actually verified is the
next-best layer, and it is a real one: `actionlint` type-checks the workflow the way `go vet`
type-checks code — it knows `goreleaser-action`'s inputs, which contexts are legal inside a
step's `with:`, and how to resolve `uses: ./.github/workflows/ci.yml` against a workflow that
declares `workflow_call` — and the goreleaser command the snapshot job runs was run here,
verbatim, at the pinned version, with its output globs checked against what the upload step
demands. That is the whole of what is checkable without credentials, and it leaves exactly
one unknown: whether GitHub's runner behaves as documented. The snapshot job answers that
part on this commit's own push, which is a pleasant property of putting the dry run on every
push — the leg that adds it is also the leg that tests it.
