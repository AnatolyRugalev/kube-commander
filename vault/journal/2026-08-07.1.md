## The survey was the leg's first real finding

The feedback's instruction — "check current behavior for both before doing the work — this
may already be partially done for one and not the other" — turned out to be right in a way
that changed the shape of the work rather than just saving effort.

There are three `/`-ish surfaces, not two. The logs view's live grep highlights, and has
since LOGS-03: `spanSubstring` finds the byte spans, `highlight` paints them with
`styles.Match`, and D145 records it. The resource table's `/` filter narrows and says
nothing. Cluster search neither highlights nor could easily.

That third case is why this leg is half the item. The table's filter is a case-insensitive
substring over the visible cells — so the matched runes can be re-derived at paint time from
the query and the cell, and nothing needs to be carried. A cluster-search hit can be a
**fuzzy subsequence** (D153: `wbp` matching `web-pod`, scattered runes) or a **label
selector** (D151: `-l app=web`, which matches nothing that appears in the label the reader
sees). In both cases the runes to mark are known only to the code that scored the hit, which
lives in a different package and has already thrown them away. That is a `kube.SearchHit`
shape question with a real answer to record, not a rider on a rendering change, so it is
SEARCH-06 with the argument written down rather than left to be re-derived.

## `styles.Match` was written for this three legs before anyone asked

The interesting part of the leg was not producing the spans, it was deciding whether the
cursor row keeps them — because M4-06's rule is stated flatly in `renderRow` and in a test
called `TestSelectionWinsOverCellColor`: "Selection wins outright over cell coloring … a row
whose STATUS is repainted mid-bar reads as a broken highlight rather than as information."
Extending that to matches is the obvious reading, and it is wrong.

The reason it is wrong is in the rule's own justification. Status color is *information about
the row*, and the comment closes by noting that the color "is still one keystroke away — move
off the row and it is there". A match is not information about the row; it is the reason the
row is on screen. Blanking it under the cursor blanks the answer on exactly the line the
reader is reading — and, once `Enter` commits the filter, on exactly the line `n`/`N` keeps
putting there. The escape hatch that makes the M4-06 rule tolerable does not exist here:
moving off the row to see why the row matched is not a thing anyone would do.

What settled it was finding that `styles.Match`'s own doc comment had already made this
decision, in M0, for the logs view: it "paints a background so a match is findable by eye in
a wall of log output, **using the Warn hue rather than Selection so a highlight is never
confused with the cursor (the two can appear on the same line)**". The one style in the theme
whose documented job is to coexist with the selection bar. So no new role, no new color
question — `paintRow` just needed the base style as a parameter (Selection for the cursor
row, body text otherwise) instead of reaching for `m.styles.App` four times.

## Cutting the role span instead of letting paintRow arbitrate

`paintRow` walks spans in order and clamps each to `last`, so overlapping spans do not
corrupt the line — the later one is simply truncated. That means the naive merge
(concatenate, sort) *works*, in the sense that it produces a well-formed line. It just makes
the outcome depend on sort order among equal starts: a match at the very start of a `Warn`
cell would win, a match in the middle would be clipped away by the role span that reached
`last` first, and neither behaviour is written down anywhere.

`mergeSpans` cuts the role spans around the matches instead, so the result is genuinely
disjoint before it reaches the painter and the precedence is a property of the data rather
than of the loop. The visible payoff is the case the test pins: `0/1` filtered by `1` renders
as `Warn("0/")` followed by `Match("1")` — the part of the cell that did not match keeps
saying what it said. The invisible payoff is that `paintRow`'s clamp goes back to being what
its comment claims it is, a defence against a pathological input, rather than the thing
quietly deciding precedence.

`cutSpan` is a single pass because both inputs are already sorted and internally disjoint,
and both are, for the same reason: `roleSpans` and `matchSpans` walk `m.visible` in display
order and each cell's own occurrences are found left to right, non-overlapping.

## The guard I copied from the logs view can never fire, and that is worth knowing

`spanSubstring` in `logsview` carries a careful degradation: if lowercasing changes the
string's **byte** length (`İ` → `i`), the offsets it found in the lowered copy no longer index
the original, so it reports the line as matching but returns no spans — highlighted wrongly
is worse than not highlighted.

I wrote the same guard here, and then could not write a test that tripped it. The reason is
that this code works in **runes**, not bytes, and `strings.ToLower` is `strings.Map` over
`unicode.ToLower`, which is rune → rune. The fold can change how many *bytes* a rune occupies
and it can lose a diacritic (Go's `ToLower("İ")` is `"i"`, not `"i̇"`), but the rune
count is preserved by construction. Candidates that look dangerous are not: `ﬁ` does not
decompose under `ToLower` at all, `ß` is already lower.

So the guard came out and the comment says why, with the pointer to `logsview` so the
contrast is legible from either side. This is the kind of thing worth stating in the code
rather than only in a journal entry: the next person to copy that function will copy it into
another byte-offset context, where it is still needed.

## What the frame-comparison test caught

`TestFilterHighlightKeepsWidthAndText` re-runs the existing layout invariant with a filter
on: at three pane widths and three horizontal scroll offsets, the ANSI-stripped frame must be
byte-identical to the same rows rendered with no filter. It failed on the first run — not
because painting moved anything, but because `SetFilter` re-clamps the scroll, so setting
`hoffset` before the filter left the two models on different offsets. A real ordering fact
about the component, surfaced by a test that was only trying to hold something else still.

The reason to spend a test on this at all is that match spans are in unclipped coordinates
and are shifted by `hoffset` inside `paintRow`, which is precisely the arithmetic that would
silently drop a rune or double one at a nonzero offset. Comparing whole stripped frames
catches that without anyone having to predict which offset breaks.
