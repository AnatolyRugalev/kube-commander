## Why the no-op is keyed on the extras list and not on the menu

The board's wording — "pinning an already-pinned or already-listed kind is a no-op with a
notice" — has a reading that quietly kills the feature. The menu already lists every kind
discovery finds (`Reconcile` appends the CRDs the seed does not know, D57), so "already
listed → do nothing" means pressing `*` on the `ExternalSecret` row you just found does
nothing at all, and the feedback that started this line was about `ExternalSecret`.

The pin is not what puts a kind on screen in a healthy, fully-discovered session. It is
what keeps it there when discovery does *not* list it: before the pass returns (the seed +
extras are what the first frame draws), when its API group fails (D187 marks the row
unavailable rather than inventing it), and after any later slice narrows what a CRD-heavy
menu lists — which is the whole premise of CRD-PIN-04. So the test is against
`m.menuExtras`, the merged authored + pinned list the launcher hands in: "is this kind
already an *entry*", which is the thing a second row would duplicate.

That also makes the authored case fall out for free rather than needing its own branch. A
kind hand-written into `menus/<context>.yaml` is in the extras list, so `*` on it declines
and says so — correct, because D193 pt 3 makes the authored entry win, so the pin it would
record could never render and would sit in the state file forever as a line with no effect.

## The key could not be `p`, and the id should not have been `pin.*`

`p` is the port picker's local-port prompt (D139) and `P` is `res.children` (D165). The
browse context is flat — one action per chord — so the mnemonic is spent twice over, the
same wall `logs.previous` hit when it took `ctrl+p` (D177). `*` takes the *starred /
favourite* reading instead: free, not a reserved nav chord (D10), and a symbol rather than
another letter in a context where the row actions keep claiming letters. It carries text,
so it would type into an always-open query field — which is exactly why this slice's
surfaces are the menu and the table and not the search view or a picker (see below).

The id started as the board's `pin.toggle` and the help overlay caught it: `FullHelp`
groups bindings by action namespace, one column each, and the registry already has sixteen.
A `pin.*` namespace holding a single action buys a seventeenth column on an 80-column
overlay for nothing. `menu.pin` joins `menu.toggle`, and reads better anyway — the menu is
what a pin changes. D201 pt 3 turns that into the standing rule, because "new feature, new
namespace" is the default instinct and the cost is invisible from the keymap file.

## What this slice deliberately did not do

- **The pickers and the search view do not offer the gesture**, though the board's notes
  named the resource picker. Every picker filters as you type since PAL-01/D194, and the
  search view's query field has always been open (D140 pt 1), so a bare `*` there types a
  `*` — it is not that the gesture is hard to wire, it is that the key cannot reach it.
  Nor is it needed for the feedback's flow: a search hit drills into the browse table for
  that kind, and `*` on the table pins what you are looking at. A picker-side pin wants
  either a no-text chord or the row-verb palette PAL-04 is building, and it should be
  decided there rather than spent now.
- **No hint-bar entry.** CRD-PIN-03's board notes already carry it, and it belongs with the
  unpin: hinting a key whose only half is "add" invites the question the next slice answers.
  `?` and `docs/keybindings.md` carry it meanwhile.
- **No unpin.** `State.Unpin` has existed since CRD-PIN-01 and the action is named for the
  toggle it becomes; what is missing is provenance on the menu `Item` — only a *pinned* row
  may be unpinned, and today an Item cannot say where it came from. That is the whole of
  CRD-PIN-03 and the reason it is one slice rather than a rider here.

## One thing worth knowing for the next leg

`statePersister` retains the loaded `config.State` and mutates it in place, which is now
load-bearing rather than incidental: `SaveFile` marshals the whole struct, so a pin written
from a freshly-zeroed State would drop the namespace the same session recorded, and vice
versa. Two writers, one file, one in-memory copy — a third write into that file (there will
be one; the state file is where recorded-for-you things go) must go through the same object
rather than construct its own.
