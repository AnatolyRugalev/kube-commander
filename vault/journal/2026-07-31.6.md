## The discriminator problem

The obvious way to write this test is the one that proves nothing. Take a Deployment,
scale it, assert `spec.replicas`. It passes — and it passes just as well if the
`"scale"` argument is deleted from the `Patch` call, because `{"spec":{"replicas":3}}`
against the *object body* sets the very same field on the very same object. Every
scalable built-in keeps replicas at `spec.replicas` in its own schema too, so the two
code paths are indistinguishable by their effect on the kinds you would naturally reach
for. Deployment and StatefulSet are in this test because the slice's note asks for two
kinds and one contract, not because either can tell you where the patch went.

What tells you is a kind that has no `scale` subresource. `apps/v1` registers one for
Deployment, ReplicaSet, StatefulSet and ReplicationController, and **not for
DaemonSet** — a DaemonSet runs one pod per node by definition, so there is no replica
count to set. Ask a real apiserver to patch `daemonsets/agent/scale` and there is no
route to answer with: 404, `Classify` → `KindNotFound`. Ask the fake and it cheerfully
applies the patch to the object body and reports success.

So the assertion is a refusal, and it is the one place in this test where the fake's
answer and the server's answer differ in kind rather than in detail. Removing the
subresource argument is exactly the mutation it catches (below), which is the practical
statement of the same thing.

## A rejected patch that is not rejected

The DaemonSet subtest also reads the object back and asserts no `spec.replicas`
appeared, which looks redundant next to the error check until you see what the
apiserver does with the body-patch version of the same call:

```
W0731 06:22:20.614838 warnings.go:70] unknown field "spec.replicas"
```

— a warning, and a **200**. A merge patch carrying a field the typed schema does not
have is decoded leniently: the unknown key is dropped and the request succeeds. So "the
server would reject a wrong patch" is not true in general, and any later slice that
wants to prove a patch was malformed has to read the object back rather than trust the
error. `stack.md` carries this; it is the sort of thing that costs an afternoon exactly
once.

## Zero is a value

`spec.replicas: 0` is the "stop this workload without losing it" case, and it is the
one a plausible bug makes disappear: anything that treats the replica count as
optional-when-empty — a struct with `omitempty`, a guard that skips a no-op patch —
turns "scale to zero" into "leave it alone", silently, in the direction that keeps
pods running. `scalePatch` builds its JSON with `fmt.Sprintf` and has no such hole
today, so the assertion is a guard on the future rather than a bug found; mutation 2
below is what it looks like when it fires.

The scale-to-zero assertion reads the count two ways — from the workload body and from
`GetScale` — because the write-through is the thing being proven, and a fake has only
one object to answer both questions from.

The sibling-field check (`minReadySeconds: 7`, set at creation and outside the Scale
schema) covers the other direction: a scale that arrived as a whole-object write would
drop it back to zero. It is cheap and it is the only witness available, since the Scale
schema is small enough that nothing else survives a round trip through it.

## Watched fail, twice

1. **Drop the `"scale"` argument** from the `Patch` call in `Scale` → the DaemonSet
   subtest fails with `scaling a daemonset succeeded; the patch did not go to a scale
   subresource`, and the run prints the unknown-field warning above. The other four
   subtests still pass, which is the whole point of the previous section.
2. **Make `scalePatch` return `{}` for zero** (the omitempty-shaped bug) → the
   deployment subtest fails on both reads, `spec.replicas = 3, want 0` and
   `scale.spec.replicas = 3, want 0`. Two messages rather than one because the body and
   the subresource are checked separately; a mismatch *between* them would be a
   different bug and is worth being able to see.
