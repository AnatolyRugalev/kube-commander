## The bug is in the word "printed", and it is worth being precise about it

The report guesses the age "is computed once (probably at fetch/render time from the
resource's creation timestamp) and never refreshed on a tick". Every clause of that is true
except *who* computes it. kubecom has never computed an age. It asks the API server for
`application/json;as=Table`, and the server runs the same printer `kubectl get` runs —
`printers.translateTimestampSince`, which is `duration.HumanDuration(time.Since(created))` —
and hands back the finished string `12s`. Everything downstream of that, all the way to the
terminal, moves a `[]any` of already-rendered cells around.

That distinction is the whole leg. If the age were computed at render time, the fix is a
repaint. Because it is computed at *print* time, a repaint changes nothing: the cell is a
string and it will still be `12s` after a thousand paints. The only thing that re-prints it
is a new response from the server — a re-List, or a watch delta for that specific row — and
an idle pod generates neither. So the freshness of AGE is currently a function of how often
the object happens to be modified, which for a healthy Pod is never.

The reason this reads as a kubecom bug and not a Kubernetes one is that `kubectl get` prints
and exits. The value is correct for the entire lifetime of the program that produced it. A
TUI keeps the frame up, and inherits a value with a shelf life it does not honour.

## Re-deriving on the client, and why only this one column

Once the age is being computed locally the obvious question is where that stops. The
temptation is a general "refresh the derived columns" seam, and the answer is that there are
no other derived columns — there is one column kubecom can re-derive and it is a coincidence
of what the row already carries.

`decodeTable` unpacks each row's embedded `PartialObjectMetadata` for `ObjectRef`
(`IncludeObject=Metadata`, the Table default). `creationTimestamp` is sitting in that same
struct, unused. So AGE is the one column whose *input* kubecom already holds — everything
else (`READY 1/1`, `STATUS CrashLoopBackOff`, `RESTARTS 4`) is the server's reading of an
object body kubecom deliberately never fetched. Server-side printing exists so kubecom can
show a CRD's columns without knowing what they mean; re-deriving any of them would require
knowing exactly that. D234 pt 2 writes that boundary down, because "we recompute AGE locally"
is the kind of sentence a later leg reads as a licence.

The formatter matters more than it looks. `HumanDuration` is not a simple unit picker: it
switches to compound forms at specific thresholds (`5m30s` under ten minutes, plain `45m`
under three hours, `5d3h` under eight days) and clamps a slightly-future timestamp to `0s`
instead of going negative. A reasonable hand-rolled version gets `2h` where the server says
`120m` — I know because my first test asserted exactly that and failed. A re-derived cell
that disagrees with a freshly-printed one is a worse bug than the stale cell, because it
appears only on the rows nothing has touched, which is the same set of rows this leg exists
to fix.

## The column has to be allowed to grow

`RefreshAges` re-derives the whole view — filter, sort, widths — rather than just rewriting
cells, and that is not caution. `measureWidths` sizes the age column at snapshot time, and
`padRight` explicitly never truncates: the widest cell defines the width, and the line is
clipped once, at the pane. So a cell that outgrows its measured width does not get cut, it
pushes every column to its right by the overflow — on that one row. A pane left open long
enough to hit `59m` → `1h2m` would have started tearing exactly one row at a time, which
would have read as a rendering bug with no obvious connection to the age fix that caused it.
`TestRefreshAgesWidensTheColumn` asserts the frame stays square across the transition rather
than asserting the width alone, for the same reason AUTH-06's tests did.

The re-derivation is skipped when no cell moved, which is what makes it affordable to run
every second on the ticks where the reader is looking at a table of week-old objects.

## Why the tick has no generation tag, and why that is a decision rather than laziness

`metrics.go` next door is the same shape — a `tea.Tick` chain that refreshes a piece of the
table — and it carries a generation counter, a cancel func, a restart in `watchResource`, and
a stale-result guard, because **each of its ticks issues a request**. A sample set that lands
after the reader has changed kind must not be painted onto the new table, so it has to know
which poll it belongs to.

This tick issues nothing. It reads timestamps that are already in the model and writes
strings back into the same rows. There is no in-flight anything to invalidate, so a "stale"
tick is indistinguishable from a fresh one and there is nothing for a generation to guard. Tag
it anyway and the tag becomes a thing to keep correct across kind changes, namespace
re-scopes, drill-downs, reconnects and context switches — five places that already exist and
would each need to remember to restart a clock. The failure mode of getting that wrong is a
column that silently stops updating, which is the bug that was reported. So D234 pt 4 fixes it
as unconditional: armed by `Init`, re-armed by its own handler, off only when the program is.

The honest cost is a wakeup per second for the life of the process, including while the
welcome screen is up. That is the price of a design that cannot be left off, and it is
visible in one place (`ageInterval`) if a later leg decides otherwise.

## Three Init tests changed shape, and the reason is worth noting

`Init` used to return exactly one command in each of its three cases, and three tests asserted
on `initCmd()` directly — `if _, ok := initCmd().(startDiscoveryMsg); !ok`. Adding a second
unconditional command turned all three into `tea.BatchMsg` and broke them, including
`TestInitInertWithoutDiscoverer`, whose whole claim was `Init() == nil`.

The fix is `initMsgs` + `findMsg`: run the batch, flatten it, look for the message you care
about. What that changes is the claim each test makes — from "Init emits X" to "Init emits X
among whatever else it emits" — and the inert one from "Init does nothing" to "Init does not
start discovery", which is what it was actually about. The first phrasing was only ever true
by accident of there being one startup concern at a time, and it would have broken again on
the next one.
