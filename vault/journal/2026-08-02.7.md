## Why the merged extras list had to come apart

CRD-PIN-01 merged the authored entries and the pins in the launcher (`mergeMenuExtras`) and
handed the shell one list, which was right for a feature that could only *add*. The unpin
makes the question "where did this row come from?" load-bearing, and a merged list has
thrown that away by construction: `externalsecrets` in `menuExtras` might be a line the
user wrote by hand — theirs to edit, not `*`'s to delete — or a pin `*` recorded last week.

So the two lists arrive separately and are merged once, in the menu, in the order that
*is* the precedence rule: `AddExtras` then `AddPinned`, with the GVR dedupe that was
already there skipping a pin the authored list has claimed. That deletes the launcher's
merge and its four tests rather than adding a parallel mechanism — D193 pt 3's "authored
wins" now has one implementation instead of two agreeing ones, and it is tested where it
happens (`TestAddPinnedYieldsToAnAuthoredEntry`).

## The rule that keeps a stray keypress from eating the menu

The tempting removal rule is "the state file says this kind is pinned, so remove its row".
It is wrong in three ordinary cases, all of which happen: `*` on a **seed row** records a
pin that renders nothing (the row was already there), a pin can name a kind an **authored**
entry also names (the authored row wins and renders), and a pin very often names a kind
**discovery** lists too. Under the tempting rule, unpinning any of those deletes a row the
pin never created — including Pods.

So provenance lives on the row, set by the code that inserts it: `AddPinned` marks only
what it actually inserts, `Reconcile` marks what discovery lists, and `Unpin` removes a row
only when it is `Pinned && !Discovered`. Everything else is a no-op on the menu while still
clearing the state-file line, which is the honest outcome — the pin is gone, and the row
was never the pin's to begin with.

`Discovered` is also why the revert case is free rather than a special path: a pinned row
whose twin turns up in discovery is *the same row*, upgraded in place (that dedupe is D57's
and predates all of this), so by the time anyone presses `*` on it the row already knows it
would survive.

## What the toggle says, and the one case it refuses

Three outcomes, and each says which it was:

- **not an entry → pinned X.** Unchanged from CRD-PIN-02.
- **a pin → unpinned X.** The same sentence whether or not the row survives: what the
  reader did is the same, and whether the kind is in the cluster's discovery is on screen.
- **an authored entry → "X is in this context's menu file".** The one refusal, and the
  wording is the point: the old copy said "already in the menu", which after this leg would
  read as "and yet `*` won't remove it". Naming the file says where the delete key is.

## Two things worth knowing for the next leg

- **The hint line elides past drill-in below ~120 columns**, so the pin hint (and the
  namespace, help and quit hints, which were already there) is invisible at 80×24. That is
  pre-existing, not something this leg introduced; shortening `menu.pin`'s description to
  "Pin/unpin the kind for this context" bought the entry back at 120. A leg that wants the
  menu hints legible at 80 has to shorten descriptions globally or elide differently — it
  is a `?`-overlay-wide question (D147 pt 3), not a per-action one.
- **Unpinning the kind you are currently browsing removes its menu row while the table
  keeps streaming it.** The active marker is keyed by GVR, so it simply stops matching;
  `esc` returns to a menu without that row. Deliberate — the alternative is refusing the
  gesture on the open kind, which is the surface a reader is most likely to press it from.
