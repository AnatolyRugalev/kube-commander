## Why the variable is not the descriptor, and why that is the whole leg

The tempting fix is `os.Stderr = logFile`. It fixes nothing that matters here, for three
separate reasons, and each one is a different mechanism:

- **client-go already has the old value.** `plugin/pkg/client/auth/exec` builds its
  authenticator with `stderr: os.Stderr` and later runs the plugin with
  `cmd.Stderr = a.stderr`. The capture happens when the authenticator is constructed —
  at connect time, before any refresh — so a later reassignment is read by nobody.
- **A child inherits a descriptor, not a variable.** Even a writer that re-reads
  `os.Stderr` on every use hands `*os.File` → fd 2 to `os/exec`, which dups *that fd*
  into the child.
- **The runtime writes a panic straight to fd 2.** No Go-level indirection is consulted
  at all.

So the fix has to be dup2, and once it is dup2 the interesting question stops being "how
do I redirect" and becomes "when must I stop". Two answers, both recorded as D247 points
because both are silently reversible by a well-meaning later leg:

**The redirect starts after the last fallible startup step.** `runTUI` can still fail
after `setupLogging` — a missing kubeconfig, an unparseable config, a context that does
not exist — and those errors are printed by cobra to stderr. Installing the redirect
beside `setupLogging`, which is where it looks like it belongs, sends every one of them
to a log file the user has no reason to look at yet, for a kubecom that never drew a
frame. It goes in immediately before the model is built and `Close()` runs before
`runTUI` returns, so the window is the TUI's life exactly.

**It stops inside every suspend.** `$EDITOR`, `kubectl exec`, an approved `aws sso
login` — the reader is watching those, and an editor that cannot open a file says so on
stderr. bubbletea hands an `ExecCommand` the `os.Stderr` *variable*, which resolves to
fd 2 at write time, so moving the descriptor back for the length of `Run` is enough and
no stream plumbing changes. The window is strictly inside bubbletea's own
release/re-capture, so the TUI is never on screen while fd 2 points away from the log.

## The wrapper is a guard against the leg that has not been written yet

`Model.suspend` could have been three lines inlined at three call sites. It is a wrapper
because the failure mode is a *fourth* suspend: a future action that hands the terminal
over, calls `tea.Exec` directly, and quietly sends its subprocess's stderr to a file the
user is not tailing. That is not a compile error and it is not visible in a diff review
of the new action alone.

`TestEverySuspendGoesThroughTheHandover` is therefore a type assertion on what bubbletea
would be handed, for all four routes (edit, exec in-process, exec via kubectl, reauth).
It reads tea's unexported `execMsg.cmd` field by reflection — reading a `Type` is allowed
where reading a value is not, so no `unsafe` — which is the only way to observe the
choice from inside this package. Both mutations confirm it: reverting the edit call site
fails with `*tui.editCommand, want tui.handover`, reverting the kubectl one fails with
`*tea.osExecCommand`.

That second mutation is also why `suspendProcess` exists at all. bubbletea's `*exec.Cmd`
adapter (`osExecCommand`) is unexported and `tea.ExecProcess` returns a finished `Cmd`,
so there is no seam to compose a wrapper onto; `procCommand` re-implements that adapter
to the same contract (fill a stream only if the caller left it nil) purely so the kubectl
parity path is wrapped like the other three. A test pins that contract, because "only if
nil" is the half a re-implementation loses.

## dup2 is not portable, in a way that only bites on release

`syscall.Dup2` does not exist on linux/arm64 — the syscall was dropped there, leaving
only `dup3` — and `syscall.Dup3` does not exist on darwin. kubecom releases for
linux/{amd64,arm64} and darwin/{amd64,arm64}, so a single-file implementation compiles
on the sandbox and fails on a quarter of the release matrix, at goreleaser time, in a
leg that has nothing to do with this one. Hence the two-line build-tagged shim:
`dup3(old,new,0)` is defined to behave exactly as `dup2` on Linux, `dup2` on the BSDs.
Recorded in `stack.md` rather than only in a comment, because the next person reaching
for a descriptor trick will hit it too.

## The claim a test cannot make, and why no new human task

What is hermetic here is more than usual: the tests move the real fd 2 (each installs its
own file as a stand-in "terminal" first, so a `Release` lands somewhere assertable rather
than on the test runner's stderr) and assert that a *subprocess* wired to `os.Stderr` —
which is precisely how client-go runs the plugin — lands in the log before the release
and on the terminal after it. The pty run above adds that the binary still launches.

What remains is one sitting of dogfood: on a real expired SSO session, the plugin's stderr
no longer appears over the panes — and, the half that matters more, the three suspends
still show the reader everything they used to. That went in as **item 8** of the existing
`vault/human-tasks/2026-08-02-conversion-webhook-reason-dogfood.md` rather than as a new
file: items 6 and 7 already ask the maintainer to reach exactly that expired session, and
a second task competing for the same setup would have made the queue longer without making
anything more likely to be checked. It stays advisory and blocks nothing — the regression
risk it covers (a suspend that has gone silent) is the one thing here a test can only
approximate, since what the test asserts is that fd 2 moved, not that a human saw it.
