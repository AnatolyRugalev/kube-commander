## The marker list has a property, not a length

The obvious way to write this leg is to collect AWS SSO error strings until the list feels
complete, which is a list that can only be judged by whether the next string is on it. The
list here is judged by an invariant instead: **every marker contains the substring "sso"**.
That is what makes the match narrow in the sense D195 pt 2 asked for — it is not that the
three sentences were chosen carefully, it is that no AWS credential failure which does not
mention SSO can trip them, whatever the CLI's wording drifts to.

The tests are written from that invariant rather than from the sentences: the negative cases
are the four failures a reader would most plausibly want handled — `ExpiredTokenException`,
`Unable to locate credentials`, `AccessDeniedException … eks:DescribeCluster`,
`ResourceNotFoundException … No cluster found` — and each one needs a *different* fix
(wait for the plugin's own refresh, run `aws configure`, fix an IAM policy, fix the
kubeconfig). Offering `aws sso login` for any of them would be worse than the nameless auth
error the feedback complained about, because it would be confidently wrong.

`usage: aws [options] <command> <subcommand>` is in the negative set for a different
reason: it mentions `aws` and it is stderr from a real failure, so it is the case that
catches a match written against the *command* rather than against the failure.

## Two kinds of "no remediation", and only one of them is a gap

`SuggestedRemediation` returns false for two quite different situations, and it is worth
being explicit that they are not the same, because AUTH-04 renders them the same way and
AUTH-05 must not.

*Not recognised* — a `gcloud` plugin, a wrapper script, a non-SSO AWS failure — is the
catalogue honestly having nothing to say. The surface shows the stderr and stops, which is
already most of what the feedback wanted.

*Recognised but unsubstantiated* — the SSO sentence is there, the plugin is `aws`, and the
stanza names no profile — is the case D195 pt 5 legislated for, and it is the one where the
tempting fix is wrong. kubecom could resolve the profile from `AWS_PROFILE` in its own
environment, or from `~/.aws/config`'s `default`, and be right most of the time. It would
then be quietly wrong for exactly the user whose kubeconfig has several contexts on
different profiles — who is the user this feature exists for. So it declines, and D212 pt 3
says why in a form the next entry inherits.

Note which guard actually protects the `NotFound` case: not the `Failed()` gate (a missing
binary *is* a failure) but the stderr match, because a binary that never ran printed
nothing. That is load-bearing by accident, so `TestSuggestedRemediationNotFoundAndNilPlugin`
pins it explicitly rather than relying on it falling out.

## A table with one entry, tested as a table

`pluginRemediations` has one entry, so its ordering rule — a recognised entry ends the
search — is unobservable today: with a single entry, `return` and `continue` compile to the
same behaviour. That is exactly the kind of rule that gets refactored away by someone
tidying up, and then rediscovered when `gcloud` lands and an `aws` plugin with no profile
starts being offered a `gcloud` command.

So `TestRemediationCatalogueStopsAtTheFirstMatch` installs a permissive second entry for the
duration of the test and asserts both directions: the catch-all does *not* run for a plugin
`aws-sso` recognised but could not substantiate, and it *does* run for a `gcloud` plugin
`aws-sso` never claimed. The mutation is recorded in Verify above, and it is the only one of
the five that tests a rule about a future the code does not yet have.

## `flagValue` is not an argv parser, and the difference is a decision

Reading `--profile` out of the stanza's args looks like it wants a flag parser, and it does
not get one: `pflag` on a foreign command's argv would need that command's flag definitions
to know whether `--profile` takes a value, and kubecom has no business modelling the AWS
CLI's grammar. So it is a two-spelling substring scan, and the interesting part is what it
refuses. `--profile` as the last token, `--profile --debug`, and `--profile=` all read as
**absent** rather than as a value to salvage, because a stanza spelled that way is ambiguous
for the plugin's own run too — the CLI would have failed on it, or consumed the next flag as
a profile name. Guessing which is a worse answer than declining, and it is the same
declining as pt 3's.

Last-occurrence-wins is the one thing it does copy from real parsers, since that is what the
plugin's own invocation does with a repeated flag, and a remediation that disagreed with the
failing command about which profile it ran under would be the most confusing possible output.
