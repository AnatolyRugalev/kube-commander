# 2026-07-25 — LOGS-03: regex grep mode + match highlighting in the logs view

- Agent: claude-opus-5
- Milestone: M3
- Did: Gave the logs view's live grep a second mode and a way to see what it hit.
  `logs.regex` (`ctrl+r`) re-reads the same field as a case-insensitive regex instead of
  a case-insensitive substring, and in either mode every matched span in a shown line is
  painted with a new shared `styles.Match` role. A pattern that does not compile keeps
  narrowing by the last one that did, with the header saying `invalid regex`. → D145.
- The interesting constraint was **where the toggle can live**. LOGS-02 established that
  the grep field swallows every text-producing key while it is open, so `f` and `q` and
  `/` type characters there. A mode toggle bound to a letter would therefore only work
  *before* you start typing — which is exactly backwards: you discover your substring
  wants to be a pattern halfway through typing it. So `logs.regex` is a no-text chord
  (`ctrl+r`, free in the browse context), which `routeLogsFilterKey`'s existing
  mapped-and-no-text branch already routes as an action. Nothing in the wiring changed:
  the whole leg is the component, the registry, and one style. That is also why it is
  hinted in *both* logs contexts, where follow and quit are hinted in only one.
- The degrade got the most thought. "Invalid regex → no match" is the obvious rule and it
  is unusable in a live filter: `err(` is a state you pass through on the way to
  `err(or)?`, and blanking the screen at every intermediate keystroke means you cannot
  actually type a pattern while watching. So `compile()` keeps the last pattern that
  compiled and raises `reBad`; `shown()` narrows by the old one; the header flags the
  query on screen as not-the-one-being-applied. The "no match" half survives for the case
  where there is genuinely nothing to fall back to (regex mode, first query invalid) —
  showing the unfiltered stream there would be pretending the query said something it
  didn't. The flag sits *before* the counts in the header because the header clips from
  the right, and "these counts aren't your query's" outranks the counts.
- Kept the throughput promise the open human-task is about. The empty-query path is
  byte-for-byte what it was: join the buffer, no matcher, no highlighting — so the
  unfiltered high-throughput stream did not get slower this leg. Substring mode keeps its
  `strings.Contains` membership test and computes spans only for lines it already kept;
  only regex mode pays a regexp scan per line, and only because you asked for it. Also
  removed a pre-existing double scan: `header()` used to re-run `shown()` just to label
  the count, so every frame matched the whole buffer twice. `render()` now records the
  count and `View` costs nothing beyond drawing.
- One sharp edge worth knowing: highlighting means **a matching line is no longer a
  contiguous run of bytes in the frame**, so two existing tests that asserted
  `strings.Contains(view, "keep this")` broke the moment the match was styled. Both test
  files grew an `ansi.Strip` helper (`plain` / `frame`) and content assertions go through
  it; assertions about the highlight itself compare against `styles.Match.Render(span)`
  rather than restating an escape sequence. Any future in-content highlight will hit this
  same wall — it is D145 pt 4.
- Small correctness note: substring spans come from a lowercased copy of the line, which
  only indexes the original when folding preserved the byte length. For the rare fold
  that does not (`İ` → two runes), the line still matches — the match is real — but is
  shown unhighlighted rather than sliced at offsets that no longer line up (tested).
- Decisions: D145 — a live filter degrades to its last working pattern and labels it
  (never blank on a half-typed query, never silently apply something untyped); a mode
  toggle for a text field must be a no-text chord; the unfiltered render path stays free
  of match work; highlighting is a shared `styles.Match` role and it breaks naive
  content assertions on a rendered frame.
