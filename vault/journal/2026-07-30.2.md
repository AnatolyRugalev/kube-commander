## What was actually hard: proving the pick, not making it

The mechanism was already built and tested (M4-12b-1), and the picker component is the
same one six other surfaces reuse, so the code here is small. The interesting question
was what to assert. "The view changed after the pick" is the assertion that looks
obvious and proves almost nothing — the same trap D170 and D171 each hit — because
fifteen of sixteen components repainting also changes the view.

`TestThemePickRepaintsAndPersists` reuses M4-12b-1's oracle instead: the shell after the
pick must render **byte-identically** to one built with that theme by `WithTheme`. That
needed one adjustment which is worth remembering, because it will catch the next person
who compares a rendered shell against a reference: the pick also writes a status-bar
notice, so the reference has to carry the same notice or the comparison fails on the
bar rather than on colors. `want.surfaceNotice("theme monokai")` is the whole fix, and
it is a reminder that this equality assertion compares *everything on screen*.

The theme picker also joined `themeSurfaces`, so the applyStyles equality test now
covers the component this leg added — D171 pt 1's rule ("a new component field is added
to `applyStyles` in the same leg") applied to itself. It has to be seeded with fixed
rows rather than opened through `openThemePicker`, because the real opener marks the
*rendering* theme: the launch-themed build would mark `monokai` and the restyled build
`default`, and the test would fail on glyphs (a real difference, just not the one it
exists to find).

## The batch, and why two tests look like they are working around something

`handleThemeSelected` returns `tea.Batch(notice, persist)`. The notice's half is a
`tea.Tick(errorDisplay)` — a five-second sleep — so a test that runs the batch to reach
the write-back sleeps five seconds, and one that runs it to check the notice finds the
notice *cleared*. Both were observed before they were fixed, and the fixes are the
existing precedents rather than new machinery:

- the notice is asserted **synchronously**, right after the pick, because
  `surfaceNotice` writes it onto the status bar itself and only the auto-clear is a Cmd;
- the write-back is reached with `themeCmdMsgs`, which runs each sub-command with a
  200 ms timeout and skips whatever blocks — the `copiedClipboard` helper (M3-08b) does
  exactly this for the same reason, so the shape is not novel.

A successful `PersistTheme` returns a nil message (the `persistNamespace` precedent),
which the helper drops, so "no messages" is the success assertion and an `ErrorMsg` is
the failure one.

## The write-back is the risk, and three tests are about not losing a config

`config.SaveFile` marshals the whole `Config`, so the failure mode is silent data loss:
a fresh `&config.Config{Theme: name}` deletes the user's `keys:` section, and a copy
held from launch reverts anything they edited since. `configThemePersister` therefore
re-reads the file at write time, sets one field and saves. Two less obvious calls:

- **A missing config is created, not an error.** Most users have no config file at all,
  so the first theme pick has to write one; `LoadFile` already treats absent as the zero
  config and `SaveFile` creates the directory, so this fell out for free — but it is
  worth a test, because "load first" instinctively reads as "require a file".
- **An unparseable config fails the write.** If the file went invalid while kubecom ran,
  saving would replace it with defaults. Losing a color choice is recoverable; losing a
  hand-written keymap is not. The shell toasts the failure (D74) and keeps the theme for
  the session (principle 3).

What no shape of save can keep is comments and formatting — `sigs.k8s.io/yaml` marshals a
struct, not a document. That is now stated in the README next to the picker, with the
advice to set `theme:` by hand if you keep comments, rather than being discovered by a
user whose annotated config came back canonicalized.

## Two small deliberate asymmetries

**This picker is never inert.** Every other picker in the shell opens nothing without
its seam, because an empty modal is worse than no gesture. The theme registry is
compiled in, so there is nothing to be missing: with no persister the pick still
repaints and only the memory is lost. That is D172 pt 1, recorded because the
inert-without-a-seam pattern is otherwise uniform enough to "fix" this into.

**`resetCluster` leaves the theme picker open.** Every other picker is dismissed by a
cluster teardown because it shows cluster or kubeconfig data a switch invalidates. A
palette list is neither, so closing it would yank an overlay the reader opened for an
unrelated reason. The omission is commented in `resetCluster` so it reads as a decision
rather than a missed line, and `TestThemeSwitchSurvivesAContextSwitch` pins the rest of
it: a teardown neither reverts the palette nor drops the persister.

## Key choice and the doc

`T` — the mnemonic, free in the browse context, not a reserved nav chord (D10), and it
joins the capital-letter app-global family (`C` context, `M` mouse, `F` forwards, `X`
stop-all, `P` pods; lowercase `t` is `logs.timestamps`). It is deliberately *not* in the
ctrl+<letter> family the search surfaces need: this picker's filter is opt-in (`/`), so
no always-open text field can swallow a plain letter (D140 pt 1).

`theme.switch` forms a new action namespace, so the `?` overlay and the generated
`docs/keybindings.md` grew a sixteenth column — which is why two counts in
`keymap/help_test.go` moved. It is not hinted on the bottom hint line: those lines are
already eliding (D147 pt 3 / LOGS-04b's reasoning), and a theme switch is a
once-a-session gesture that self-announces the moment it fires.
