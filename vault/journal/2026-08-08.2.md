## The design that looks obvious, and the ten minutes that killed it

The board's brief said "have the panes paint it", which is the natural reading: give
`Styles` a background, hand it to the pane frames, done. Before writing any of that I
rendered a miniature of kubecom's actual frame — a bordered pane holding a line with two
differently-styled spans, joined above and below with a bar and a hint line — and wrapped
the whole thing in `lipgloss.NewStyle().Background(c).Width(w).Height(h)`. What comes back:

```
\x1b[48;2;48;48;48m\x1b[38;2;136;136;136m│\x1b[m\x1b[38;2;255;0;0mRED\x1b[m plain …
```

The outer background opens, the border glyph's foreground opens, and then the *inner*
style's reset (`\x1b[m`) closes both. Everything after the first nested span on that line
— the text, the spaces, the closing border — renders on the terminal's background. lipgloss
does not re-open an outer background after a nested reset, so a composed frame wrapped this
way comes back painted at its margins and bare through its middle. That is not a bug to
work around; it is what "wrap a styled string" means when the styling is already in-band.

Painting per-component instead is the same failure spread over eleven components, plus the
parts that belong to no component at all: the gap `JoinHorizontal` leaves between the menu
and the table, the rows below a short overlay, the unfilled tail of every line shorter than
the pane. Nobody owns those, so nothing could paint them.

## What it does instead

`tea.View.BackgroundColor`. Bubble Tea v2 makes the terminal's default background a
property of the View — the same place `AltScreen` and `MouseMode` already live — so the
root model sets it from `m.styles.Theme.Background` on every frame and every cell that
carries no explicit background takes it. `styles.New` deliberately derives **no** Style
from the role, which is the constraint D249 pt 1 records: a `Styles.Background` field
would invite exactly the half-painted frame above.

Reading the renderer before committing to it mattered more than reading the docs, because
the objection to a terminal-level setting is always "who resets it". `cursedRenderer`
does, from `close()` — and `close()` runs on quit **and** from `releaseTerminal`, which is
the path `tea.ExecProcess` takes. So `e` (`$EDITOR`) and `x` (exec) hand the user their
own terminal back rather than kubecom's, without kubecom knowing anything about it. The
same reading explains why a live theme switch needs nothing added to `applyStyles`: the
renderer re-emits when the color changes, and `View` reads the color fresh each frame.

Three returns had to be right rather than one, which is why `View`'s two exits now go
through a small `screen` method: the pre-size frame (`width == 0`) is what the terminal
shows for the whole first paint, and it was already the return where `MouseMode` had to be
remembered separately. Folding them removes the shape of that mistake rather than adding a
third instance of it. The orphaned `View` doc comment that had drifted above `browseBody`
moved back onto `View` in the same edit.

## The values, and the one arithmetic surprise

Each `Background` is the scheme's own base: Catppuccin's `base` per flavor (`#303446`,
`#24273a`, `#1e1e2e`), `#272822`, solarized `base03`, dracula's `Background`, gruvbox
`dark0`, `nord0`, rose-pine `base`, tokyo-night `bg`. All eleven were already in front of
me from THEME-02's data-file transcriptions, so no new fetch was needed — but the flavor
struct only carried `mantle`, so `base` is a new field on it.

The surprise is that `Background` is *darker* than `StatusBarBg` in eight of the eleven and
*lighter* in the three Catppuccins, which is D248 pt 3 restated from the other side: that
decision said the bar is "not the base" and deliberately left the direction free. Now that
kubecom owns the base, "not the base" is checkable, so `TestBuiltinChromeIsVisibleAgainst
TheCanvas` asserts it as inequality rather than as a luminance gap — a gap test would have
to pick a direction and would fail Catppuccin or fail everything else.

## What the tests now claim that they could not before

`TestBuiltinThemesAreDarkAndLegible` gains a pair it was structurally unable to assert:
**body text on the canvas**. Until this leg the background under ordinary text was the
terminal's and therefore unknowable from a unit test, so the contrast floor covered only
the selected row and the status bar — the two places kubecom happened to paint. Now the
palette owns the whole screen and the most common pixel in the app is finally measurable.
All eleven clear 4.5:1; solarized-dark is again the floor by design.

`themeColors` is the mechanism that made the role impossible to half-add: it is a map
literal over every field, so `TestBuiltinThemesAreComplete` fails on a nil `Background`
in any built-in, and `TestDefaultThemeIsCatppuccinFrappe` compares the alias across the
new role for free.

On the shell side, `TestViewHandsTheCanvasToTheTerminal` walks the registry and asserts
both frames — the sized one and the pre-size one — because the pre-size return is the one
a new property is easiest to forget and is what the terminal shows first.
`TestApplyStylesRepaintsTheCanvas` is there for a specific future mistake: caching the
color into a Model field would pass every other test and silently stop following a live
switch. And `TestZeroThemeLeavesTheTerminalAlone` pins the degradation — nil means "reset
to your own", not black — which is the difference between a zero Theme being inert and a
zero Theme repainting someone's terminal.

## Four mutations

1. Set `BackgroundColor` only on the sized return → `TestViewHandsTheCanvasToTheTerminal`
   fails on the pre-size half for all eleven themes.
2. Cache the color in a Model field at construction →
   `TestApplyStylesRepaintsTheCanvas` fails; everything else passes.
3. Drop `Background` from one built-in → `TestBuiltinThemesAreComplete` names the theme
   and the role.
4. Give `rose-pine` `StatusBarBg: base` (the tidy-looking mistake D248 pt 3 forbids) →
   `TestBuiltinChromeIsVisibleAgainstTheCanvas` fails; before this leg nothing did.

## What a test cannot claim, and what was checked instead

Neither the unit tests nor a pty can say the screen *looks* right, so the pty check was
scoped to what it can prove — that the bytes leave the process, carry the palette's own
value, follow a runtime switch, and are withdrawn on the way out. All four hold. The
remainder is `vault/human-tasks/2026-08-08-app-background-look.md`, and one of its items
is not cosmetic: whether a multiplexer passes the escape through decides what THEME-04
has to do about a light palette, because where it is filtered kubecom renders exactly as
it did before this leg — fine for ten dark palettes, unreadable for a light one.
