## The measurement, because "15 rows" is not a constant and that is the point

The probe that opened this leg rendered the overlay at seven sizes and printed
`lipgloss.Height`:

```
200x60 -> 15 rows    80x24 -> 15 rows    80x8 -> 15 rows
120x40 -> 15 rows    80x12 -> 15 rows    60x6 -> 15 rows
```

Fifteen everywhere — not because fifteen is a layout choice but because `bubbles/help` with
`ShowAll` renders one column per namespace and returns the tallest. It elides *horizontally*
(the `…` at the end of a row is its work, and it is why the narrow sizes still fit the
screen), and it has no height input at all. So the number is a property of the action
registry: it is twelve content rows today, and every namespace that grows past twelve pushes
it. That is the part that would not have stayed noticed — a leg that adds four actions to the
busiest namespace silently costs the overlay four more rows, and there is no test anywhere
that would have gone red.

A body height of 12 is a 15-row terminal with a status bar and a hint line, which is an
ordinary split pane. The reader there saw the bindings from `k/up` down to about `ctrl+d`,
no bottom border, and nothing indicating there was more — the overlay looked like the whole
keymap.

## Why this marker is not `elide.Marker`, and why that is a decision rather than a preference

BOX-01 settled the wording as `… (truncated)`, matching `browsefail.go`. Copying it here was
the obvious move and it is subtly wrong for the same reason BOX-02's window was right: what
matters is what the reader can do next. The modal's reader has no gesture that reveals the
elided message — naming the loss is the entire remedy available. The forwards panel's reader
can walk to the hidden rows — so a counter, not a marker. This overlay's reader can do
neither *in the TUI*, but the complete answer is committed in the repo at
`docs/keybindings.md`, generated from this very registry by `keymap.Markdown` and drift-
guarded by `TestKeybindingsDoc`. A marker that stops at "truncated" would be accurate and
useless.

So D222 pt 1 re-founds D220 pt 3 on what it was actually protecting: the invariant is that a
cut is announced. The sentence is the surface's to choose, and `elide.Marker` remains the
default for content that exists nowhere else. Two surfaces sharing a phrase is a convention;
three surfaces sharing a phrase when one of them has somewhere better to point is a habit.

## Extracting the clamp was the fix for a smell this leg would otherwise have created

`clampLines` and `truncatedMarker` were unexported in `components/modal`. Nothing about them
is modal-specific — the function does not render, does not know about styles, and takes the
marker as an argument. Writing the third copy of a ten-line algorithm whose whole purpose is
enforcing a cross-cutting invariant is how the invariant stops being enforced: the next
overlay copies whichever version it happened to read.

`internal/tui/elide` has no dependencies (`strings` only), so `components/modal`, `help` and
the root `tui` package all import it without any cycle risk, and the package doc is where the
*reason* now lives — overlayCenter clips silently, no component test can see it, so each box
bounds itself. The table-driven test moved with the function. `modal_test.go` changed in three
places and its behavioural tests are untouched, which is the check that this was a move and
not a rewrite.

`browsefail.go`'s literal came along for the same reason, since it is the site the convention
was named after: its indented `"  … (truncated)"` is now `"  "+elide.Marker`. That one is
cosmetic today and load-bearing the first time anyone reconsiders the wording — the phrase now
has exactly one definition, and D222 pt 1 can say "the default, except where the content is
reachable" and have that be checkable rather than aspirational.

## `ih <= 0` renders nothing, which is the third thing D220 left unsaid

At a body height of 3 the box has room for its two border rows and its title and not one
binding. Rendering that is worse than rendering nothing: it covers the browse view with a
frame that answers no question, and on a canvas of 3 it is not even a complete frame. The
forwards panel already made this call at `bodyHeight <= 2` (BOX-02) without generalising it;
D222 pt 3 does. The reason it is safe is outside the box — the hint line sits below the body
and still names `?`, so a reader who pressed it on a tiny terminal and saw nothing change
still has the way back on screen. The test sweeps heights 1, 2 and 3 rather than asserting
one, since the boundary is exactly where an off-by-one would hide.
