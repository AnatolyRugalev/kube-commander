# 2026-08-16 — STORY-06c: `enter` opens the actions menu on a resource row; `a` frees up

- Agent: opencode (do-rewrite-leg, interactive session)
- Milestone: M5 (UX-validation line, D268)
- Did: Landed the enter half of the keymap redesign — pressing `enter` on the
  selected resource row now opens the actions menu (`:action ` palette stage),
  the gesture the S01/S02 walks reached for (a red thing wants describe, logs,
  edit, delete, children, pin, all in one step). `enter` stays the universal
  accept key on modals, prompts, pickers and confirms; only the resource-table
  context changes. Implemented as a **third key context** (`ctxTable`), the same
  split D132 gave the confirm modal: `actions.menu` binds `enter` in the table
  context, the shell consults `TableAction` first while the resource table owns
  the keys (gated on `hintContext() == HelpTable`, the same ladder the hint uses,
  so an open modal/logs/viewer/forwards/help/sort-mode surface keeps its own
  `enter`, and a pending `g` of `gg` still owns the press), and `enter` keeps its
  browse meaning (`nav.drillIn`) on the menu pane, in pickers and on modals. The
  table's old `enter`→`RowSelectedMsg` dead end — the S01 "lost gesture", never
  handled by the shell — is gone: the actions menu opens instead, and drill-in
  (Show pods) is an entry in it, so drilling into an owner's pods is one menu pick
  away. `a` frees up, pinned unbound in the keymap default-resolution test.
  `docs/keybindings.md` regenerated; the `openActionStage` test helper now presses
  `enter`, and the logspalette inertness test presses `enter` too.
- Decisions: **D271** — `actions.menu` binds `enter` in a table key context
  resolved while the table owns the keys; `a` frees up; the table's `enter` no
  longer emits the dead RowSelectedMsg. Supersedes the "`a` opens the actions
  menu" gesture, not the `:action ` stage it opens (that stage is unchanged).
