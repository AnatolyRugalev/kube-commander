## The board note said "refresh"; the tool says "new package"

M5-06 did the archaeology and wrote the answer into this slice's note ahead of time: the 2020
package is `kube-commander`, not `kubecom`, so "expect the same stale-package trap the tap
had". That was right about the trap and wrong about the remedy, and the difference is the
whole leg.

For Homebrew, the address was keepable — the tap is a repository name and goreleaser writes
whatever you tell it to. For the AUR it is not:

```go
// internal/pipe/aur/aur.go, Default()
if !strings.HasSuffix(pkg.Name, "-bin") {
    pkg.Name += "-bin"
}
```

Unconditional, no opt-out, and it feeds `pkgname`/`pkgbase` in both generated files. The AUR
in turn requires `pkgbase` to equal the repository the push targets. So `name: kube-commander`
produces `kube-commander-bin`, `name: kubecom` produces `kubecom-bin`, and there is no value
of `name` that produces `kube-commander`. **`.goreleaser.yml` cannot write to the 2020
package.** A future leg that tries to "restore the original name" is chasing something the
tool will not do, which is why that is D183 pt 1 rather than a comment.

This is also the better outcome on the merits — `-bin` is the Arch convention for a package
shipping a prebuilt binary, and the 2020 package violated it — but the framing matters for
what leaves the repo. The consequence is not cosmetic: **there is no upgrade path.** The AUR
has no `replaces:`, goreleaser exposes no such field, and `pacman` will never offer
`kubecom-bin` to somebody holding `kube-commander`. Every existing user has to act, or stay on
the 2020 binary forever.

So the generalisation went into the decision, because this is now twice in two legs:
*for each distributor, the 2020 artifact keeps being served until a human removes it, and
nothing in this repo can see that it exists.* Docker is next and will have its own version of
this.

## The one place the collision *can* be expressed in config

M5-06's most valuable finding was negative: `conflicts.formula` on a Homebrew cask is accepted
by goreleaser, never rendered, and Homebrew removed the DSL for it — so there was no
config-side seatbelt at all, only a human step.

The AUR is the opposite, and it is worth writing down as a contrast rather than a footnote.
Both packages install `/usr/bin/kubecom`; `pacman` honours `conflicts`, so:

```
conflicts=('kubecom' 'kube-commander')
```

means a user who tries to have both gets a clear refusal instead of one package's binary
silently overwriting the other's. It is a real seatbelt. It is still not a migration — a
conflict blocks co-installation, it does not redirect anyone — so the human task keeps
retiring the old package as a required step with its own heading.

`provides`/`conflicts` also had to be set explicitly rather than left to default. goreleaser
defaults both to the **project** name, which here is `kube-commander` — so the generated
PKGBUILD would have advertised `provides=('kube-commander')`, claiming to install a binary by
that name that the package does not install. Accidentally right for `conflicts`, wrong for
`provides`, and worth neither.

## Three quiet no-ops, and which one the guard actually catches

The AUR pipe can decline to publish in three different ways, and only one of them is loud:

| condition | what happens |
| --- | --- |
| `skip_upload` templates to `"true"` | `pipe.Skip("aur.skip_upload is set")` — first thing in `doPublish` |
| `git_url` empty | `pipe.Skip("url is empty")` — inside the git client, after author/message templating |
| `private_key` empty | `pipe.Skip("private_key is empty")` — in `keyPath`, after that |

All three read as success in the run log. The dangerous one is the middle: **`git_url` has no
default.** A config that sets `name`, `private_key` and `skip_upload` correctly and simply
omits `git_url` produces a release that publishes nothing to the AUR, forever, with nothing
anywhere to indicate it. That is `TestAURGitURLMatchesThePackageName`'s first half; its second
half is the `-bin` mismatch, since goreleaser appends the suffix to `name` and never to the
URL, so the natural spelling (copy the configured `name`) is the wrong one and would be
rejected by the AUR on push.

The key itself has one failure that is *not* a skip and belongs in the workflow comment: a
passphrase-protected key makes goreleaser **error** (`git: key is password-protected`), which
would turn a release nobody can retry into a failed one. Hence the `-N ""` in the human task,
spelled out as a requirement rather than a convenience.

## What was run rather than recalled

`goreleaser jsonschema -o schema.json` was the first move and should be the first move next
time — it lists every field of every publisher, which is faster and more honest than
remembering field names. Beyond that, four things were established by running the tool:

- **The `-bin` rename**, from the rendered `dist/aur/kubecom-bin.pkgbuild` (and by reading
  `Default()` to confirm it is unconditional).
- **`skip_upload` flips both ways.** Same probe technique as M5-06: put the template in
  `description`, run the snapshot twice. No key → `pkgdesc='PROBE skip_upload=[true]'`; with
  `AUR_SSH_PRIVATE_KEY=dummy` → `[false]`.
- **`pkgver`'s transform.** The snapshot renders `v0.0.0_next`, which looks like the leading
  `v` survives. It does not — that is the tagless-sandbox synthesized tag showing through
  `snapshot.version_template`. Tagging `v9.9.9-probe` and templating `{{ .Version }}` gives
  `pkgver=9.9.9_probe`: the `v` is dropped and `-` becomes `_` (it must — `pkgver` forbids
  `-`). Worth pinning down because "the version looks wrong on the AUR" is exactly the kind of
  thing a future leg would otherwise re-derive under time pressure.
- **`ids:` is load-bearing**, and this one I would have written as a guess. The config declares
  two archives over the same GOOS/GOARCH pairs (a `tar.gz` and a bare `binary`), and the AUR
  pipe filters on `UploadableArchive` **or** `UploadableBinary`. Removing `ids` and counting:

  ```
  $ grep -c '^source_' dist/aur/kubecom-bin.pkgbuild
  4
  ```

  Two `source_x86_64=` lines and two `source_aarch64=`, each pair overwriting itself in bash.
  It would probably still have installed — the `.tar.gz` line comes second — which is worse
  than breaking, because the `.SRCINFO` would list sources the PKGBUILD never fetches.

## The guards, and what each would have caught

Nine mutations, each applied and the failure message read:

| mutation | fails |
| --- | --- |
| drop `git_url` | "goreleaser has no default for it and silently skips the publish when it is empty" |
| `git_url` without `-bin` | "the AUR requires pkgbase to equal the repository name, so this push would be rejected" |
| `skip_upload: 'false'` | "not conditioned on AUR_SSH_PRIVATE_KEY, the secret its private_key reads" |
| `private_key: '{{ .Env.X }}'` | "want an `{{ index .Env \"NAME\" }}` template" |
| drop `AUR_SSH_PRIVATE_KEY` from `release.yml` | the release step does not pass it |
| restore `depends: [kubectl]` | "kubecom talks to the apiserver through client-go and requires no kubectl at runtime (D2)" |
| drop the `kube-commander` conflict | "both packages own /usr/bin/kubecom" |
| drop `ids` | "the duplicate per-arch sources overwrite each other" |
| README says `kube-commander-bin` | "README names the AUR package …, but .goreleaser.yml publishes …" |

The `depends` one deserves a note. It is the only guard here that defends against *copying the
old package forward* rather than against a fresh mistake — the 2020 PKGBUILD declared
`depends=('kubectl')`, and the obvious way to write this config is to port that file. D2 has
been true since M0, but nothing until now could fail when a packaging file contradicted it. An
empty `depends` also looks like an oversight in review, which is why the config says why it is
empty in a comment instead of just omitting the key.

## What the README says, and deliberately does not say

Same shape as M5-06's Homebrew paragraph, and for a sharper reason. A returning Arch user's
instinct is `yay -S kube-commander`, which **works today** and installs the 2020 build. The
README therefore does not get an install section; it gets a warning that names the new package
(`kubecom-bin`), says outright that it is not an upgrade of the old one, explains that the
rename was forced, and mentions the deliberate conflict so that `pacman` refusing to install
looks like the designed behaviour it is.

Naming the package there is also what makes `TestReadmeAURPackageMatchesTheConfig` live from
this leg rather than dormant. The real install block is written out verbatim in the human task,
to be pasted by whoever makes it true — the same pattern M5-06 and M5-09 used.

## Sandbox artifacts, again

`dist/aur/kubecom-bin.pkgbuild` contains `https://github.com/git/AnatolyRugalev/…` download
URLs and a `v0.0.0-next` version, for the same two reasons M5-06 documented: goreleaser derives
the URL from the git remote (here a local proxy whose path contains `/git/`) and synthesizes a
tag when the checkout has none. Both resolve on a real tagged CI run. The human task repeats
the first one as something to *check* on the first published PKGBUILD, since a `/git/` in the
real output would mean something is wrong with the CI checkout rather than with the sandbox.
