## The find worth having: previous-container logs

`kube.LogOptions.Previous` exists, is documented as `kubectl logs -p`, and is threaded all
the way into the API request in `internal/kube/logs.go`. Nothing reaches it. There is no
`logs.previous` action in the registry, no actions-menu entry, no toggle in the logs view —
the field is dead weight, and the one moment you most want it (a container that just
CrashLoopBackOff'd, whose current instance has no logs yet) is the moment kubecom cannot
help. The 2020 build could: `legacy-architecture.md` lists `l` current / **`L` previous**
under "Behavior worth preserving", and the rewrite kept the first and dropped the second.

This is the shape of gap a DoD audit is *for*, and note that it is invisible from the DoD
itself: the logs box reads "In-TUI logs … viewers", which is emphatically met — a dedicated
full-screen view with live grep, wrap, sideways scroll and timestamps. A box can be honestly
ticked and still sit above a missing feature, because the box states a capability and parity
lives in the details underneath it. Filed as M5-01a with the two decisions it needs
(separate action vs in-view toggle; what to do when there is no previous instance) and one
trap noted: `L` is currently `res.logs`, so reusing the legacy key would be a shipped-default
change (the FB-delete-key-d/D133 situation), not a free win.

## Why I did not just reword the YAML bullet

The DoD asks for an in-TUI YAML viewer. M3-15c/D135 removed exactly that on purpose and
routed YAML through `$EDITOR`, on the argument that one surface for read+write beats two.
Editing the bullet to match would have made the list tidier and cost the project the only
remaining record that a v1 promise changed shape — and it is the maintainer's list, not the
agent's. Ticking it would have been worse: it would assert an in-TUI viewer that does not
exist.

So the box stays unticked with the divergence stated, and M5-01b carries the choice with both
options costed (re-adding a read-only view is cheap — the `viewer` component and the
`YAMLGetter` seam both survived M3-15c, only `res.yaml`/`ActionYAML` were removed). D174 pt 3
generalises it, because this will recur: the DoD was written before M1 and four milestones of
decisions have accumulated against it.

## Two calls that could have gone the other way

**The CRD box.** Generic listing is one of the best-covered paths in the tree — server-side
Table printing for any GVR, CRD printer columns, the D103 param-codec fix, the D104
watch-less degrade — and on tests alone it ticks comfortably. It does not tick, because
CRD-01 says a real `ExternalSecret` errors instead of listing. A DoD box is a claim about the
shipped product; a credible field report contradicting it wins over a green suite. If the
human task comes back showing the fault is cluster-side (a conversion webhook is the standing
suspicion), the box ticks *then*, with that finding as its evidence — which is a materially
different tick from one made today by looking away.

**The browse-parity box.** It ticks despite two visible differences from 2020: menu
customization is a per-context file rather than in-TUI add/hide/reorder (D83/D89), and the
menu pane is optional with a `:` palette beside it (D96/D100). Both are recorded decisions
that supersede the legacy behaviour deliberately, which is the difference between a deviation
and a gap — and the annotation names them so the tick cannot be mistaken for "identical to
the original".
