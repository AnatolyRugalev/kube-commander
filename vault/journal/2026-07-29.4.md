- Did: Added `kube.Contexts(ClientConfig) ([]ContextInfo, error)` in
  `internal/kube/context.go` beside `ContextName`: every context declared in the
  kubeconfig with its cluster name, its declared default namespace, and which one is

  Nothing consumes it yet; M4-04's picker will.

- **`Current` reuses `ContextName`'s selection rule rather than reporting
  `raw.CurrentContext`.** The list is for a picker that must mark "the cluster you are
  actually on", and `--context` overrides the file's current-context, so the marked
  entry is the one `Connect` would select for the *same* `ClientConfig`: the explicit
  `Context` if set, else `raw.CurrentContext`. `TestContextsNamesRoundTrip` pins the
  agreement (the `Current` entry equals `ContextName(cc)` for the same cc) so the two
  cannot drift; if a later leg adds another selection input, both must move together.
  A `Context` naming no declared context marks *nothing* current and is not an error —
  the picker then shows an unmarked list rather than lying about which is live.
- **Sorted by name, and that is load-bearing, not cosmetic.** `raw.Contexts` is a Go
  map, so an unsorted list would reorder itself between runs and the picker's rows —
  and any cursor position remembered against them — would jump for no reason.
  `TestContextsListsSortedWithFields` uses a kubeconfig that declares `ctx-c, ctx-a,
  ctx-b` in that order precisely so a pass-through of map/file order fails it.
- **Error shape matches `RESTConfig`, deliberately.** A missing or malformed kubeconfig
  returns an error wrapped with `errBadContext`, so `Classify` reports `KindBadContext`
  whichever entry point hit the broken file first — the caller degrades on one kind
  instead of special-casing the context list. Both are tested through `Classify`, not
  just for non-nil. Note this is where `Contexts` and `ContextName` deliberately
  *differ*: `ContextName` swallows the error and returns `""` because its result is
  cosmetic (status bar), whereas an empty context list would be indistinguishable from
  a valid kubeconfig that declares none — a real distinction the picker needs, so this
  one returns the error. A readable kubeconfig with no contexts returns an empty slice
  and no error, and that case is tested separately.
- Scope note: `ContextInfo` carries no `User` field. The board named four fields and
  nothing needs the user; adding it later is additive and harmless, guessing at it now
  is a field the picker would have to be taught to ignore.
