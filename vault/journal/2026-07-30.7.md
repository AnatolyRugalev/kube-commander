## Why a toggle and not a second row action

The board left this open deliberately, and the two options are not close once you look at
what each has to touch.

A separate open action means `Previous` has to travel the whole resolution path: the row
gesture builds a `rowActionMsg`, a pod-owning kind goes out to `PodForOwner` (M3-07b), the
resolved pod goes out to `PodContainers` (M3-07a), and a multi-container pod parks in the
picker with its selection stashed on the model until the pick lands. Every one of those
hops would need to carry one extra bit, and `ctrPurpose` — which already distinguishes
logs from exec — would grow a third value or a companion flag. That is four files of
plumbing to reach a stream the reader is usually already looking at.

A toggle spends none of it. By the time you want the previous instance you have *already*
resolved the pod and picked the container, so the request that got you here is the request
you want with one bit changed. Stash it (`Model.logReq`), flip the bit, re-open. The
plumbing is one struct and one function, and `L` stays the only way into logs — which also
means the actions menu does not grow an entry that is inert on the 90% of rows that have
never restarted.

The board's own hint pointed here ("a toggle re-requests the stream, which is closer to
the other logs toggles") but it is worth being precise about how it is *not* like them:
`logs.wrap`, `logs.timestamps` and `logs.regex` are display toggles that redraw a buffer
already in hand, and D148's whole argument for timestamps was that flipping it costs
nothing. This one costs a round trip, because the two instances are two different logs. So
it lives in the shell (`handleLogsAction`), not in the component — the component cannot
open a stream — and it is the one logs key that is a *request* flag.

## The key: why `ctrl+p` and not `p`

kubectl's flag is `-p`, so the obvious key is `p`. It is taken — the port picker's
local-port prompt (FB-pf-local-port/D139) — and so is `P` (`res.children`/D165). There is
one browse-context keymap, so "taken in the port picker" means taken here.

`ctrl+p` is the nearest free thing to the mnemonic, and it turned out to have an
independent argument in its favour. The logs grep field swallows every text-carrying key
while it is open (D140 pt 1), which is why `logs.regex` is `ctrl+r`. This gesture belongs
in the same family for the same reason: grepping a crash-looping pod for a stack trace,
finding the running instance has not printed it yet, and wanting the same look at the
instance that died is a *sequence*, not two separate sessions — so the key has to survive
the open field, and the query has to survive the flip.

That second half is what made me change the component's API rather than reuse `Reset`.

## `Restream` vs `Reset`, and why the difference is a real one

`logsview.Reset` is the new-object path: it empties the buffer *and* clears the reader's
lens (grep, mode, wrap, timestamps), because a different object's logs should not open
narrowed by a query typed against the last one. Correct there, wrong here — flipping
instances and losing your query means retyping it to ask the very question the flip was
for.

So the component gained `Restream`: empty the buffer, re-arm following (the new stream
tails from its own start), touch nothing else. `Reset` is now `Restream` plus clearing the
lens, which is the part worth keeping: written that way, the two cannot drift apart about
what emptying a buffer means, and a future field added to the "lens" has exactly one place
where it must be decided whether it is per-object or per-instance.

The buffer really must be replaced, not appended to — two instances are two logs and
interleaving them would be worse than useless. The test asserts that as a number rather
than a claim: the fake replays two lines, so a replaced buffer reports `1/2` under the
query and an extended one would report `1/4`.

## The two decisions the sandbox could not settle, and what I did instead

**Does `Follow` belong on a previous-instance request?** Semantically no — a terminated
instance's log cannot grow. I kept it anyway, and the reasoning is a chain, which is
exactly why it is in a human task rather than asserted as fact: the kubelet resolves
`previous=true` to the *previous* container's id and follows that container's state, which
is not running, so `ReadLogs` should stop and the stream should close; a clean EOF is
already how `followLogStream` stops following (the same path a followed pod takes when its
container dies); so the flip changes one bit and needs no second code path. If that chain
is wrong the symptom is specific and visible — an empty view, a hang, or a 2-second
reconnect loop — so the human task asks for exactly those three symptoms by name, and the
fix if it is wrong is `Follow: false` for the previous case.

The alternative was to set `Follow: false` now, which is safe but not free: the view would
open claiming `[following]` while the stream is one-shot, so it needs a way to tell the
component it is not following, and flipping back would need to restore it. More state, to
guard against something I have reason to believe does not happen. Recorded as D177 pt 2 so
the next leg knows it is a bet and not an oversight.

**What happens with no previous instance?** Nothing pre-checks. The alternative is reading
the pod's `containerStatuses[].lastState.terminated` before asking — but the container
lister returns names and kinds, not statuses (LOGS-06), so that is another fetch, and a
guess that can be wrong in both directions: a container that terminated in a way the
status does not describe gets its readable log hidden, and a stale status promises one that
is not there. The apiserver is the only authority, so the request goes out and its
rejection lands on the emptied view, where the existing rule already applies — an error
with nothing shown yet is an open failure, so it toasts the server's own words and closes
(D74). The one thing the sandbox cannot know is whether that message reads well at a real
terminal width, which is question 4 of the human task.

## The header marker is the part I would defend hardest

LOGS-04b deliberately gave the timestamps toggle *no* header marker, and the argument was
good: a timestamp is on every row the moment it is on, so a marker restates the body and
costs a segment of a header that already elides at narrow widths.

`[previous]` is the counter-example, and the distinction is worth stating because the two
decisions look contradictory side by side. Two runs of one container produce output that
*looks alike* — same format, same messages, often the same first lines — so which instance
you are reading cannot be seen in the lines. That makes it precisely the class D146 says
to name: state the reader can lose sight of. And it is why the marker sits *before*
`[following]` rather than joining `[wrap]`/`[re]` at the end: the header is clipped from
the right, and a clipped `[following]` or a clipped match count misleads nobody, while a
clipped `[previous]` turns a dead instance's log into what reads as the running one's.
