## The bug is invisible to every test that reads `View()`

`modal.View` returns a complete box — border, title, message, input, border. Every assertion
in `modal_test.go` was a `strings.Contains` over that string, and all of them passed while the
thing on screen was missing its bottom third. The clip happens one layer up, in `overlayCenter`,
which builds a `lipgloss.NewCanvas(width, height)` and renders it: a layer placed at y=0 that
runs past `height-1` is simply not in the output. Nothing errors, nothing warns, and the
component's own tests cannot reach the canvas.

That is why D220 pt 1 is phrased as a rule about the *component* rather than about the
composition. Making `overlayCenter` clip more gracefully — shrink, scroll, scale — is not
available: it is the compositor, it has no idea which rows of a box are load-bearing. The only
place that knows the message is expendable and the input is not is the modal, and it already
computes the budget. It was throwing it away with `iw, _ :=`.

The prompt case is the one that turns an ugly frame into a broken surface. `parts` is built
title → message → input, so the input is the *last* row before the bottom border and therefore
the first thing a bottom-first clip takes. A reader on a 12-row terminal answering "Scale
deployment" saw the question, no field, no border, and typing changed nothing they could see.
The new test pins that specific reading: it clips the box to the screen height by hand
(`onCanvas`) before asserting `> 7` is in it, so removing the clamp fails it.

## Why truncate rather than scroll, and why the marker is a sentence

Scrolling needs a key context, a scroll position in the model, and an entry in `hintContext`
(D217/D218) — three things that make it a different leg for a surface whose messages are one
to four lines. Truncation is what the box can do with no new state, and D220 pt 3 makes it
say so: `… (truncated)`, the exact wording `browsefail.go` already uses when it drops the tail
of a credential plugin's stderr. A reader who meets both meets one convention.

A bare `…` was the alternative and reads as decoration — an ellipsis at the end of a line is
just as likely to be prose. Inside a *question* that distinction matters more than elsewhere:
the reader is about to agree to something, and text quietly missing from the thing being
agreed to is the failure the whole AUTH line exists to avoid.

`clampLines` spends the last available row on the marker rather than adding one, which is the
only version that satisfies pt 1. It also returns the block untouched when it fits, so the
marker is evidence rather than furniture — a modal that dropped nothing never shows it, which
is its own test.

## `modalMinHeight` 3 → 4, because a minimum below the chrome makes the rule unsatisfiable

With the clamp in, the invariant is `2 (border) + 1 (title) + min(lines, ih) + 1 (prompt) ≤ mh`,
and `innerSize` derives `ih` by subtracting exactly those reservations — so it holds by
construction *as long as `mh` is at least the reservations*. In prompt mode that is 4, and the
old minimum was 3. On a screen short enough to hit the floor, `ih` clamped up from −1 to 0 and
the box rendered four rows where the geometry said three.

Raising the floor is the honest fix rather than special-casing the render, and it also improves
the confirm case: the smallest box now has one line for the message instead of none. The
mutation test earns its keep here — reverting the constant fails at 60×5 in prompt mode by
exactly one row, which is not a size anyone would have thought to check by hand.

## Two comments were describing the opposite of what lipgloss does

`reauthQuestion` and `remediationLead` both stated that the confirm box "clips each line to
sixty cells, so a long invocation is truncated". It does not: lipgloss's `Width` word-wraps
*and* hard-wraps a token too long to break, so a long command has always wrapped inside the
box. The real limit was the one nobody wrote down — height — and it did not truncate the
command, it deleted the border and the field.

Both comments now say what is true after this leg: the box wraps horizontally and elides
vertically, so a long cause *followed by* a long command can push the command into the marker.
That leaves the two conclusions those comments were drawing intact but re-founded — the pane
behind the box still quotes the command in full, and that is still the reason `remediationLead`
prints it rather than deferring to the prompt.

I left `reauthQuestion`'s ordering alone (cause, blank, question, command) even though bottom-up
elision means the command is cut before the cause. Reordering to protect the command would put
the question above its reason, which reads worse in the overwhelmingly common case where
nothing is cut, to protect a case the pane behind already covers. The comment records that
trade so the next agent does not "fix" it silently.

## The other two boxes, measured rather than assumed

Writing the board note tempted me into the claim that no other overlay is unbounded. Two
probes said otherwise, so the note names them instead: `forwardsPanelView` renders one row per
active forward with no height clamp at all, and `help.View` constrains width via `helpMargin`
and ignores the `m.height` it is already given — a flat 15 rows at every screen size I tried,
200×60 down to 80×12, because `bubbles/help` with `ShowAll` lays out at the height its tallest
namespace column needs. That number is not a constant; it grows with the action registry.

Neither is folded in here. The panel is the more interesting one and is not a marker problem:
it has a *cursor*, so a clamp that drops the tail can hide the selection, and the right answer
is the picker's — a window that follows `m.forwardsSel`. That is a view change with its own
tests, filed as BOX-02, with BOX-03 for the overlay. Both are unblocked, which matters more
than usual right now: the board had nothing pickable when this leg started.
