# 2026-07-25 — SEARCH-03a: kube.Search streams typed SearchEvents

- Agent: claude-opus-5
- Milestone: M3
- Did: Split **SEARCH-03** the D52 way (primitive first, surface second) because the
  "searching N/M kinds…" line and the "first 200 matches" state are simply
  unrenderable today: `kube.Search` streamed bare `SearchHit`s and the channel *close*
  had to mean "every kind finished", "the cap stopped us", and "the caller cancelled"
  all at once. This slice widens the channel item once, to a typed `SearchEvent`
  (`SearchMatch` / `SearchKindDone` / terminal `SearchDone{Capped}`), and adapts the
  wiring mechanically — the pump now carries `SearchEventMsg` and appends only matches,
  so the **running binary behaves exactly as before** (D68: nothing regressed, nothing
  new on screen either). SEARCH-03b counts the new events into the view. → D142.
- Four choices worth naming. (1) **One channel, not two.** A `(hits, progress)` pair
  would have meant a second pump and a second staleness clock in `search.go`; a
  discriminated event keeps D141's single `searchGen`-tagged pump and one teardown path.
  (2) **Exactly one `SearchKindDone` per requested kind, emitted from a `defer`** — a
  denied kind, or one the cap cut short, still reports done, so a progress counter can
  never stick at 10/11 because a group was forbidden (principle 3). `Failed` is set only
  for a *genuine* List error (`ctx.Err() == nil` at the failure), never for the cap's own
  cancellation, so a future "N failed" surface can't over-count. (3) **`Capped` means
  matches were truncated**, not "you got `limit` matches": a search whose hits exactly
  fill the cap is exhaustive, and the flag is set at the point a goroutine finds the cap
  already full. (4) **The terminal event is not the teardown** — the close still is. A
  consumer that stopped pumping on `SearchDone` would leave the channel undrained and
  duplicate the cancellation path for no gain.
- The one real trap, caught by `make check`: the progress and terminal sends are guarded
  by the **caller's** ctx, not the internal one (the cap cancels the *listing*, but the
  events it produces still have to arrive) — and with a buffered channel plus an already
  done ctx, a bare `select` picks an arm at random, so a cancelled search emitted its
  terminal event about half the time. `sendEvent` now pre-checks `ctx.Err()`, which makes
  "cancelled ⇒ nothing further is emitted" an actual invariant instead of a coin flip.
- Decisions: D142 — three event types on one channel; one kind-done per requested kind
  with `Failed` for genuine List errors only; `Capped` = truncated, not "limit reached";
  the channel close remains the only teardown point; cancelled ⇒ silent.
