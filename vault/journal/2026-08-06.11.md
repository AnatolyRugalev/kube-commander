## The default theme has been Catppuccin Frappé since M0, unattributed

`DefaultTheme` shipped thirteen hex values with the doc comment "a dark-friendly palette
with a blue accent (a nod to the original kube-commander)". Every one of those values is a
Catppuccin Frappé role: `#c6d0f5` is `text`, `#8caaee` is `blue`, `#414559` is `surface0`,
`#51576d` is `surface1`, `#292c3c` is `mantle`, `#f2d5cf` is `rosewater`, and the semantic
trio is the flavor's `red`/`yellow`/`green`. That is not a coincidence anyone could reach by
picking pleasing colors; it is a transcription.

So the feedback's "add Catppuccin" was, for one flavor, already done — and its "check
licensing" instruction had already been skipped once, for the theme kubecom renders by
default. Catppuccin is MIT and permits exactly this, so nothing was wrong; it was just
uncredited, which is the failure mode D236 pt 1 now names. The interesting part is how
invisible it was: a palette is thirteen strings, it has no import, no `go.mod` line and
nothing to grep for, so provenance vanishes the moment nobody writes it down. That is the
argument for putting attribution in the constructor's doc comment rather than a NOTICE file
— it sits where the values are, so a port that lacks one is visible in review.

## One palette, two names, and why the alternative was worse

D169 pt 1 makes a theme name API: `config.yaml` persists it, so renaming a shipped theme
breaks every config that selected it. `default` therefore cannot become
`catppuccin-frappe`. The three options were:

1. Ship Latte/Macchiato/Mocha and document that `default` is Frappé. Rejected: a reader
   filtering the theme picker for `catppuccin` sees three of four, and the way to select
   Frappé is to pick a theme called `default`, which no Catppuccin user would guess.
2. Retune `default` to something non-Catppuccin and free the name. Rejected: it changes what
   every existing user sees, on a leg that was supposed to *add* themes.
3. Register both names over one set of values.

(3) costs one duplicate in a registry whose test suite explicitly forbids duplicates — which
is how it announced itself: `TestBuiltinThemesRenderDistinctly` failed on the first run with
`themes "default" and "catppuccin-frappe" render identically`. That test is right about
everything except this pair, so it got an `aliasPair` exception rather than a weakening, and
the exception is *paired* with a new test asserting the two are equal role-for-role. The
duplicate is now pinned from both directions: it cannot silently spread (any other identical
pair still fails) and it cannot silently drift (the alias test fails if someone retunes one).

The values live in `catppuccinFrappeFlavor` and both constructors call `catppuccinTheme`, so
there is one place to be wrong rather than two places to disagree.

## The reason there are 6 and not 10 is a background, not a lack of time

The obvious way to hit "~10" in one leg is to transcribe ten palettes; each is twelve hex
values and the mapping is mechanical. I stopped at the Catppuccin family because the survey
turned up something that changes the shape of the remaining work.

**kubecom paints no app background.** `styles.New` sets `Background` on exactly three
styles — the selected row, the status bar, and a search match — and everything else is
foreground text drawn over whatever the terminal already is. Every built-in to date is dark,
which made this invisible: dark text roles on a dark terminal look intentional.

Add Catppuccin Latte (`text: #4c4f69` on `base: #eff1f5`) and the theme renders near-black
text on the user's black terminal. It is not a bad theme, it is an unusable one, and the
reader's diagnosis would be "kubecom's Latte is broken" rather than "kubecom does not paint
a background". The same applies to `solarized-light`, which the codebase already anticipates
— `ByName`'s test asserts `solarized-light` is *not found*, and D169 pt 1's example for why
`solarized-dark` carries the variant in its name is a light port landing beside it.

So the light half of the theme catalogue is gated on a `Background` role that every built-in
must fill (D169 pt 3) and that the panes must actually render. That is a change to how every
component draws, with real questions attached (what does a painted background do to the help
overlay, or to a terminal already set to the same scheme?), and it has no business riding
along on a leg whose diff is otherwise a table of hex numbers. It is THEME-03, and D236 pt 3
states the constraint so a later leg does not helpfully add Latte to the registry and ship a
theme nobody can read.

## What the licence survey actually found, since "they're all MIT" was nearly true

Six of the seven candidate schemes are MIT and permit reimplementing the values with
attribution. Two are not the boring case, and both would have been missed by assuming:

- **Tokyo Night is Apache-2.0** (`folke/tokyonight.nvim`). Still permissive, still fine, but
  a different licence with its own notice requirement — so it cannot be attributed inside an
  "all MIT" sentence, which is exactly what a survey that stopped at the first two repos
  would have written.
- **Gruvbox upstream has no licence file at all.** `morhetz/gruvbox` ships none; the same
  author's `gruvbox-community/gruvbox` fork carries MIT. A list of hex values is not a
  creative work, so porting is fine either way, but the attribution has to point at the fork
  — and the note in `knowledge/themes.md` exists so a later leg does not "fix" that pointer
  to the upstream repo, where there is nothing to point at.

Nord's licence lives on the `develop` branch (`main` 404s), which is the kind of five-minute
detour worth writing down once.

The other durable finding is about transcription: use each project's own data file
(`catppuccin/palette`'s `palette.json`), never another project's port. Ports disagree with
each other about accents constantly, and a wrong value in a theme is invisible until someone
who knows the scheme looks at it — the worst kind of bug for an autonomous loop, because
nothing fails.
