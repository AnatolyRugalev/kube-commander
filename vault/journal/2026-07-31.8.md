## The assertion, and the one that gives it meaning

The load-bearing subtest is the race D129 promises to lose safely: fetch the buffer with
`GetYAML`, let another actor write through the typed client, then `Update` from the buffer.
It is a Conflict, `Classify` → `KindConflict`, and the other actor's key is still there.

On its own that assertion is weaker than it looks, because a great many bugs also produce
"the update failed". What gives it meaning is the subtest after it, which is the same race
with `metadata.resourceVersion` removed from the buffer and nothing else changed:

```
data = map[editor:mine], want the concurrent write clobbered
```

— that is the *passing* expectation. The request succeeds, 200, and the concurrent write is
gone. An unconditional PUT is not an error condition, it is an ordinary API call, and that
is the whole reason D189 exists: there is no failure anywhere for a "tidy the buffer" leg
to trip over. Strip the field, every test that checks "the edit applied" still passes, and
the guarantee is gone.

The two mutations below are both that leg, which is why they were the ones worth running.

## The finding: a deleted object is a Conflict

The subtest I wrote for the #86 contract — object deleted while the editor is open —
asserted `KindNotFound`, because that is what `Update`'s doc comment said and what the
situation obviously is. It failed:

```
Classify(kube: updating configmaps "vanished": Operation cannot be fulfilled on
configmaps "vanished": StorageError: invalid object, Code: 4, …
Precondition failed: UID in precondition: 53e244ef-…, UID in object meta: ) = conflict,
want not-found
```

The buffer carries `metadata.uid`, and an apiserver reads a UID on an update as a
precondition — the same mechanism c-1 sends explicitly in `DeleteOptions`, arriving here
implicitly through the object body. So the answer is a Conflict about identity rather than
a NotFound about existence, and the control subtest (uid edited out of the buffer, same
deletion) gets the plain NotFound, which is what says the Conflict came from the uid.

This is a better answer than the one I expected, and it is why D189 pt 3 is about copy:
both an edit Conflict causes — stale version, deleted object — mean *your buffer is out of
date, re-open it*, and neither means "someone else changed this object", which is what an
error message would naturally reach for. The doc comment on `Update` now says what the
server does. That is a fix, not a constraint, so it is not a decision.

## Status is a subresource, and the PUT half-lands

`status` on a workload is a subresource, so a buffer with an edited `status.replicas` PUTs
cleanly: 200, the spec in the same request applies, the status does not. The subtest asserts
both halves of that one request, because the interesting property is that they disagree —
a fake, which has no subresources, would store both and let a hermetic test prove a status
edit "worked".

It is the same shape as D188: a successful call that did less than the user asked, with
nothing in the error to say so. Less dangerous here (nobody edits status expecting it to
stick, and no-change detection means a status-only edit at least *tried*), but worth being
written down before a leg adds an "applied" confirmation that overstates what happened.

## Watched fail, twice — as the same plausible leg

Both mutations are the future change D189 forbids: `marshalYAML` stripping one more field
from the buffer, exactly the way it already strips managedFields.

1. **Strip `resourceVersion`** → `update from a stale buffer succeeded; the resourceVersion
   never reached the server`. Nothing else in the suite fails, hermetic or live: the round
   trip still round-trips, the immutable-field edit is still refused, the deleted object is
   still a Conflict. One subtest stands between the tree and a silent clobber.
2. **Strip `uid`** → `Classify(kube: updating configmaps "vanished": configmaps "vanished"
   not found) = not-found, want conflict`. The weaker refusal, and it degrades in the
   direction that reads as normal.

The `editBuffer` helper fetches through `GetYAML` and renders back with `sigs.k8s.io/yaml`
rather than the package's own `marshalYAML`, so the test's buffer is not produced by the
half of the code the mutations edit — which is what makes mutation 1 fail in the test
instead of quietly propagating into the fixture.
