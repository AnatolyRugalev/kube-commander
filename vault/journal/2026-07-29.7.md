# 2026-07-29 — M4-04a: the context switch itself (connect, then tear down)

- Agent: claude-opus-5
- Milestone: M4
- Did: Split M4-04 on pickup into **M4-04a** (the switch) and **M4-04b** (the picker that
  triggers it), then landed 04a: a `ClusterConnector` seam plus `switchContext` —
  connect the named context **off the update loop** behind `ctxGen`, and only with the
  new client in hand `resetCluster` (M4-03) → repoint the `Cluster` bundle (M4-02) →
  rename the context on the model, status bar and welcome page → restart discovery. The
  launcher implements the seam with `kube.Connect` + the existing `clusterFor`. Nothing
  reaches it from the UI yet; M4-04b's `ctx.switch` picker does. → D157.

- **The split is the same bottom-up rhythm the whole switcher line has followed, and it
  was chosen over the other obvious cut.** M4-04's own board note and the M4-03 journal
  both flagged a split, but suggested "the action + picker listing contexts (no switch)"
  as the first half — which would ship a visible gesture that opens a picker and then
  does nothing when you press enter, on a binary the maintainer dogfoods between reviews
  (D68). Cutting the other way keeps the precedent M4-01/02/03 set: the machinery lands
  and is tested while it is reachable from tests only, then one small leg wires the
  gesture and ticks the criterion. Nothing user-visible changes in this leg, which is
  exactly what the previous three did.
- **Connect first, tear down second — the leg's one real constraint (D157).** The
  tempting shape is "reset, then connect": it reads in the order the user experiences it
  and needs no message round-trip. It is also wrong. `resetCluster` is destructive by
  construction (D155 pt 1), so a connect that fails *after* it — a typo'd context, a
  kubeconfig entry whose cluster no longer resolves — leaves the shell on nothing, having
  already thrown away the working cluster it had. `TestConnectFailureLeavesTheCurrentClusterUntouched`
  pins the whole of what a failure costs: one transient toast, same context, same live
  watch (the watch context is asserted *not* cancelled), same rows.
  `TestSwitchContextConnectsOffTheUpdateLoop` pins the other half — that the connect runs
  as a Cmd and that nothing is torn down at that point.
- **Discovery restarting against the *new* discoverer is the assertion that proves the
  ordering.** The headline test wires a different `fakeDiscoverer` into each cluster and
  requires the new one to have been called exactly once and the old one not at all. A
  weaker "discovery is running" check would pass even if the restart happened before the
  swap — which is the realistic bug, since `startDiscovery` reads `m.discoverer` and both
  orderings compile. Every assertion in the new file was mutation-checked (dropping the
  gen guard, the reset, the swap, the async connect and the error branch each fails a
  named test), so none is vacuous.
- **`ClusterConnector` deliberately does not live on `Cluster`.** D155 pt 2's test —
  "would it be wrong to keep using this after a switch?" — says no: the connector outlives
  every switch and a `Cluster` is its *product*. So it sits on the Model beside the context
  name it changes, and the launcher (not `tui`) implements it, since connecting means
  `kube.Connect` plus the `PortForwarderFunc` adapter over a concrete `*kube.Clients` —
  the client-free boundary M4-02 kept. Reusing `clusterFor` rather than writing a second
  wiring path means a seam added there is live on both the launch and the switched
  cluster; a parallel path is exactly how a feature ends up pointed at the previous
  cluster after a switch.
- **`ctxGen` is the whole guard, and that is a narrower claim than D156 pt 2's.** A connect
  is a single call with no stream to cancel, so there is no context to tear down — two
  switches in quick succession (a mis-pick corrected immediately) are ordered by
  generation alone, and the superseded result is dropped rather than applied on top of the
  newer one (`TestStaleConnectResultIsDropped`). An inert switch — no connector wired, or
  the context already live — does not burn a generation, which the inert-cases table test
  asserts so a future no-op cannot silently invalidate an in-flight switch.
- Scope note: switching to the context already live is a no-op rather than a reload.
  There is nothing to gain from tearing down a working cluster to rebuild the same one,
  and M4-04b's picker marks the current entry rather than hiding it, so it is choosable.
  The namespace stays cleared by the reset (D156's corollary) — landing the new context
  in *its* last-used namespace is M4-05's, and inheriting the previous cluster's is the
  bug M4-05 exists to prevent.
- Decisions: D157 — a context switch connects before it tears anything down, so a failed
  connect costs one toast and changes nothing; the connector is per-app state, not a
  `Cluster` seam, and reuses the launcher's one `clusterFor` wiring.
