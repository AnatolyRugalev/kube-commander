## The one non-obvious thing: you cannot nest a styled span in a styled line

The obvious implementation — paint the cells, then hand the joined line to
`m.styles.App.Width(innerW).Render(...)` as before — is wrong, and quietly so. lipgloss
closes an inner style with a full SGR reset, so everything *after* the first colored cell
renders in the terminal's default foreground instead of the theme's:

```
\x1b[38;2;198;208;245mpod-a  \x1b[38;2;166;209;137mRunning\x1b[m  x\x1b[m
                                                            ^^^ unstyled
```

So a row with colored spans is concatenated from segments that are each rendered through
a *complete* style (`paintRow`), and the trailing pad to `innerW` is written by hand
rather than delegated to `Style.Width`. That is D164 pt 6, and it is a trap for any
future surface that paints inside a width-constrained line. The uncolored row — the
common case, since most kinds have no status column — still takes the old single-`Render`
path untouched, which `TestUncoloredTableRendersUnchanged` pins.

The span coordinates are the second half of it: `roleSpans` works in the *unclipped*
line's display columns (the same space as `columnStarts`), and `paintRow` subtracts
`m.hoffset` once and clamps. Keeping the clip in one place means `hclip`'s rune math
never sees an ANSI byte, which is the invariant its comment already relied on.

## Notes for whoever picks this up next

- **The classifier is data, extend it as data.** A new rule should be a column name in
  `classifyCell` or a word in `statusWords`, not a branch on the resource kind — that is
  the whole reason a CRD gets colored for free. `TestClassifyCell` is the place to say
  what a value means.
- **The known cosmetic:** a completed Job pod shows `Completed` (green) beside `0/1`
  (yellow), because READY is classified without looking at STATUS. Reading the row's
  other cells would fix it and would also re-introduce kind knowledge through the back
  door, so D164 pt 2 declines it deliberately. If a human finds it actually annoying in
  practice it is one condition in `readyRole`, and it should be feedback-driven.
- **The theme swap (M4-11/12) inherits this for free** — the roles are `styles.Styles`
  fields, so a new `Theme` re-colors the table with no change here. The one thing a theme
  must not do is give `Error`/`Warn`/`Success` a *background*: spans cover the value's own
  width, not the padded column, so backgrounds would look ragged. Worth a look when
  M4-11 lands.
- The dogfood value here is real but small: it is a pure render change with no cluster
  surface, so no human-task was raised. It will be seen for free during the next
  context-switch or logs dogfood.
