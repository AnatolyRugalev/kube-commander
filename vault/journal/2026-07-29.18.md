## Where the samples live, and why not in the rows

The obvious implementation is to write the usage into the row's cells when a poll lands:
the rendering, the sorting and the widths then need no changes at all. It is wrong twice
over. The rows belong to the watch and are replaced **wholesale** by every RESET — a
reconnect, a namespace re-list — so a sample folded into a row is destroyed within
seconds and has to be re-joined on arrival anyway; and `full.Rows` is the authoritative
set two other derivations (the filter, the sort) read, so writing into it is exactly the
shared-mutable-state shape principle 1 forbids, one call frame away from a delta.

So the component holds the map beside the rows and derives the display columns in
`applyFilter` — the single place the displayed view is re-derived from the authoritative
set. That choice is what keeps the rest of the diff near zero: the two columns are *real*
visible columns, so `measureWidths`, `rowMatches`, `columnStarts`, `hclip` and the M4-06
cell coloring all treat them like any other, and the rows and the samples refresh on
their own clocks without either clobbering the other.

Two places needed care rather than nothing:

- **Sorting.** The cells are formatted strings, and `"100m"` sorts below `"20m"` as text.
  `usageSortKey` compares the raw `CPUMilli`/`MemoryBytes` out of the map instead — exact,
  no parsing, and the map is already in hand. A row with no sample keys as `-1`, below
  every measurement including zero, so unscraped rows gather at one end.
- **`selectVisible`'s fallback.** A server table whose columns are *all* priority-1 falls
  back to showing everything. Counting the overlay's two priority-0 columns in that scan
  would have made the fallback never fire — such a table would have shown CPU and MEMORY
  and nothing else. The scan runs over the server's columns only and the overlay's are
  appended after (`TestUsageColumnsShownWithNoPriorityZeroColumns`).

## The nil/empty contract, and the poll's one arming point

`SetUsage(nil)` and `SetUsage(map{})` are deliberately different states: nil is "this
cluster does not measure this kind" (no columns), an empty map is "measured, nothing
scraped yet" (columns, blank). Availability decides whether the columns exist; samples
decide what is in them. Collapsing the two would make the columns flicker into existence
whenever the first sample landed and out again on an empty scrape — which is the visual
noise D167 pt 1 refused to build a probe for in the first place.

The poll is armed in `watchResource`, and nowhere else, for the same reason M4-08 put the
child scope there: it is the single place a browse watch starts, so every restart — kind
change, namespace re-scope, drill-down, the reconnect's re-list — re-evaluates
availability and re-scopes the poll in one step. A Node drill-down's pods are cluster-wide,
so the poll takes the *watch's* namespace (the scope's) rather than `m.namespace`; that is
`TestMetricsPollScopedToChildScopeNamespace`, and it is the same trap the M4-07 journal
flagged for the watch itself.

## Notes for whoever picks this up next

- **`stopClusterAsync` now inventories the metrics poll.** Anything else per-cluster and
  asynchronous goes there too, or it survives a context switch and reports the wrong
  cluster's numbers.
- **A batch now comes back from `watchResource`.** It used to return the watch pump
  alone; tests that did `cmd().(watchMsg)` still work because Bubble Tea's `Batch`
  collapses a single non-nil command, but a test on a *measured* kind must flatten
  (`drainMsgs` in `metrics_test.go`).
- **The metrics kinds are in the menu.** Discovery keeps every listable resource, so
  `PodMetrics`/`NodeMetrics` appear under Custom Resources and browsing them shows their
  server-printed table. That is how `availableResources()` can answer availability at
  all — and it means a future leg that filters the menu must not filter them out of the
  set `MetricsFor` reads.
- **Units are fixed on purpose** (millicores, mebibytes — never scaled to cores or GiB),
  so a column of them compares by eye and matches `kubectl top`. `Usage.Timestamp` is
  decoded but unused: dimming a stale sample is a rendering judgment that wants a real
  cluster, and is the obvious follow-up if a dogfood pass says the numbers ever look
  wrong rather than merely old.
- No human-task was raised. The mechanism is hermetically covered and the remaining
  question — do the numbers read well next to the other columns at a real terminal
  width — rides along on the standing dogfood passes, which now exercise it for free on
  the pod list they already open.
