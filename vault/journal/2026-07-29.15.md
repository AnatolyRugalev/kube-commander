## The shape question, and why it went this way

The board note already called it, but it is worth pinning: the tempting signature is
`Children(...) ([]Row, error)` — it is one call and the caller renders it. It is wrong
because the rows would be a **snapshot**. The browse table is fed by a watch; a
snapshot-only child table would sit there while pods restart, and would need its own
refresh mechanism to catch up. Handing back a scope instead means M4-08 calls the same
`Watch` it already calls, with an extra `ListOptions` — the child table is live, sorts,
filters, colors and accepts every row action with no new code path. That is D165 pt 1.

The second half is that a scope must be **honest or absent**. Every failure here returns
an error rather than a scope, including the one that looks harmless: a `spec.selector`
that is present but has no terms parses to `labels.Everything()`, whose `String()` is
`""` — which as a `ListOptions` field means *no filter*. That would have produced a
table titled "pods of deployment/api" listing every pod in the namespace. `sel.Empty()`
catches it.

## Notes for whoever picks up M4-08

- **`Namespace` in the scope is not the app's namespace.** A Node's children are
  cluster-wide (`Namespace: ""`), so the browse model must carry the scope's namespace
  alongside its own rather than reusing `m.namespace` — otherwise a Node drill-down
  silently shows one namespace's pods. The board note's "the browse model must carry the
  scope alongside the resource" applies to both fields, not just `Options`.
- **`Selector()` exists for the status bar**, so the TUI never has to know which of the
  two `ListOptions` fields a given owner filled in.
- **The watch restart is the real work.** `ListOptions` must be re-applied on every
  restart (namespace change, reconnect), which is exactly the place a scope is easy to
  drop. A test that drills in, forces a reconnect and checks the selector is still on the
  request is the one worth writing.
- **Gate the action on `HasChildren`**, not on a kind list in the TUI — that is the whole
  point of the predicate being exported, and it keeps the owner set in one place.
- Extending the owner set later: a `spec.selector` kind is a one-line entry in
  `childLinks` with no new parsing. An `ownerReferences`-based hop (CronJob→Job) is *not*
  available at this seam by design (D165 pt 5) — it would need a client-side filter over a
  full list, which is a different primitive.
