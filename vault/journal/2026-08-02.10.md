## Why the target goes in the title and not on the rows

The obvious alternative is to make each row say what it acts on — `Delete Pod
default/web-1`. It reads well in isolation and is wrong three ways in this surface. The
modal is 60 columns at most, so the object eats the width the verb needs and every row
repeats the same string. The label is also the identity a `SelectedMsg` is resolved by
(`cmdByLabel` and now `palRowByLabel` key on it), so putting the object in the label puts
it in the lookup key, and the key would then change whenever the cursor moved. And it
would make the object part of what the matcher searches, so typing a pod name would match
*every* verb equally — the ranking that makes the line usable would go flat exactly when
the list got longest.

The title carries it once, in chrome nothing resolves against, in the same
`viewerTitle(res, ref)` form the viewers and the delete confirm already use — so the
sentence a reader sees above the palette is the sentence they will see inside the confirm
modal a moment later.

## The one entry in this surface that can do damage

The previous leg's note ended on `:delete` — a palette opened over an unclear selection is
where a destructive verb goes wrong. Two things answer it, and neither is a special case
for delete. The selection is never unclear because the title names it (D205 pt 2). And the
pick does not delete: it emits `rowActionMsg{delete}`, which `handleRowAction` routes to
`openDeleteConfirm`, which opens the modal that names the target again and waits. The
palette adds a way *to* the action and no way *past* its confirmation — which is why the
test for this asserts on the modal being up and the fake deleter's call count still being
zero, rather than on the toast.

That also settles the shape for the mutating actions that fire straight from
`handleRowAction` (cordon, uncordon, suspend, resume — idempotent by D35). They are
reachable from the palette now and they act immediately, exactly as they do from `a`. That
is not a new exposure: it is the same gesture count as the actions menu, on the same
guarded set, and if it ever becomes wrong it is wrong for `a` first.

## Why the globals keep the top

`:` + Enter has meant "Switch resource" since PAL-02. Appending the row verbs keeps that
true whether or not a row is selected — the same line typed twice does the same thing. It
is not merely conservatism: the empty-query order is the *only* order the matcher does not
control, so it is the only place where a stable meaning can be promised at all. The moment
anything is typed, `NameMatcher` ranks row verbs and globals together on merit (D194 pt 1),
which is where a row verb should win — `:log` over a Pod is unambiguous, and it now lands
on Logs.

## Two things left for PAL-05

- **`ActionActions` ("Open actions menu for the selected row") is still a palette verb**,
  and it is now redundant with the entries it would open. It is kept because removing a
  way in is PAL-05's business, not this slice's (D194 pt 4) — and it is the one entry that
  still works when the palette's own row-verb list is empty for a reason PAL-04 did not
  anticipate. PAL-05 should decide whether it survives the conversion.
- **The row verbs cannot be reached with the menu pane focused and no row under the
  cursor**, which is `openActionsMenu`'s precondition, deliberately mirrored. If PAL-05
  makes `a` a pre-typed palette line, the two inertness rules become one and this is where
  to check they still agree.
