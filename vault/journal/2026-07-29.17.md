## Why availability is a discovery lookup and not a request

The obvious implementation of "are metrics available?" is to ask: list once, and if it
works, show the columns. It is wrong in the case that actually happens. metrics-server
is the canonical flaky aggregated API — installed, registered as an APIService, and
returning 503 because its pod is restarting or its scrape window has not filled. A probe
would make that a *runtime* condition: columns appearing and disappearing between
refreshes, an error to decide what to do with on every tick.

Discovery already answers it, and answers it better. `ServerPreferredResources` isolates
a group it cannot load into `DiscoveryResult.Failed` rather than `Resources` (#87 — the
original's central bug, and metrics-server was always the classic trigger). So a group
that is down is simply *not in the available set*, which is byte-for-byte the same input
as a group that was never installed. One code path, no probe, no request at all before
the reader has asked for anything. That is D167 pt 1, and `TestMetricsForAbsentWithout
MetricsServer` is deliberately written against a kind set with the group missing — it
does not care which of the two reasons produced it, because nothing downstream should.

The corollary for M4-10: **do not add a "metrics unavailable" message.** There is
nothing to say, and the milestone's exit criterion says so too — "absence is silent".

## The trap that cost this leg its first red run

`UsageKey` exists because a `PodMetrics` is not a `Pod`. It has its own `metadata`, and
its `uid` is either empty or unrelated to the pod's. `ObjectRef` — the key the table's
rows are addressed by — carries a UID, so the natural `map[ObjectRef]Usage` compiles,
type-checks, reads fine, and matches nothing at runtime, for every row, forever. The map
is keyed by `UsageKey{Namespace, Name}` instead and `UsageKeyOf(ref)` is the only
sanctioned way to build one from a row (D167 pt 2).

The second trap is in the tests, and it is worth knowing before writing any fake-dynamic
test for a resource whose plural is not its kind lowercased: objects handed to
`NewSimpleDynamicClientWithCustomListKinds` are filed under a GVR the fake **guesses
from the kind** (`UnsafeGuessKindToResource`). `PodMetrics` guesses to something that is
not `pods`, so every seeded sample went into a resource nothing lists, and `Metrics`
returned an empty map **with no error** — the failure mode looks exactly like "the
server has nothing yet". The fixture now constructs the fake empty and calls
`f.Tracker().Create(gvr, obj, ns)` with the real GVR. Recorded in `stack.md` under
Testing, next to the existing fake-dynamic gotchas (D35/D36).

## Notes for whoever picks up M4-10

- **`HasMetrics(kind, availableResources())` is the gate**, evaluated where the browse
  table learns its kind — not a `Kind == "Pod"` check. It costs nothing (a map lookup
  plus a scan of the discovered set) and keeps the measured-kind set in one place.
- **Poll, then join, and keep the samples out of the row data.** The rows are the watch's
  and they are re-`RESET` from under you; the usage map is a separate value the render
  reads through `UsageKeyOf(row.Object)`. A missing key means "not scraped yet" and must
  render as blank, never `0m`.
- **A refresh that errors keeps the previous map.** The columns should not blink empty
  because one tick hit a 503; log it (D159) and try again on the next tick. Whether the
  columns should eventually disappear after N consecutive failures is a judgment call
  M4-10 gets to make — D167 does not constrain it.
- **The ticker belongs to the shell, not to a goroutine loop** — `tea.Tick` in the update
  loop, generation-guarded like every other async here, cancelled on kind change, on
  namespace change and on quit. Roughly 10 s is the right order: metrics-server's own
  default scrape interval is 15 s, so anything faster re-fetches the same sample.
- **`Usage.Timestamp` is the honest staleness signal.** If a node's sample is minutes
  old the number is still what the server said, and dimming or annotating it is more
  useful than hiding it — but that is a rendering choice, and it needs a real cluster to
  judge, so it may be worth a dogfood note rather than a guess.
- Formatting (`1250` → `1.25` / `1250m`, bytes → `128Mi`) is deliberately *not* in the
  kube layer: it is presentation, it belongs beside the other column rendering, and the
  primitive owes the TUI numbers rather than strings.
