## The question the feedback asked, and why state won

The feedback was explicit that this is a real fork and asked for it to be picked
consciously: "does a pinned CRD land in the authored menu file (visible, hand-editable,
survives as config) or in the state file (invisible, automatic, 'recorded for you')".

The deciding line is not visibility, it is **who writes the file**. D90 created the state
file so kubecom would have somewhere it could rewrite freely "without ever reformatting or
clobbering the comments in a hand-edited config file". A pin is produced by a keypress, at
a rate of one per CRD you touch, and CRD-PIN-03 will delete them by keypress too. Pointing
that write loop at a file a user may have commented and ordered is exactly the thing D90
forbids — the first `p` would silently reformat it. So the pin is state, and D193 pt 1
turns that into a standing prohibition rather than a preference, because the tempting
future leg ("just append it to the menu file, it's the same struct") is obvious.

What the menu-file side had going for it — hand-editability and being visible config — is
mostly preserved anyway: the state file is plain YAML in a documented location, and pins
use the *same* `MenuResource` schema, so a user who wants to hand-write one can, and can
move it into `menus/<context>.yaml` if they want it to be permanent config rather than
something a keypress can remove.

## The merge, and the bug it is written to prevent

Both lists reach the menu through `menu.AddExtras`, which already dedupes by GVR against
seed rows, earlier extras, and (via `Reconcile`, D57) discovered twins. So the launcher's
`mergeMenuExtras` is not what makes dedupe work — `AddExtras` would have handled a plain
concatenation. It exists to make the **precedence explicit and testable**: authored first,
a pin with a colliding GVR dropped, so the hand-written section/title is what renders. A
property that only holds because one slice happens to be scanned first is a property the
next leg breaks by accident.

The real trap is the second call site. `LoadContextState` is what a context switch reads
(M4-05/D163), and the menu is rebuilt from the `ContextState` it returns. A merge added
only to the launch path would work perfectly until the first `C`, at which point the new
context would show the *old* context's pins — the precise failure D163 was written to
prevent, and the one the feedback flagged ("whichever file this lands in must be part of
that rebuild"). `TestLoadContextStateMergesPinsForTheSwitchedContext` pins it.

## Why the README is untouched

Nothing a user can do changed in this slice: there is no key that pins, and the state file
is documented as kubecom-managed. Documenting `pinnedResources:` now would advertise a
hand-edit into a file the README correctly tells people not to hand-edit, before the
gesture that makes the key worth knowing exists. The README section lands with CRD-PIN-02,
which is noted on that board item so it cannot be forgotten.

## Triage of the rest

Four slices, bottom-up (D52), on the board:

- **CRD-PIN-02** the write gesture — a named `pin.toggle` action (never a raw key, D10/D11)
  on the picker and the menu, a persister seam so `internal/tui` still touches no disk, and
  `AddExtras` on the live menu so the row appears without a relaunch. It needs the kind's
  `Namespaced` flag from *discovery*, not a guess — a namespaced CRD pinned as
  cluster-scoped lists nothing.
- **CRD-PIN-03** the unpin — the half the feedback insists must be as easy as the add. It
  is the one that needs new menu state: only a *pinned* row may be unpinned, so `Item` has
  to carry provenance. A kind that discovery also lists reverts to a discovered row rather
  than vanishing.
- **CRD-PIN-04** "reach for it once" — the premise the line rests on needs a surface
  listing *every* discovered kind. That is the resource picker, which the
  `2026-08-01-command-palette-unification` feedback wants to turn into `:resource` inside a
  general palette. Sequenced last for that reason: two legs remodelling the same picker in
  either order would fight.
