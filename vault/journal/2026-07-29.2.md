# 2026-07-29 — M2-15: half-page/page nav in the resource menu

- Agent: claude-opus-5

- Did: The left menu handled `nav.up/down/top/bottom` only, so `ctrl+d`/`pgdn` and
  `ctrl+u`/`pgup` were inert in the pane even though it scrolls and discovery grows it
  past a screen (the gap M2-EXIT filed). Added the four page actions to
  `menu.Model.Update`. No new decision — the constraint lives in the code comment.

- **Why paging steps in display rows, not item indices.** This is the whole substance of
  the leg and the one thing a future refactor could get wrong. The table's `pageStep` is
  the visible *data height* and its cursor indexes rows one-to-one with lines, so
  `moveTo(cursor ± pageStep)` is exact. The menu's lines are not its items: section
  headers (D77) occupy screen lines the cursor can never land on, and the scroll `offset`
  is already a display-row offset for exactly that reason. Stepping the cursor by item
  index would therefore scroll the window *further* than one page in any section-dense
  stretch of the list — the seed menu is seven sections deep, so a page-down near the top
  would skip roughly a section's worth of items off-screen. `moveByRows` converts through
  `cursorRow()`/`rows()` instead: clamp the target row to the row range, then walk to the
  first non-header row in the direction of travel (and back the other way if the clamp
  landed past the last item), and hand the resolved item to the existing `moveTo` so the
  clamping and `scrollToCursor` behaviour is byte-identical to every other move. That last
  part is why the diff needs no new scroll code at all.
- **`halfPageStep` floors at 1, unlike the table's `pageStep()/2`.** In a one- or two-row
  pane the table's half-page is a literal no-op (`1/2 == 0` → `moveTo(cursor)`). Copying
  that faithfully would have shipped a key that silently does nothing, which is the exact
  complaint M2-15 exists to fix, so the menu floors it — a full page already floors at 1
  the same way. Not worth a decision, but worth not "matching" a bug.
- **Nothing needed wiring.** `routeNav` already forwards every non-focus-switching action
  to the focused pane, so the app side was complete and only the component was deaf. That
  is also the failure mode most likely to come back, so `TestMenuPagingKeysReachTheMenu`
  asserts it end-to-end through the real key path (`ctrl+d` with the menu focused moves
  the cursor more than one row, `ctrl+u` returns it) rather than trusting the component
  test alone. No keymap entry, no hint-bar and no `docs/keybindings.md` change: the four
  actions are long-registered globals, and no hint context advertises them for the table
  either, so the menu stays consistent by leaving them off.
