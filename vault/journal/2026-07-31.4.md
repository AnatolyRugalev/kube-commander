## Two flags, and why one of them is a trap

The board note inherited from b-1 said this leg needed a short
`--etcd-compaction-interval`, because a stock plane replays a watch from
`resourceVersion=1` even after 150 writes. That is right and it is not sufficient. With
only compaction shortened, the watch **still** replays:

| plane | watch from a long-passed rv |
| --- | --- |
| stock | replays every event |
| `--etcd-compaction-interval=1s` | replays every event |
| `--etcd-compaction-interval=1s --watch-cache=false` | `410 Expired` in ~300 ms |

The reason is that compaction bounds *etcd's* history, and with the watch cache on the
apiserver is not reading etcd — it answers the watch from memory, where the compacted
revisions are still sitting. So the bound in force is the cache's window, and that
window cannot be shrunk into test range from a flag: it starts at 100 events and
**grows** whenever it fills within 75 s. Writing past it enlarges it. That is exactly
what b-1's 150-event probe measured, and reading its result as "the RV window is etcd's
revision history" was half the picture — it is etcd's history *once you take the cache
out of the path*, and the cache's own window otherwise.

Serving from etcd is a faithful shortcut rather than a different code path, which is
what makes the flag legitimate: both the cache and etcd answer an out-of-window watch
with the same `Status{Reason: Expired, Code: 410}`, and the client cannot tell them
apart — that status is the entire contract `watchStatusError` parses.

## Why the timing works out

The interesting constraint is that the loop must *hold* its resourceVersion while it
goes stale. Only one path does: a stream that ends without an expiry (`io.EOF` from the
cut wire) leaves `rv` untouched and sleeps one `watchRetryBackoff`. Every other failure
route — a failed watch open, a failed List — already sets `needList`, so it would
produce a RESET for a reason that has nothing to do with expiry, and the test would pass
while proving nothing.

So the whole test lives inside that 2 s gap, and it fits with room to spare:

```
t+0ms     proxy.dropAll()          stream EOF; loop keeps rv, sleeps 2 s
t+~10ms   create during-outage     etcd revision moves past rv
t+~300ms  rv is unreplayable       (measured; 100 ms compaction interval)
t+2s      loop reopens from rv  →  410 Expired → needList
t+4s      List → RESET             the assertion
```

Compaction only drops history *below* a revision it has already seen, so a quiet cluster
never expires anything no matter how short the interval — `waitUntilExpired` writes a pod
between probes for that reason, not for pacing.

## The precondition is the point

`waitUntilExpired` opens a throwaway watch from the held resourceVersion and fails the
test if the server has not started refusing it. That is not a retry helper; it is the
assertion that this test's premise holds, and it is what stops the most confusing
possible pass. If the revision has not expired, the loop **resumes** — which is correct
behavior for the situation it is actually in, and is precisely what b-1 asserts. The test
would then be re-testing b-1 under b-2's name, or failing with a message about a missing
RESET that points at the watch loop instead of at the plane.

Held-rv choice matters for the same reason: it is read *after* the pre-outage delta, so
it is at least the loop's own. Compaction drops a contiguous prefix, so proving the
larger one expired proves the smaller one did.

## The two ways it was watched fail

1. **Drop the compaction flag.** The premise check fires in 2 s:
   `resourceVersion 192 was still replayable after 2s of compaction: the plane is not
   expiring anything, so this test cannot prove the re-List path`. This is the
   configuration the leg started from, so the message is aimed at whoever inherits the
   flags and wonders whether they are still load-bearing. They are.
2. **Break the re-List branch** (`if false && errors.As(werr, &exp)` in `watchLoop`).
   The channel goes **silent** — no RESET, no ADDED, nothing — because the loop reopens
   the same refused resourceVersion every 2 s forever. It fails on the read timeout, and
   the message says what a silent channel means here: a table that quietly stopped
   updating, which is the user-visible shape of this bug and the reason it would never
   be noticed without a test. Slow to fail (60 s) but unambiguous.

The RESET assertion also checks its rows contain *both* the pre-outage and the
during-outage pod, and that it carries columns: a re-List that loses rows is worse than
no re-List, and a consumer told to replace its whole row set needs the column
definitions to render it (`WatchEvent`).

## Cost

The plane starts in ~4 s and the test takes ~8 s, of which 4 s is the loop's own pacing
(one backoff before the doomed reopen, one after). The gated suite is now five tests /
five control planes in 27 s — still a per-leg command. `startControlPlane` taking
per-test options makes the existing one-plane-per-test rule load-bearing for a second
reason: the planes are no longer even identical, so there is nothing left to share.
