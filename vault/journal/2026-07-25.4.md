# 2026-07-25 — LOGS-02: res.logs streams into the dedicated logs view

- Agent: claude-opus-5
- Milestone: M3
- Did: Wired LOGS-01's component up and retired the shared-viewer logs path, which is the
  whole of what D134 asked for: `res.logs` (`L`) now opens the **full-screen logs view**
  with its live grep instead of the centered M3-01 pager. `/` narrows the already-streamed
  lines *while the log keeps following* (matched/total in the header, nothing re-fetched),
  `f` and any upward scroll still pause/resume follow, and the shared viewer is now
  one-shot content only — YAML/describe/secret. The container picker (M3-07a) and
  pod-owning resolution (M3-07b) feed the new terminal unchanged. → D144.
- What actually got deleted is the point. The shared viewer had grown a logs *mode*: a
  `viewerKindLogs` stamp, `logFollow` + `logTitle` on the root model, `syncLogViewerTitle`
  splicing `[following]`/`[paused]` into a title string, and an `isScrollUp` rule that had
  to run *before* forwarding the action so an up-scroll could pause follow. All five exist
  only because one component served two content shapes; all five are gone, and the
  behaviours they implemented are the component's own (`Following()`, the header, the
  pause-on-scroll-up inside `Update`). The shell kept exactly the two things that are
  genuinely concurrent: `logCh`/`logCancel` and the generation.
- Four choices worth naming. (1) **`viewerGen` stays the single supersede clock**, shared
  with the viewer, rather than a new `logsGen`. The container and pod-owning resolutions
  are shared with exec and already bump it, so a second counter would have to be bumped in
  the same three places to be correct — a guard you can forget is worse than a coarse one
  (D144 pt 3). Only `handleLogMsg`'s liveness check moved, `!m.viewer.Active()` →
  `!m.logsView.Active()`. (2) **The filter-closed keys go through the sequencer, the
  filter-open keys do not.** The search view resolves `keymap.Action` directly because its
  query field is always open; the logs grep is *modal*, so with it closed the view can take
  the ordinary `handleAction` path — which is what makes `gg`/`G` work in a log, for free,
  the way they work everywhere else. Only `m.logsView.Filtering()` short-circuits into raw
  routing. (3) **Two hint contexts, not one.** D143 pt 1 says a hint entry is a promise, and
  the grep changes what the view honours: closed, `q` closes the view and `f` toggles
  follow; open, both type a character. So `HelpLogs` advertises scroll/grep/follow/back/quit
  and `HelpLogsFilter` only scroll/back, with `syncHints` re-run wherever the field opens or
  closes (D143 pt 3 applied to a sub-state, not just to the view). (4) **`q` closes the view,
  not the app** — the viewer/help/search precedent, so a pager never exits kubecom.
- One thing I deliberately did *not* fix, because it needs a measurement I can't take:
  `logsview.render()` re-joins the entire line buffer on **every** appended line, so cost
  grows with lines held rather than with the arrival rate. On a busy pod that is a plausible
  gradual slowdown, and the honest fix (keep the rendered content, append to it) is a
  different change from this leg's rehome. Hermetic tests feed a handful of lines
  synchronously and can never see it, so it went into a **human task** (D79) with the
  suspected mechanism named and a `Blocks: none`, plus a pointer that a confirmed slowdown
  outranks LOGS-03/04.
- Decisions: D144 — streaming content gets its own full-screen view and the shared viewer
  is one-shot-only (no new `viewerKind*` for a stream); state a view renders is the view's,
  not the shell's; `viewerGen` remains the one supersede clock across content surfaces; a
  full-screen view with a text field needs two hint contexts.
