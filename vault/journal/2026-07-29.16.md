## Why this leg is small, and where the one subtle bit is

M4-07 chose the shape that made the consumer thin: because `Children` hands back a
scope rather than rows, the drill-down is not a new data path at all — it is the
ordinary browse watch with a namespace and a `ListOptions` the shell carries. Sorting,
filtering, cell coloring (M4-06), every row action and the watch's own reconnect keep
working with no new code, and the child table is *live*.

The one place it could have gone wrong is where the scope is read. Passing it as an
argument to the watch start would have worked exactly once: the second start — a
re-selection, a reconnect's re-list — would drop it and quietly widen a table titled
"pods of deployment/api" to every pod in the namespace. So `selectResource` was split
in two:

- `selectResource(r)` clears the scope, then calls
- `watchResource(r)`, which reads whatever scope the model holds.

Every path a reader takes to a kind *they* chose (menu drill-in, resource palette,
search hit, namespace re-scope) goes through the first; the drill-down installs the
scope and calls the second. That is D166 pt 1/3 and it is the whole safety argument —
there is no third way to start a browse watch. `TestChildScopeReappliedOnWatchRestart`
pins it by calling `watchResource` a second time and asserting the selector survived.

Two smaller things worth knowing:

- **The namespace is half the scope.** A Node's pods are cluster-wide
  (`Namespace: ""`), so `watchResource` takes the scope's namespace *instead of*
  `m.namespace`, not in addition to it. Reusing the app's namespace would have shown
  one namespace's pods under a title claiming all of the node's — the M4-07 journal
  flagged exactly this.
- **Resolve, then switch.** The table is untouched until a scope comes back, so a
  selector-less Service or a deleted owner leaves the reader watching what they were
  watching, with one toast. Same ordering as the context switch's connect-before-teardown
  (D157), same reason.

## Notes for whoever picks this up next

- **`availableResources()` is now the single kind snapshot.** Cluster search and the
  drill-down both take it (it was inlined in `searchResources` before), so the two
  cannot disagree about what this cluster offers. A third consumer should use it too.
- **Extending the owner set is a kube-layer change**, not a TUI one: the action gates on
  `kube.HasChildren`, so a new entry in `childLinks` lights the gesture up here for free
  (D165 pt 6). Resist adding a kind list to `rowActions`.
- **The return path reuses the search drill-in's pending selection**
  (`searchTarget`/`applyPendingSelect`), because it is the same problem: the owner's row
  only exists once the fresh watch's first RESET lands. If a third consumer appears, that
  field pair deserves a neutral name.
- **A child table's own row actions are the child kind's**, resolved against the child
  `Resource` the caller's discovered set supplied — so `P` on a pod inside a child table
  is inert, and delete/logs/exec are gated on the pods' real verbs. Nothing special was
  needed for that; it falls out of the scope carrying a real `Resource`.
- The M4 drill-down exit criterion is ticked on this evidence. What no fake shows is a
  real apiserver honouring the selector, but that is client-go's contract rather than
  kubecom's, and the kube half is fake-client covered (D66) — so no human-task was
  raised; the next dogfood pass exercises it for free, since `P` sits on the same
  screens as the context-switch check.
