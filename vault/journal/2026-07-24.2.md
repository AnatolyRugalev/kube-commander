- Did: Extended the Port-forward action to **Services** (M3-13a narrowed it to Pod-only,
  D122). A Service can't be forwarded directly — `kube.PortForward` POSTs to the pod
  `portforward` subresource — so the shell resolves a Service to a backing endpoint pod
  first, mirroring the logs viewer's `PodResolver`/`PodForOwner` hop (D112). New
  **`kube.PodForService(ctx, ref)`**: reads the Service's `spec.selector` (a flat label
  map, via the typed clientset — no unstructured parsing), lists matching pods, returns
  the **newest Ready pod** (fallback newest overall) reusing `newestReadyPod`; a
  selector-less Service (headless/ExternalName), a missing Service, or no matching pods
  is a wrapped error the caller degrades to a toast (principle 3), never a panic. New
  **`ServiceResolver` seam** (`WithServiceResolver`, `*kube.Clients` satisfies it) —
  separate from `PodResolver` since the two resolve for different features and a Pod row
  forwards with no hop. `openPortForwardPrompt` now branches on kind: a **Pod** takes the
  extracted `showPortForwardPrompt` directly; a **Service** resolves off the update loop
  (a fresh `pfResolveGen`, gen-guarded like `viewerGen`) → `serviceResolvedMsg` →
  `handleServiceResolved` opens the ports prompt over the resolved pod (titled/labelled as
  the Pod, so the user sees which endpoint pod is forwarding), or toasts on error / drops
  a superseded resolution. With no resolver wired a Service **degrades to a toast**, not a
  silent no-op. Re-added `Service` to the Port-forward applicability in `rowaction.go`.
  Ports typed are pod-side — no Service-port→targetPort translation (out of this slice's
  scope, D123). → D123.
- Decisions: D123 — port-forwarding a Service resolves it to a backing endpoint pod

  toast); separate seam from PodResolver; resolve-then-prompt off the loop, gen-guarded,
  no resolver → toast; ports are pod-side.
