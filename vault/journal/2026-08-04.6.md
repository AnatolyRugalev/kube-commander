## The pane drops what it cannot fit, so line order is a correctness property

`table.noticeBody` renders a notice into the rows the pane has and returns early when it runs
out — text past the available rows is dropped, not scrolled. That is the right behaviour for a
pane that is not a viewer, and it was harmless for CRD-01, whose notice is three lines.

It stops being harmless here, because the plugin's stderr is the only part of this notice with
no bound on its length (8 KiB, capped by `execDiagnosisStderrLimit`). A notice that reads
"here is what failed, here is what it said, …and here is the command that fixes it" puts the
one actionable line in the position most likely to be dropped — and dropped *silently*, with
no ellipsis, on exactly the small pane where a user is most likely to be squinting at a
problem. So the order is: headline, cause, remediation, the invocation, then the stderr. Read
top-down it degrades gracefully at every truncation point.

The rendered check at 58 columns (transcribed, styles stripped):

```
Cannot list Pod
The credential plugin your kubeconfig runs for context
"acme-prod" failed, so the request never reached the
cluster. The fix is on this machine, not in the cluster.
The AWS SSO session for profile "acme-prod" is expired or
missing.
Run this in another terminal, then reopen the resource:
  aws sso login --profile acme-prod
Plugin: aws --region eu-west-1 eks get-token --cluster-
name acme --profile acme-prod (exit 255)
It said:
  The SSO session associated with this profile has expired
or is otherwise invalid.
```

Two things that render worse than they read as a string, both accepted: a wrapped line loses
the two-space quote indent on its continuation, and the command line wraps mid-token. Fixing
either means the notice knowing the pane's width, which is a component's job and not a copy
function's — if it matters after a dogfood, it is the viewer's (D135) job, not this one's.

## Not restating client-go's error is the one thing this notice *removes*

`browseFailure` ends every notice with `Server: <the error>`, on the principle that the
server's own words beat kubecom's paraphrase. `authFailure` deliberately drops that line, and
it is worth being explicit that this is a removal and not an oversight.

The error in a `KindExecPlugin` failure is `exec: executable aws failed with exit code 255` —
client-go's own rendering, which AUTH-01 had to match with a regexp because the wrap chain is
broken by `%v` formatting (D195 pt 3). Every fact in it is now stated better elsewhere in the
notice: the executable by the `Plugin:` line, the exit code beside it, and the *reason* — the
thing the error never carried — by the stderr. A row spent restating it is a row of stderr
lost, on a surface that drops its tail. It survives in the toast and in `surfaceError`'s log
line, which is where a bug report is assembled from anyway (D159).

## Four causes, because four different people have to do four different things

The cause sentence branches on the diagnosis, not on the error kind, and the branches are not
shades of one message:

- **Exited non-zero** → re-authenticate (and, if the catalogue substantiated one, here is the
  command).
- **Binary not found** → *install* it; re-authenticating cannot help, and the sentence says so
  in as many words because this is the case where a user will otherwise spend ten minutes
  refreshing a session that was never the problem. `InstallHint` — the operator's own answer,
  usually empty — is printed here and nowhere else, flattened, since it is free text.
- **Timed out** → neither of the above. The plugin is wedged (waiting on a prompt it will
  never get, since `Diagnose` closes stdin), so the honest advice is to run the quoted command
  in a terminal and watch what it waits for.
- **Did not fail at all** → nothing. This is D211 pt 5's obligation, and the test asserts the
  *absence* of every fix-flavoured string: a user who re-authenticated in another terminal
  while the pane sat there must be told the plugin works now and that kubecom keeps retrying,
  not handed a command for a problem that is over.

## `Suggested` collapses two cases, and says so where someone will read it

D212 pt 3 distinguishes "not recognised" from "recognised but the stanza names no profile",
and the AUTH-03 journal noted that AUTH-04 renders them the same but AUTH-05 must not. A
single `Suggested bool` on the report is what makes the first half easy and the second half a
trap — so the field's own doc comment says it is for renderers, and that anything acting on
the difference must ask `SuggestedRemediation` itself.

The copy had to move for the same reason. The first draft said "kubecom does not recognise
this failure", which is a lie in the unsubstantiated case — kubecom recognised it perfectly
well and declined to guess the profile. It now says it has no command it *can* suggest, which
is true of both, and the test drives both plugins through it.

That case also caught the sloppiest assertion in the suite: "no command was invented" was
first written as "the notice does not contain `sso login`", which fails on the
unsubstantiated case for the best possible reason — the AWS CLI's own stderr says *"To refresh
this SSO session run aws sso login"*. Quoting a provider telling the user what to run is not
kubecom suggesting a command, and the assertion now names the remediation block's own lines
instead.
