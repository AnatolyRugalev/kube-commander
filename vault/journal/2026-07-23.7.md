- Did: Enabled the logs viewer for pod-owning workload kinds (#84) — Deployment/
  ReplicaSet/StatefulSet/DaemonSet/Job/ReplicationController — by resolving a backing
  pod before streaming, replacing the "not yet available" degrade. Added a kube-layer
  `PodForOwner(ctx, res, ref) (ObjectRef, error)` (`internal/kube/podresolve.go`): it
  Gets the workload through the **dynamic client by GVR** (one path for all six kinds,
  and any CRD with a pod selector), reads `spec.selector` — a `metav1.LabelSelector`
  (matchLabels/matchExpressions) for every kind but ReplicationController, whose
  selector is a plain label map, both shapes converted to a `labels.Selector` by
  `podSelector` — lists the matching pods via the typed clientset, and returns the
  **newest Ready pod** (falling back to the newest pod overall when none is Ready, so a
  mid-rollout / crash-looping workload still yields a log target). A missing selector or
  no matching pods is a wrapped error, never a panic (principle 3). Wired a `PodResolver`
  shell seam (`WithPodResolver`; `*kube.Clients` satisfies it). Refactored `openLogsViewer`:
  a Pod goes straight to the container path, now factored into a shared
  `resolveContainersFor(res, podRef)` (the tail extracted from the old pod branch); a
  pod-owning kind first issues `PodForOwner` off the update loop (fresh `viewerGen`
  guard), and `handlePodResolved` feeds the resolved pod into `resolveContainersFor` so
  **D111's container resolution/picker applies unchanged**. The resolved pod's logs are
  titled as a **Pod** (`podLogResource`) so the user sees which pod is tailing, not the
  workload. `WithPodResolver` gates it: with no resolver wired a non-pod kind still
  degrades to the M3-05…07a toast. Launcher wires `WithPodResolver(clients)`. → D112.
