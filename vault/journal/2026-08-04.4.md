## The bound that matters is not the timeout

`Diagnose` sets a 15 s deadline, and the obvious reading is that a wedged credential plugin
therefore costs at most 15 s. It does not, and the test that proves it took 30 seconds to
fail: `sh -c 'sleep 30'` under a **50 ms** deadline ran to completion.

The deadline does what it says — `exec.CommandContext` kills the process on `ctx.Done()`.
What it does not do is end `Wait`. Because `Stdout`/`Stderr` here are ordinary writers
rather than `*os.File`s, `os/exec` wires the child through an `os.Pipe` and copies in a
goroutine, and `Wait` blocks until that copy returns — i.e. until **every** holder of the
write end is gone. A shell that forks rather than execs, a plugin that spawns a helper, a
wrapper script: any of them leaves a grandchild holding the pipe after the parent is killed,
and the copy blocks on the grandchild.

`Cmd.WaitDelay` is the bound that actually closes the pipe, and it is the one a reader would
not think to look for, so it is D211 pt 4 and a `stack.md` entry rather than a comment: it
applies to every future subprocess kubecom captures output from, not just this one. It is
also why the timeout test asserts *elapsed time* rather than just the `TimedOut` flag — the
flag was already true in the 30 s run.

## Discarding stdout is a feature, and the test says so out loud

A credential plugin's stdout is an `ExecCredential`: `{"status":{"token":"k8s-aws-v1.…"}}`,
a live bearer token for the cluster. The natural implementation of "capture the output"
grabs both streams into one buffer, which is how a token ends up in a struct that AUTH-04
renders into a pane and a user pastes into an issue. So `Stdout` is `io.Discard`,
`ExecPluginDiagnosis` has no field it could live in, and `TestDiagnoseNeverCarriesStdout`
formats the *whole* diagnosis with `%+v` and fails if a marker printed on stdout appears
anywhere in it. Merging the streams fails that test today, which is the point of writing it
as "anywhere in the result" rather than as "not in `.Stderr`".

(The first version of that test failed for a silly reason worth recording: the marker was a
literal in the shell script, and `CommandLine` — correctly — echoes the script. The token is
now assembled by the shell, so the command line cannot contain it.)

## Why a re-run is not a re-test

The tempting contract for `Diagnose` is "returns the error, with better text". It is not
that, because the plugin is re-run *later* than the request that failed, and in between the
user may have re-authenticated in another terminal — which is exactly the workflow the
feedback describes. So a successful re-run is a real, common, useful outcome, and it must
not be reported as a failure or as an error. Hence `Failed()` as the predicate, and an
`error` return reserved for "could not be attempted": no stanza (tagged so `Classify` says
`KindBadContext`, like every other unusable-kubeconfig case) or a cancelled caller.

AUTH-04 inherits a small obligation from that: "the plugin worked when I re-ran it" is a
message it has to be willing to show, not a case it can assume away.

## What is deliberately not here

No provider knowledge. The stderr is returned raw and unparsed — matching the AWS CLI's
SSO-expiry wording, and resolving the profile from `--profile`/`AWS_PROFILE`, is AUTH-03,
and D195 pt 5 keeps it a one-entry table rather than a framework. No caller either: wiring
`Diagnose` into the failure path is AUTH-04's, where it can be attached to a surface big
enough for multi-line stderr. The seam is deliberately a method on `ExecPlugin` (which
`ExecPluginFor` already returns) rather than a new interface, so AUTH-04 wires one thing.
