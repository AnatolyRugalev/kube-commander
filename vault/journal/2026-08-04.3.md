## The exception that was a mis-filing

D209 pt 3 was written one leg ago and this leg contradicts a third of it, which is worth
being precise about rather than quiet about. The decision grouped `actPicker` with
`ctrPicker` and `portPicker` as surfaces that list "a *selected row's* own data", and
gave the test: could a reader name the value on the palette line before seeing the list?
Applied honestly to the actions menu the answer is **yes** — `Delete`, `Describe`,
`Exec shell` are a compiled-in registry (`rowActions`), the same fifteen entries on every
cluster, and a reader who has used kubecom twice can type `:action del` without looking.
What is row-scoped is which *subset* applies, and that is a filter over a known set, not
data the object carries. A Pod's container names are the other thing entirely.

The clinching evidence was already in the tree: PAL-04 put those exact titles into the
palette's verb stage on 2026-08-02, resolved through `palRowByLabel`, dispatched through
`dispatchRowAction`. So the actions menu was not a surface the rule did not owe — it was
the one remaining surface listing a set the palette *already listed*, which is the
duplicated-surface state D197/D207 pt 3 exist to remove. D209 pt 3 got the principle
right and the instance wrong, so D210 supersedes that third of it and leaves the rest.

## Narrower, not identical — the question the board asked

The slice's open question was whether `a` should open the whole verb stage (making it a
second `:`) or a row-verbs-only one. Row-verbs-only, because the *reason* to keep the key
at all is that it is narrower: `a` is "what can I do to this?", and answering it with a
list whose first six entries are Switch resource / Switch namespace / Switch context /
Search / Toggle forwards / Act on the selected row is answering a different question. The
cost of narrowing is that the other verbs are behind one backspace — which is the rewind
D207 pt 2 already built for every other converted key, so it cost nothing to inherit.

That also settles the second question in the note. `ActionActions` **survives** as a
palette verb, and it is no longer redundant: picking it in the verb stage is now the way
to *narrow* to the row verbs from inside the palette, which is exactly what its key does.
A verb whose entry pointed at a surface that no longer exists would have had to go; a
verb that enters a stage is a verb like the other five.

## The title is the one place this stage is not like the others

Every argument stage titles itself with its verb's `Describe()`. This one does not: it
reads `Command — Pod default/web-1`, the verb-stage title, because D205 pt 2's rule is
about the *object* and this is the stage where every entry acts on one. Titling it "Act
on the selected row — Pod default/web-1" would spend 28 of ~60 columns restating what the
`:action ` prompt already says, and would push the target — the part that stops a `Delete`
being picked over an unnamed selection — off the edge on any real object name. So
`enterPaletteArg` grew a per-arm title override, defaulting to `a.Describe()` for the
five stages that want it.

## The map that is cleared on close, from the other side

PAL-05c-2's journal recorded that `ctxByLabel` must stay *out* of `closePalette` because
`applyPaletteArg` closes before it resolves. `palRowByLabel` is the mirror case: it is
*in* `closePalette` (PAL-04 put it there, correctly — it is the palette's own state), so
the new arm cannot resolve after the close. Reading it out into a local before
`m.closePalette()` is the whole fix, and the failure it prevents is the quiet kind: the
palette shuts, no intent is emitted, no error is surfaced, and `Delete` on a pod looks
like a key that did not register. The mutation is recorded in Verify above rather than
left to a comment, and D210 pt 4 states the general shape — a new stage must know which
of the two kinds of map it owns.
