## Why the load had to become addressed, and not "seed whoever is open"

Both handlers were written for one caller and encoded that in a guard:

```go
if !m.nsPicker.Active() { return m, nil }
```

The obvious way to let the palette wait for the same load is to widen the guard — seed the
palette if the palette is open, the picker if the picker is. It works for every sequence a
test would naturally write, and it is wrong for one a reader will produce within a day:
open `ctrl+n`, change your mind, `esc`, hit `:` and commit `context`. The namespace list
lands into a palette that is on the *context* stage, and the rows it paints resolve through
`ctxByLabel` — a namespace row that means nothing, or worse, means whatever the map's
entry for that string is.

So the surface asking is recorded when the load is *issued*, and the handler routes on it
(D199 pt 1). That leaves the wart the old guard existed for — a list arriving after its
surface is gone — which is now expressed positively as `awaitingPaletteArg`: open, and
still on this verb. Both conditions are needed and the second is the interesting one, since
esc and backspace both rewind the line without closing the box (D198 pt 5), so "the palette
is open" is not the same question as "the palette still wants namespaces".

## The stage opens before its values exist, and that is the point

`enterPaletteArg` could have waited: issue the load, keep the palette on its verb list, and
enter the stage when the values land. That is one fewer state to render and it makes the
line feel broken on any cluster that takes 300 ms to answer — you press space and nothing
happens, so you press it again. The stage therefore opens instantly, and what is *not*
instant is the list inside it.

Which forces the two rules the render check was for. The prompt has already advanced to
`:namespace `, so the box has to distinguish "no namespaces" from "not yet": the title
carries it (`Switch namespace — loading…`, dropped by `fillPaletteArg`). And the query is
live from the first frame, so typing `sys` before the answer arrives must survive it —
`SetItems` applies the standing query, which is the same property PAL-03a had to *defeat*
with `ClearQuery` when swapping a verb's list. Same mechanism, opposite intent: clear when
the query belonged to the previous stage, keep when it belongs to this one.

Inertness stays a synchronous decision (D199 pt 3). `m.nsLister == nil` is knowable before
the stage opens, so a wire-less build declines the verb outright rather than opening a stage
that waits forever — the case a purely async design would have gotten wrong by construction.

## What was extracted, and the one thing it fixed on the way

D198 pt 2 makes extracting the verb's apply *part of* adding an argument verb, so:

- `handleNamespaceSelected` was hiding `applyNamespaceValue` (sentinel → empty scope,
  `setNamespace`, persist, re-select the current resource). Both surfaces now call it, which
  also means the `all namespaces` sentinel could not be forgotten in the palette — the
  one-way-door regression dogfood-09 already paid for once. `namespaceItems` is the shared
  row builder for the same reason.
- `handleContextSelected` was hiding `applyContextLabel` (label → name → `switchContext`).
  Its rows are `contextPickerItems`' rows, so the palette marks the context you are on and
  qualifies duplicated cluster names exactly as `C` does, from one function.

Extraction found one live edge: the palette's context stage sets `ctxByLabel`, so a stage
abandoned mid-flight could leave a stale map that resolves a row the *new* stage never
listed. `enterPaletteArg` clears it on entry, alongside the existing clear in
`openContextPicker`.

## Two things noticed, left alone deliberately

- **The empty list still renders bubbles' "No items."** underneath the `— loading…` title,
  so the box says two things at once for the moment the list is in flight. It is the
  picker component's generic empty rendering — every picker has shown it during its load
  since M2-08, the standalone namespace picker included, with no title to soften it — so
  the palette is strictly ahead here, and changing it is a picker-level change (an empty-
  state string the embedder sets) rather than a rider on this leg.
- **The hint bar still lies while a picker is open** — PAL-02 and PAL-03a both flagged it,
  and it is still the same leg-sized fix (a picker `HelpContext`, the D143 pt 1 shape).
  This leg adds a third undiscoverable gesture to the palette's line (the loading wait is
  not a gesture, but `space`/`backspace` remain unadvertised), so the case keeps growing.
  Worth doing before PAL-05 hands the palette the shortcut keys' whole job.
