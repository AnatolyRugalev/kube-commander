- **The quit path and the switch path had to become one list, and that is most of the
  leg's value.** Quit already cancelled the watch, discovery, the log stream, the search
  fan-out, a drain and the forwards — written out inline in the `ActionQuit` case. A
  switch needs *exactly* that list, so writing it twice guarantees they drift, and the
  drift is asymmetric in the worst way: a teardown missing from quit is invisible (the
  process is exiting), the same gap in a switch leaves a goroutine talking to the cluster
  the user just left. `stopClusterAsync` is now the single inventory and quit is three
  lines shorter. `TestStopClusterAsyncLeavesNoCancelBehind` walks the Model's
  `context.CancelFunc` fields by reflection and fails on any left set, so a *new*
  per-cluster cancel is covered without anyone remembering to extend the test (the
  M4-02 `TestNewClusterWiresEverySeam` trick, applied to the other end of the lifecycle).
- **Cancelling is not the same as "will not deliver", and discovery is where that bites.**
  `kube.StartDiscovery` selects between a cap-1 send and `ctx.Done()` (D8), so a pass
  cancelled by a reset can still win the race and deliver — and `handleDiscovery` would
  then `menu.Reconcile` the *old* cluster's API surface into the new context's menu. That
  is the D155 pt 1 bug class exactly, just via the menu instead of the table, and no gen
  guard existed for it: `watchGen`/`searchGen`/`viewerGen`/`drainGen` all did, discovery
  did not. Added `discoveryGen`, tagged onto `DiscoveryReadyMsg` as an **unexported**
  field so the zero value is generation 0 (the launch pass) and every existing test that
  constructs the message by hand keeps working unchanged. `discoveryPump` now takes the
  generation. D156 pt 2.
- **The reset clears the namespace, deliberately, and that is a handoff not an omission.**
  "Pre-drill-in" is taken literally: the `-n` launch scope and discovery's menu additions
  both describe the cluster being left, so both go. That means after a reset there is no
  namespace to inherit — which is the correct shape, because M4-05 has to *resolve* the
  new context's last-used namespace anyway (D90/D91) and inheriting the previous
  cluster's would be the specific bug M4-05 exists to prevent. Recorded as D156's
  corollary so M4-05 does not read the cleared field as a regression.
- **What is deliberately left alone:** the context name (M4-04 sets it when it knows the
  new one), the menu extras + namespace persister (M4-05, both need the new context to
  resolve against), the keymap/help overlay/mouse+menu toggles (not cluster data), and
  the status bar's context segment. The stashes that *are* cleared (delete/mutate/drain/
  container/port/secret/search targets) are only read while their surface is up and all
  of those are now down — cleared anyway because a stale `ObjectRef` surviving a switch is
  precisely what a later leg would resolve against the wrong cluster.
