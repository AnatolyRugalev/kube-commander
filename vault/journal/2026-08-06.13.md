## Backspace was routed to the field on purpose, which is why nothing was obviously wrong

D73's split is stated in three route functions in almost identical words: a mapped key
carrying no text is a control action, "any text-producing or **editing** key (a rune, or an
unmapped no-text key like backspace) is filter input fed to the field". Backspace is named
explicitly, as the example. So the reported behaviour is not a gap someone forgot to fill —
it is the rule working exactly as written, and the rule is right about every backspace but
one.

That is worth being precise about, because the tempting fix is to special-case backspace out
of the text arm, which would break the common case. The claim D238 pt 1 makes instead is
narrower: backspace *is* editing, and this leg does not change that; what changed is the
recognition that an edit needs something to edit. A delete against an empty line is a request
the field cannot serve, and a request no one can serve is where the router gets to decide
what it meant. So the predicate reads `m.filterInput.Value()`, not a "has the reader typed"
flag — a `/` reopened on a committed query (`openFilter` seeds it, deliberately) has three
characters in the line and therefore costs three backspaces before the fourth cancels. The
line is the only thing the reader can see, so the line is the only thing that may decide.

## Resolving to nav.back instead of writing a cancel

The direct implementation is two lines: call `m.clearFilter()` in one router and
`m.logsView` something in the other. I wrote `return m.handleFilterAction(keymap.ActionBack)`
instead, and the reason is not tidiness.

Both surfaces already have an unwind ladder and both ladders have a documented shape. The
table filter's esc "clears the filter, restoring every row — and closes it", and it is the
same call whether the field is open or the filter was committed. The logs view's is two
rungs: "one esc clears an open filter (restoring the full stream); a second closes the view
— the filter must never be lost by the same key that dismisses". A cancel written beside
those is a second definition of cancel, and second definitions drift: the next leg that
changes what esc does on either surface would have to know to change this too, and nothing
would fail if it didn't.

Routing through the action means there is one definition and backspace joins it at whatever
rung the reader is standing on. In the logs view that is also what makes the dangerous case
impossible rather than merely avoided: `routeLogsFilterKey` is reached **only** while
`logsView.Filtering()` is true (app.go checks it before the route), so `ActionBack` there can
only take the first rung. Backspace cannot dismiss the view, not because I wrote a guard, but
because the code path does not exist. `TestLogsGrepBackspaceOnEmptyQueryCancels` asserts
`Active()` anyway, since the interesting failure of this leg was never "nothing happened".

## Why the check goes after the keymap and not before

Order decides who wins if a user binds backspace to an action in `config.yaml`. Putting the
cancel first would make it unbindable — quietly, on exactly two surfaces, while the same key
kept working everywhere else. That is the worst kind of exception because the config file
still says what the reader wrote.

After the keymap, a bound backspace fires its action and the reader has traded the cancel for
it consciously, which is what binding a key means. The cost is that the default cancel exists
only because backspace is unbound by default, and that is fine — it is the same reason the
table filter's `q` types a `q`. D238 pt 3 states the ordering as a constraint because the
next `/` surface will copy one of these two routers, and copying it into the wrong position
would be invisible in review.

## What the frame assertion caught that a flag assertion would not have

The first version of the headline test checked `m.filtering == false` and the row count, and
passed. Then I tried to assert the status bar's `/query` indicator was gone by looking for
`"/ "` in the rendered frame, and it failed — because the hint bar at the bottom carries
`/ Filter / search`, permanently, as a hint. That is a false alarm, but it made the point
that the substring was the wrong instrument.

Comparing the entire frame to the one captured before the `/` is the right one, and it is
also literally what the feedback asked for: "return to the normal view". It covers the
prompt, the status bar segment, the hint context (`syncHints` re-picks it when filtering
changes) and the pane focus in one comparison, and it would fail on any of them being left
behind — including ones I did not think to check. Round-tripping a frame is cheap here
because the model is a value and the view is a pure function of it, which is principle 1
paying out in the test suite rather than in the UI.

## The README had no `/` paragraph at all

Documenting the new gesture meant finding where the table filter is described, and it isn't.
`/` appears in the README four times before this leg: as the port picker's opt-in filter, as
the logs view's grep, and twice in passing inside the cluster-search section ("`/` remains
the filter that narrows the rows of the table already open"). The most-used search key in the
app was documented only as a contrast to the one that is bound to `Ctrl+s`.

So this leg wrote the paragraph — `/` narrows live, `Enter` commits so `n`/`N` step the
matches, `Esc` clears, backspace past the start cancels — and placed it immediately before
the cluster-search section, which now reads as the widening it always meant to be. That is
the D68 obligation working as intended: the leg that changes how a key behaves is the leg
that has to go and read what the README claims about it, and sometimes the finding is that it
claimed nothing.
