- Did: Split SEARCH-04c-2 into **04c-2a** (rank) and **04c-2b** (fuzzy) and took the
  first. `kube.Search` now scores every match (`SearchHit.Score`) by *where* the query
  lands in the name, and `searchview` keeps its results in score order, inserting each
  streamed hit at its rank with the cursor carried along. Matching itself is unchanged —
  the same result set, ordered. → D152.

- **The split order is the whole point of the leg.** The board had fuzzy matching as one
  item and flagged the ordering question as "decide that first". Decided, and the answer
  reorders the work: doing fuzzy before ranking is a *regression*, not an increment. A
  subsequence matcher over an arrival-ordered list takes the exact match the reader wanted
  and buries it among scattered coincidences, at a random depth that depends on which kind
  happened to return first. Ranking first makes fuzzy additive — the noise it admits can
  only land below every exact match — so 04c-2b is now a matcher change with nowhere bad
  to put its output.

- **Ranking belongs to the view because kube streams.** The tempting place for a sort is
  the producer, and it cannot go there: `kube.Search` has no last hit to sort against until
  the whole fan-out is over, which over a hundred-kind widened sweep is seconds of blank
  screen. That would trade away exactly what SEARCH-02/03 built (hits on screen while the
  sweep runs, `searching N/M kinds…` against them). So the producer ranks and the consumer
  orders — D152 pt 1 — and the score rides on the hit as the join between them.

- **The cursor is the thing that makes a re-ordering list usable.** `AppendHit` used to
  append and re-select the same *index*, which was trivially correct because the row under
  the cursor never moved. Now rows above it do move, so the index is re-derived: an insert
  at or above the cursor shifts it by one, so the selection stays on its object. Without
  that, a hit arriving in the moment between "stop moving" and "press enter" silently
  changes which object drills in — a wrong-object action, and on this app the actions are
  destructive. Both directions are tested (better hit above, worse hit below), plus the
  first-hit case where the shift must *not* apply or index 0 would run away from the only
  row there is.

- **Score shape.** Position dominates: prefix (`api-server`) > after a separator
  (`my-api`) > buried in a word (`legacyapi`); ties break on an earlier match and a tighter
  name, both clamped. The clamps are not cosmetic — they are what keeps the substring band
  from being eaten by a long name, which is the invariant 04c-2b's fuzzy band depends on,
  and there is a test asserting the worst possible substring score still sits above the
  band floor. The best occurrence in a name wins rather than the first, so `xapiy-api-0`
  scores as the good match it visibly is.

- Test caught a real regression I introduced: folding the old `name == ""` guard into the
  matcher put it *after* the empty-needle short-circuit, so a label-only query started
  matching unnamed rows. The existing `TestSearchEmptyQueryMatchesAllNamedRows` failed on
  it. The guard is now first, with a comment saying why it stays there, and the new
  empty-needle test asserts it too.
- Decisions: D152 — stream stays in arrival order, the view ranks; a score is an ordering
  not a measurement; match bands are ordered by match kind first; a list that re-sorts
  under a live cursor carries the selection with its row.
