# 2026-07-29 — LOGS-05b: kill the per-line render cost in the logs view

- Agent: claude-opus (do-rewrite-leg)
- Milestone: M3 (LOGS line, feedback-driven)
- Did: Second and last slice of feedback `2026-07-29-logs-tail-and-perf`. The logs view
  re-scanned and re-joined its whole buffer on **every** appended line, so a followed
  stream got steadily slower as it ran. Both halves the board named are in: the rendered
  body is now a cache (`shownLines`) that an append extends and only a reader gesture
  rebuilds, and `logPump` blocks for the first event then drains whatever is already
  buffered in the 256-deep log channel into one `LogLineMsg`, so a burst is one render
  instead of hundreds. Behaviour is byte-identical — the grep still narrows live while
  following, highlights and timestamps unchanged.
- Decisions: D162 — a streamed view's cost is the number of viewport syncs, so the body is
  a cache both paths render through the same `renderLine` (no drift), the pump batches,
  and a batching pump carries the stream's end in `LogLineMsg.End` rather than dropping a
  receive it cannot put back (lines first, terminal event second — order is load-bearing
  for D74's degrade).

## What the numbers say

`BenchmarkStreamLines*` (new, hermetic — the part of the throughput question the sandbox
*can* answer: not "does it feel fast", but whether a line's cost grows with the buffer):

| streaming 1000 / 4000 lines | before | after |
| --- | --- | --- |
| one line per viewport sync | 131 ms / 2002 ms | 111 ms / 1652 ms |
| batches of 256 (what the pump now produces) | — | **2.3 ms / 14.6 ms** |

So the 1000-line open LOGS-05a introduced went from ~131 ms of render work to ~2 ms.

The headline finding is that **the cache was the smaller half** (131→111 ms). The real cost
was never our join — it is `viewport.SetContentLines`, which re-measures every line it
holds (`ansi.StringWidth` per line) to find the longest, and the bubbles viewport has no
append API. That is why one-sync-per-line stays superlinear in the table above no matter
what we cache, and why the batching pump is what actually fixed this. D162 pt 2 records it
as a constraint for the next streaming surface: sync once per batch, never once per item.

## Notes for whoever picks this up next

- The residual: an append that *does* arrive alone still costs O(buffer) inside the
  viewport. Under load the drain hides it (the producer fills the channel and batches get
  large); at a trickle the absolute cost is small. It only becomes interesting again for a
  view left following for a very long time, where the buffer grows without bound — a
  buffer cap would be the answer, and nobody has asked for one, so it is not filed.
- `SetContentLines` **takes ownership** of the slice it is given (it rewrites embedded
  line endings in place and splits them out), which is why `syncContent` clones. That is
  a live trap for anyone reusing the pattern; it is in D162 pt 5.
- The batch/rebuild drift risk is the one real correctness hazard here and is pinned by
  `TestIncrementalAppendMatchesAFullRebuild`, which streams under every filter/mode
  combination and compares the cache against a full rebuild of the same buffer.
- The `2026-07-25-logs-view-throughput-dogfood` human-task is still open and is now worth
  re-running: it predicted exactly this quadratic, and the eyes-on half ("does it keep up
  on a real busy pod") is still the half only a human can answer.
