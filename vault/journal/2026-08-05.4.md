## The footer is the only body copy in kubecom, and D218 pt 2 is why it stays

HINT-03 considered deleting the footer and decided not to: the hint line one row below names
`nav.drillIn` under its **global** description ("Open / drill into selection"), which in the
panel means *stop the selected forward*. Deleting the footer would trade a rebind bug for a
worse one — a surface whose only verb copy says "open" where the key stops something. So the
footer stays, and the fix is the split D219 records: verbs local, keys generated.

That split is not a compromise, it is where the two sources of truth actually are. The verb
is a fact about `handleForwardsPanelAction` — this surface's `enter` stops. The key is a fact
about the user's config. Writing both in one string fused a fact the code owns to a fact the
user owns, and the user's half went stale the moment they rebound anything.

## Reusing `firstKey` rather than `Binding().Help().Key`

Two ways to render a key were available. `Keymap.Binding(a).Help().Key` joins every bound
token with `/` (`j/down`), which is what the hint line one row below shows; `firstKey(km, a)`
takes the primary token only, which is what `portPickerTitle` shows.

I took `firstKey`, for the same reason the port picker title does: this is a footer inside a
bordered box that clamps to 64 columns and `MaxWidth`-truncates, and a user with three keys on
`nav.back` would push the last entry off the end — silently, since truncation is not an error.
The line's job is to teach one way to do each thing, not to enumerate. The hint line, which
elides on width by design, is the surface that enumerates.

`firstKey` returning `""` for an unbound action also gave the disabled case for free, which is
D219 pt 2: a verb with no key is a promise the reader cannot act on. Rendering nothing is
worse-looking and more honest, and it is what the port picker title already does.

## What the mutation showed, and one thing it also showed

Reinstating the literal fails both new tests, so they are load-bearing. The rebind assertion is
the one that matters — it reads the *rendered panel* after `forwards.stopAll` moved to `Z`, and
the literal version keeps saying `X: stop all` while `X` does nothing.

Reading that failure's rendered dump turned up something worth writing down for the next agent,
because it looks like a bug and is not: the hint line under the panel showed the **browse table**
set, not `HelpForwards`. The cause is the test's shortcut, not the product — `refreshHints` runs
at the tail of `Update`, and the test opens the panel by calling `m.handleAction(ActionForwards)`
directly, which never passes through `Update`. HINT-01…03's tests all press a real key
(`hint_test.go`) and see the right context. So: any assertion about the hint line must go
through a keypress; `handleAction` is fine for everything else, and the panel-body assertions
here are unaffected because `View` reads the model rather than the cached hint.
