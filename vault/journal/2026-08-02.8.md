## Why this leg was the finding half and not the pinning half

CRD-PIN-04 was one board line holding two surfaces: "a surface that lists every discovered
kind" and "decide whether a kind can be pinned *from* the picker". The second is blocked on
a key: every picker filters as you type (D194), so `*` in one types a `*`, and the answer is
either a `ctrl+…` chord or a palette verb — a decision that wants to be made beside PAL-04,
which is building row-scoped verbs into the same palette. Doing it here would spend the
choice early and probably twice. So the line was split on pickup (the board's own notes
invite it) and this leg took the half that is unblocked and is the premise: you cannot pin
from a picker you cannot find the kind in.

## What the picker listed today, which is what the board asked to check first

The board said "check what it lists today before building anything", and the check is worth
recording because the answer was not what the line's framing implied. `resourcePickerItems`
takes the **menu's** item list, and `Reconcile` appends every kind discovery finds — so the
picker does already list every discovered kind, and no re-plumbing to a discovery-sourced
snapshot was needed. The gaps were narrower and worse:

- **A Kind two groups share was unreachable.** The old loop deduped by title with a
  `continue` and the comment "a title collision would make the pick ambiguous — keep the
  first". That is true about the *pick* and false about the *listing*: the second kind was
  not disambiguated, it was deleted. On a cluster with cert-manager and Cluster API, or CNPG
  and Cluster API, one of the two `Cluster`s simply could not be switched to from the picker
  or the palette at all.
- **Only the Kind matched.** The labels are singular Kinds; `NameMatcher` needs the needle
  to be a substring or a subsequence of the hay, and `externalsecrets` is *longer* than
  `ExternalSecret` — it cannot match by construction. So the name printed in every kubectl
  command the reader has ever run found nothing, with no feedback but an empty box.

Both are today-bugs on a CRD-heavy cluster, which is the cluster the feedback came from.

## Why aliases are a picker concept and not a resource-picker string trick

The obvious fix is to bake the extra names into the label — `ExternalSecret (externalsecrets,
es)`. It needs no new API and it is wrong twice: the modal is 60 columns at most, so the row
becomes noise for every reader who already knew the Kind; and the label is the **identity**
a `SelectedMsg` is resolved by (`resByLabel`, `themeByLabel`, `ctxByLabel` all key on the
string that comes back), so every character added to a label is added to a lookup key and to
the value the palette's argument stage round-trips.

So `Item{Label, Aliases}` lives in the picker, beside the matcher that consumes it, and the
label stays exactly what it was. `SetItems([]string)` is unchanged and now delegates through
`Labels()`, so the seven other pickers did not move; only the two surfaces that list kinds
pass Items. Both setters land in `SetItemsWithAliases`, which means a reseed **replaces**
the alias set — the palette swaps its item set in place when a verb is committed, and an
alias surviving that swap would match against a list no longer on screen.

Scoring is the best of label and aliases, with no penalty. The alternative (rank alias hits
below label hits) sounds conservative and gets `es` wrong: `ExternalSecret`'s short name is
an exact, whole-needle hit, while `Secret` matches `es` only as a scattered subsequence, and
the whole point of D194 pt 1's ordering is that exactness wins. A name the server itself
advertises is not a second-class name.

## The collision rule, and why it qualifies both rows

Qualification is applied to **every row sharing an ambiguous title**, not to "the duplicate".
There is no duplicate: two kinds, two groups, and marking only the later one would leave the
reader guessing which unlabelled `Cluster` was which. It also has to be a two-pass build —
the first pass counts titles, the second labels — because whether a row is ambiguous is not
knowable when that row is reached.

The bare Kind survives everywhere else, deliberately: `Pod` does not become `Pod (core)`
because one operator installed a CRD. Qualification is a response to an actual collision, so
the names muscle memory is built on only change when they genuinely stopped being names.

The dedupe did not disappear entirely — same Kind *and* same group (two served versions)
still keeps the first, since the group does not separate them either. That is rarer and its
own question (which version should a picker offer?), and it is not this leg's.

## Two things noticed, left alone deliberately

- **The menu still renders colliding Kinds identically.** Two `Cluster` rows, no group,
  nothing to tell them apart — the same defect this leg fixed one surface up. The menu's row
  is narrower than the picker's and its titles are also the authored file's business
  (D193 pt 3), so the same qualifier may not fit or may fight a hand-written `title:`. Worth
  its own item if a dogfood hits it.
- **The hint bar still lies while a picker is open** — flagged by PAL-02, PAL-03a, PAL-03b
  and CRD-01 now, and still the same leg-sized fix (a picker `HelpContext`, the D143 pt 1
  shape). Still worth doing before PAL-05.
