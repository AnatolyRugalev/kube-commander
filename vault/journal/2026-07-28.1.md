# 2026-07-28 — LOGS-04a: wrap toggle + horizontal scroll in the logs view

- Agent: claude-opus-5
- Milestone: M3
- Did: Split the three-in-one LOGS-04 item D52-style into **04a** (long lines), **04b**
  (timestamps) and **04c** (jump-to-latest), and took the first. The logs view now has
  two ways to read a line wider than the screen: `logs.wrap` (`w`) folds it onto
  continuation rows, and with wrapping off `nav.left`/`nav.right` walk the clipped view
  sideways to the tail. The header names both states — `[wrap]`, and `[+N]` for the
  columns hidden to the left. → D146.
- **The viewport already does both**, which is what kept this leg small: bubbles' viewport
  has `SoftWrap` and an x-offset with `ScrollLeft`/`ScrollRight`, and it *ignores* the
  offset while soft-wrapping. That last detail is the whole design. The two features are
  mutually exclusive by construction, so they are one toggle rather than two settings —
  and enabling wrap has to zero the offset **before** flipping the mode, because
  `SetXOffset` is a no-op once `SoftWrap` is on and a stale offset would silently reappear
  the moment wrapping was switched back off, scrolling a view the reader never scrolled.
  That is the one behaviour with a test of its own.
- Three smaller choices. (1) **Clipping stays the default.** In a streaming view one log
  line staying one screen row is what makes the rows on screen count *lines*; a burst of
  wrapped stack traces would otherwise push the rest of the stream off the display.
  Wrapping is for reading one long line, not for resting in. (2) **Horizontal scroll does
  not pause following**, unlike an upward scroll: moving sideways says nothing about
  whether the reader still wants the newest line. (3) **The offset clamps when the content
  narrows** — the grep can hide the very line that made the buffer wide, and an offset
  that outlives its content leaves the reader staring at blank rows. `render()` re-sets
  the current offset, which is how you ask the viewport to clamp; it is O(1) and the
  unfiltered path gained no per-line work (the standing throughput human-task).
- The hint bar forced the sharper call. `w` is a plain letter, so the open grep types it —
  it is hinted only in the grep-closed context, exactly as `f` is. Horizontal scroll is
  worse: it rides the shared `nav.left`/`nav.right` and acts only while *not* wrapping, so
  a hint for it would be right half the time. D143 pt 1 says a hint entry is a promise, so
  it is hinted in **neither** context and lives in `?` and the generated doc instead. The
  eighth entry also pushed the logs hint past the test's 220-column terminal, which is a
  real signal about how full that context is getting: wrap sits after follow so the less
  essential of the two is the one that elides first.
- Two small honesty fixes on the way past: `nav.left`/`nav.right` were described as "Focus
  left pane / collapse" and "…/ expand", but collapse/expand died with the group-open menu
  (D81) and both keys have scrolled the table horizontally since D60 — they now read
  "…/ scroll left|right". And `vault/knowledge/keybindings.md` never got the LOGS-03 regex
  toggle, so it gained that row alongside the new wrap one.
- Decisions: D146 — a streaming pager clips by default and wrapping is opt-in; wrap and
  horizontal offset are one toggle (wrap owns the offset and zeroes it first); a
  mode-dependent binding is not hinted; display state the reader can lose sight of is named
  in the header.
