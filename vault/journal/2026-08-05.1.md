## The offer is the only modal no keypress opens

Every other confirm in kubecom answers a gesture: `d` asks before deleting, `s` asks for a
replica count. This one appears because a subprocess kubecom started came back with an answer,
which makes it the first surface here that can interrupt. That is the whole reason D216 exists
and why most of the leg is refusals rather than behaviour.

The one that is a correctness bug rather than politeness: `View` composites a modal **only**
over the browse body — `searchView` and `logsView` win the switch outright, and the overlay
cases are a single `switch`, one surface at a time. An offer opened while the logs view is
full-screen would therefore be invisible *and* absolute: `handleAction` gives the modal
priority over everything, so every key would be swallowed by a box nobody can see, and the
reader's only way out is `q`. `overlayActive()` — the predicate the mouse handlers already use
for "something is capturing input" — is exactly the right gate, and it covers the filter field
too, which a hand-written list of surfaces would have missed.

It does not queue. A deferred offer would fire on the reader's next `esc`, minutes later,
about a failure they have moved on from — and the thing that re-arms it is reopening the
resource, which is a gesture, not a wait.

## The notice tracks the offer, not the diagnosis

AUTH-04a's pane ends with "Run this in another terminal, then reopen the resource:" over the
command. With a prompt on screen offering to run it, that sentence is the pane contradicting
the modal, so `authFailure` grew an `offered` flag rather than a second renderer — one line
differs, and both readings must stay in one place or they drift.

The subtlety is the other edge. An offer is answered in a keystroke, and the sentence that was
true while it was open ("kubecom is asking…") is false the instant it closes: the pane would
be promising a prompt that no longer exists, which is the same class of lie the file's own
rules open with. So both texts are rendered when the offer opens and the shell swaps them back
on **either** answer — accept included, since a login that fails leaves the pane up.

Restoring is guarded by an equality check rather than done unconditionally, because "later" is
not a short window here: the watch loop keeps retrying and rewriting the notice, and the reader
can sit on the prompt as long as they like. If the pane is now explaining something else, the
old text stays retired. Storing the two rendered strings rather than the report is deliberate
for the same reason — re-rendering at answer time would re-read a report that by then describes
a failure the reader may have left behind.

## `authDiagMsg` carries the resource, and that is not tidying

The message used to carry the kind as a string, which was all the renderer needed. An offer
needs the whole `kube.Resource`, because the approval it arms is what `runReauth` retries.

The obvious shortcut — read `m.current` when the message lands, since the generation guard has
already proved the pane has not moved — is wrong on exactly the path that matters most.
`watchResource` assigns `m.current` only *after* `Watch` returns without error; on the failure
path it still names the resource the reader came from. That path is the one with no retry loop
behind it, so it is the one whose offer is the reader's only way back. Carrying the resource in
the message costs a field and removes the question.

## What the confirm box can and cannot say

`modal.View` renders its message through `Width(iw).MaxWidth(iw)` at a box clamped to sixty
cells, so the text wraps but a single long token is cut. A profile name long enough to push
`aws sso login --profile …` past the width would therefore be truncated **in the question** —
and D195 pt 4 asks the prompt to name the exact command.

Widening or wrapping the modal is a component change with every other confirm as a caller, so
this leg did the cheap honest thing instead: the pane behind the box keeps quoting the command
in full (it wraps properly), which is why `remediationLead` still prints it in the `offered`
case rather than deferring to the prompt. The dogfood task asks whether that reads acceptably;
if it does not, the fix is `modal` learning to wrap, as its own leg.
