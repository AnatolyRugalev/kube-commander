## Why the guards, and why they are not optional

A demo GIF is the one piece of documentation nothing can read back. It tells the first
visitor "press `L` for logs" in a format no test can parse, and it keeps telling them that
after a rebinding, because a recorder **types** keys — it never checks that anything is bound
to them. This project already has the evidence: `master`'s GIF (`ci/terminalizer/` +
a GitHub CDN link) outlived the UI it filmed, and there is no mechanism by which it could
have failed.

So the tape is written to be checkable, and the checkable unit is the keypress:

```
# kubecom-action: res.logs
Type "L"
```

`TestScreencastTapeMatchesTheKeymap` reads every command line, maps it to the keymap token it
produces (`Type "L"`→`L`, `Escape`→`esc`, `Ctrl+D`→`ctrl+d`, `Enter`→`enter`), and requires
the token to be in `DefaultKeymap().Keys(action)`. Two design points are load-bearing:

- **An unannotated keypress fails.** Otherwise the guard degrades to whatever the tape author
  remembered to label, which is precisely the "the pass was never evidence" failure M5-05 hit
  one leg earlier. Plain text needs an escape hatch (`Type "kube-system"` is a filter query,
  not an action), so `# kubecom-input:` is that hatch — explicit, and visible in review as the
  thing to be suspicious of.
- **The annotation sits on the line above, not trailing the command.** Trailing comments may
  well be legal vhs; a separate comment line certainly is, and the guard's parser stays a
  five-line state machine rather than a lexer.

The third guard is about the README rather than the keymap. The board note for M5-09 said it
outright — *do not reference an image that does not exist* — and the symmetric failure is just
as real, so `TestScreencastAssetAndReadmeAgree` checks both directions: GIF without a link is
dead weight; link without a GIF is a broken image at the top of the project's front page. The
consequence is that the human task carries the exact markdown line to paste, because the
recording commit that omits it will fail `make check`.

## What "verified" means for a tape

`vhs validate` was worth the install. vhs is a Go program, so `go install …@latest` works in
the sandbox even though the image has no vhs — and `validate` parses a tape without a
terminal, a display or a cluster. That turns "the tape is probably syntactically valid" into
"vhs parsed it, exit 0", which is a materially different claim, and it caught nothing only
because the syntax was right; it would have caught a bad `Set` key or a malformed `Ctrl+`
chord instantly.

What it cannot do is record. vhs shells out to **ttyd** (the headless terminal) and **ffmpeg**
(the encoder); neither is in the image and neither is a Go tool. Even with both, every frame
of this GIF is live cluster data — a pod list, a log stream, a describe — so there is nothing
to film against a fake client. Those two facts, plus "does the pacing read well" being a
judgment call, are the three independent reasons the recording is a human task (D79), and
they are written into the task file so nobody re-derives them.

## The tour, and the two knobs it exposes

The tape opens Pods through the **resource palette** (`:` → `/` → `pods` → Enter) rather than
walking the menu with `j`. That is deliberate: menu position is cluster-dependent (discovery
reconciles the seed, kinds can be marked unavailable), so a fixed number of `j` presses is a
tour that silently opens the wrong kind on somebody else's cluster. The palette route is
position-independent *and* demonstrates a feature the README sells.

Two strings remain cluster-specific and are marked `TUNE` in the tape header: the table filter
(`kube-system`, chosen because every cluster has it) and the log grep (`info`). They are
called out so a re-record is a two-line edit rather than an archaeology exercise — and the
human task repeats the warning that the pod the tour lands on must actually log something, or
the grep demo films an empty screen.

`make screencast` builds `./bin/kubecom` and prepends it to `PATH` instead of relying on
`Require kubecom` finding whatever is installed. A GIF recorded from a months-old `go install`
would be a documentation bug with no possible test — the same class of problem as everything
else in this leg, and it costs one line of Makefile to make impossible.
