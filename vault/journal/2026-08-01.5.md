## Why the feedback needed triage, and what triage decided

The submitter flagged three things to settle before building, and each one moved the design:

1. **Is provider-specific auth a non-goal?** No — `goals.md`'s non-goals are Windows,
   cloning k9s, mutation beyond the curated set, and multi-cluster/server mode. But it is
   near enough the edge that D195 fixes the shape now rather than letting five slices each
   drift a little: offer, never run; substantiate from the kubeconfig, never guess; one
   table entry, not a provider framework.
2. **"Only offer what you can substantiate."** Honoured structurally: the profile comes from
   the stanza's own `--profile` arg or `AWS_PROFILE` env (AUTH-03), and when neither exists
   the remediation is simply not offered. `ExecPluginFor` returns the stanza verbatim so
   there is nothing to invent from.
3. **"Reuse the existing suspend."** Recorded as AUTH-05's constraint (the `$EDITOR`/exec
   suspend, D125) rather than left to the implementing leg to rediscover.

The submitter's fallback — "surface the plugin's own stderr legibly with the command *shown*
but not run" — turned out to be more than a fallback. It is **AUTH-04**, the first slice with
a screen surface, and it is where most of the value lands; AUTH-05 (actually running it) is
deliberately last and separable, so the line delivers even if the run half is never built.

## The finding that reshaped the line

The feedback assumed detection means "inspect the plugin's failure — its exit status and
stderr". Reading client-go v0.31 (`plugin/pkg/client/auth/exec/exec.go`) says otherwise, and
this is the leg's durable learning (now in `knowledge/stack.md`):

- **The stderr is not in the error.** `a.stderr` is wired to the process's `os.Stderr` at
  Authenticator construction with no seam to redirect it. So the AWS CLI's SSO-expiry
  sentence is written straight to the terminal — under the alt-screen, into a void — and the
  error the caller gets never carries it. Matching on it is therefore impossible from the
  failure alone, which is exactly what AUTH-02 exists to fix, by re-running the *kubeconfig's
  own* command as a diagnostic. That re-ordering (a whole extra slice before the AWS one) is
  the main way the built line differs from the feedback's sketch.
- **The wrap chain is broken.** `fmt.Errorf("getting credentials: %v", err)` — `%v`, so the
  `*exec.ExitError` is gone and no `errors.As` reaches it. `ExecPluginFailed` matches text
  because there is nothing else to match, and it matches only client-go's two named shapes
  (`exec: executable X not found`, `… failed with exit code N`), never its `exec: %v` default
  branch, which carries no executable name. Guessing there would be exactly the "wrong
  command is worse than no offer" failure the feedback warns about.
- **It fails inside `RoundTrip`.** net/http wraps the result in a `*url.Error`, which the
  taxonomy's transport net caught as `KindUnreachable` — kubecom has been telling users the
  cluster is unreachable when the cluster was never contacted. That misdiagnosis is a live
  bug fixed by this slice's classification (a user-visible improvement lands with AUTH-04,
  which renders the new kind).

`KindExecPlugin` is checked *after* the apierrors switch, so a 401 whose message happens to
quote a plugin stays `KindUnauthorized` — pinned by `TestClassifyStatusErrorWinsOverExecPluginText`.
