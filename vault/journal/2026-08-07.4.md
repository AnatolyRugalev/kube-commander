## The whole leg is one distinction, and the feedback made it for me

"A line cursor. `j`/`k` move a highlighted line, the same way they move a row in a table."
The cheap reading of that is a highlight painted on whatever row the viewport's scroll
happens to put under an index — and it would have passed every test I would have thought to
write, right up until someone turned `w` on.

The feedback closes that door in its own words: with wrapping on "the cursor and the
selection are over **log lines**, not screen rows, and a yank returns the line as it
arrived — unwrapped, no inserted breaks". That is not a refinement of the cursor, it is the
*reason there is a cursor*. The paragraph above it explains why terminal select-to-copy is
not good enough, and the complaint is exactly this: "on a wrapped line it copies the visual
rows rather than the log line — so a long entry comes back with breaks in it that were never
in the log". Building a row cursor would have reproduced the defect being complained about,
in the feature meant to fix it.

So `cursor` indexes `shownLines`, and the viewport is a consequence rather than the model.
Which is where the arithmetic comes in.

## `viewport.EnsureVisible` exists, and is wrong for this

bubbles' viewport has exactly the method this needs — `EnsureVisible(line, colstart, colend)`
— and it is unusable here, for a reason worth writing down because the next person will find
it too and it looks right:

```go
if line < m.YOffset() || line >= m.YOffset()+m.maxHeight() {
    m.SetYOffset(line)
}
```

`yOffset` is in **display rows**. `calculateLine` maps an offset to a real line index plus a
row offset within it, and does so by walking the buffer summing `ceil(width(line)/maxWidth)`
— so with `SoftWrap` off the two numbers coincide and with it on they diverge by the total
wrapped overflow above. `EnsureVisible` compares a content-line index against a row offset.
It is correct unwrapped and quietly wrong wrapped, which is the worst shape for a bug: the
default mode works, the opt-in mode is subtly off, and the symptom is "sometimes the bottom
of the line I'm on is cut off", which nobody files.

`cursorRow` does the sum itself and returns the line's height with it, so `showCursor` can
scroll by the exact deficit rather than jumping the cursor to the top of the pane. The
mutation that reverts it to `row = n` (MUT 4 below) passed every test I had written until I
added `TestCursorScrollsInRowsWhileWrapping` — six 3-row lines, walk to the fourth, assert
both its head and its tail are on screen and that the view scrolled the one row it owed.

The cost is an O(shown lines) walk per cursor move, and only in wrap mode. That is the same
order `rebuildShown` already pays on **every keystroke typed into the grep**, and cheaper per
line (an ANSI-aware width versus a regex match plus a string build), so it does not introduce
a class of cost this component did not already accept for reader gestures. It is never paid
on an append, which is the invariant LOGS-05b actually protects.

## Where the bar is painted decides what the yank can copy

`shownLines` is a *painted* cache — the LOGS-05b append path stores each kept line with its
Match escapes already wrapped around the matched spans — and the obvious place to put a
selection bar is into it, next to the highlighting that is already there.

That would have been two mistakes at once. The small one is that the cache is defined as
"what a full rebuild would produce" (`TestIncrementalAppendMatchesAFullRebuild` asserts
exactly that), so a cursor baked into it makes every `j` an invalidation of a structure built
to survive appends. The large one belongs to the *next* leg: the feedback's sharpest
requirement is "no styling in the clipboard … worth an explicit test; it is the kind of thing
that looks right on screen and only shows up once the text is pasted somewhere". If the only
thing a cursor position can reach is `shownLines`, then the shortest path from cursor to
clipboard runs through a painted string, and the yank is one `strings.Join` away from
shipping escape sequences into someone's paste buffer.

So the bar is derived in `syncContent`, on the clone that already goes to the viewport, and
`shownIdx` lands in the same leg to give the cursor a route to `lines[i]`. `shownIdx` is not
speculative scaffolding for a leg that hasn't happened: it is what makes the cursor survive a
filter change *now*, which is the difference between a cursor and a jitter. Type one
character into the grep and the shown set is rewritten under an index that meant something
about the old set; `rebuildShown` carries the anchor across as a buffer index and re-finds it
by binary search (`shownIdx` is ascending by construction), landing on the nearest still-shown
line at or after where the reader was.

## Selection wins over cell color, and does not win here

The table's rule is stated flatly — M4-06, `TestSelectionWinsOverCellColor` — and FILT-02
carved out precisely one exception three legs ago: the cursor row keeps its **match** marks,
because a match is not information about the row, it is the reason the row is on screen.

Everything in that argument is stronger in a logs grep than it was in a table. In the table
the escape hatch was "move off the row and the color is there"; here, moving off the line to
see why the line survived the query is not a thing anyone would do, and with a query active
*every* line on screen is there because it matched. So Selection is the base style the
unmatched runs paint with and Match keeps its own background on top — which needed no new
color decision, because `styles.Match`'s doc comment has said since M0 that it uses the Warn
hue "so a highlight is never confused with the cursor (the two can appear on the same line)".
It was written for this, for this component, before anyone asked.

Mechanically the change is the one FILT-02 made to `paintRow`: `highlight` takes what the
unmatched text is painted with. The difference is that the logs painter takes it as
`*lipgloss.Style` and `nil` means "leave it exactly as it streamed" — not a nicety, a
requirement. The plain path renders every buffered line, so a base style there would put two
escape sequences on every line the view holds, on the hot path this component has been
optimised around twice (D160, D162). One painter, and the fast path stays byte-identical to
what it produced before this leg.

## Four mutations, three of them caught first time

Green on the first run made me suspicious that some of these tests were asserting the code
rather than the behaviour, so I broke it four ways and re-ran:

1. Delete the `case m.following:` pin in `placeCursor` → 7 failures.
2. Drop the anchor re-find in `rebuildShown` → `TestCursorKeepsItsLogLineAcrossAFilterChange`.
3. Make `showCursor` a no-op → 3 failures, including `TestUpwardScrollPausesAndDoesNotYank`,
   which predates this leg — the pre-existing behaviour now rides on the new mechanism, and
   that is worth knowing.
4. Make `cursorRow` ignore wrapping → **passed**. That gap is what
   `TestCursorScrollsInRowsWhileWrapping` was written for, and it is the test I would not
   have written without doing this.

The one that mattered was the one that passed. The other three only confirmed tests I already
trusted; the fourth found that the leg's least obvious code — the only part where two
coordinate spaces meet — was the part with no coverage at all.
