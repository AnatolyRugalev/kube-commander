# 2026-07-23 — FB-gray-out-empty-types: dismiss "gray out empty resource types"

- Agent: claude-opus-4-8
- Milestone: M3 (feedback triage — no M3 exit criteria affected)
- Did: Triaged the soft/low feedback idea of graying left-menu resource kinds that
  have zero objects in the current view (distinct from the M2-05b "unavailable/denied"
  muting). Read the menu component (item-state model: cursor / active / unavailable /
  normal), the watch wiring in app.go (only the **one** active resource is ever
  watched; `handleWatchMsg`→`table.ApplyEvent`; namespace is `m.namespace`, re-scoped
  by the picker), and the table's authoritative unfiltered `full` set. **Decided to
  dismiss** (D119) rather than implement. The eager "count every type on every ns
  switch" version is explicitly forbidden (dozens of API calls/switch, rate-limit
  exposure, instantly-stale counts — fights lazy-list D8/principle 4). The cheap
  opportunistic variant (gray only already-opened-and-empty types, cached per
  `(GVR, ns)`, reusing the active watch's row count) is declined **for now** on
  cost/value: value is marginal and revisit-only (the user already saw the type was
  empty when they opened it; it re-keys/evaporates on each ns switch since only one
  type is watched), while it would add a namespace-keyed emptiness cache, per-`ApplyEvent`
  plumbing on the watch hot path, and a **third** always-on menu visual state that must
  read as distinct from the existing muted "unavailable" rows — a real-terminal UX
  judgment (D68/D79) disproportionate to a low/soft item. Deleted the feedback file in
  this leg's commit; door left open (only the opportunistic shape is acceptable if
  revisited, never the eager one). → D119.
- Decisions: D119 — menu never eagerly counts resource types (eager version forbidden);
  empty-type graying declined for now, with the acceptable future shape constrained
  (opportunistic-only, reuse the existing watch, key by `(GVR, ns)`, unknown ≠ empty,
  keep "empty" distinct from "unavailable").
