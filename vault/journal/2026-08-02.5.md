## The trap this leg exists to avoid, which is the same trap AUTH-01 hit

A conversion webhook that is down is not a client failure. The apiserver answers — with a
500 or a 503 saying it could not call the webhook — so `Classify` lands it somewhere that
reads as *"the API server could not be reached. Check your network."* That sentence sends
the reader to check a network that is fine, for a failure inside their cluster that breaks
`kubectl get` the same way. It is exactly the shape AUTH-01 was created for (a failed
`aws eks get-token` reading as "cluster unreachable"), one layer up: there the fix was a new
`ErrorKind`, here it is deliberately not.

`KindExecPlugin` earned a kind because *how the call failed* was genuinely different — no
request was ever sent. A conversion-webhook failure is an ordinary server error; what is
different is *what the cluster did*, and that is a fact about one response, not a category
of client failure. So it is `kube.ConversionWebhookFailed(err) bool` beside
`ExecPluginFailed`, and the copy layer asks the named causes first and the kind second
(D200 pt 3). Adding kinds for it would have meant every `switch` on `ErrorKind` in the app
growing arms for things that are not client errors.

Both predicates match narrowly. `conversion webhook for ` is apiextensions-apiserver's own
phrase and nothing else writes it; 406 is `apierrors.IsNotAcceptable`, checked and pinned to
stay `KindUnknown` so nobody "helpfully" teaches `Classify` to guess at it later.

## Why the notice is a field on the table and not a fake row set

The tempting implementation is to put the message *in* the table — one row, one column,
the text as its cell. It renders with no new code and it is wrong in three ways that only
show up later: the row is selectable and drillable (enter on "Cannot list ExternalSecret"
would emit a `RowSelectedMsg`), the filter would match it, and the sort would sort it.

So it is a separate field the View consults only when there are no rows. That also gives
the property that makes it safe to set from *any* failure path without a guard at the call
site: a watch that drops after a good List sets the notice, keeps its rows on screen, and
the notice waits dormant for the moment the rows go away. The call sites therefore say
`SetNotice(browseFailure(...))` unconditionally and the component decides whether it is
time to show it — the alternative (each caller asking "is the table empty?") is the same
decision made in two places, which is how they come to disagree.

The clear is the half that would rot silently. `SetTable` clears it, so one kind's failure
cannot linger over the next kind's pane, and a RESET clears it — including an **empty**
RESET, which is a List that succeeded and found nothing. That last case is the one worth
naming: keying the clear on "rows arrived" would leave a stale failure over a kind that
genuinely has no objects, and the pane would blame a webhook for an empty namespace.

## What the copy says, and the rules it follows

Three lines: `Cannot list ExternalSecret` / the reason / `Server: <what it said>`. The
kind is in the headline because a reader who walked away needs to know which pane they are
looking at. The server's text is quoted last, flattened to one paragraph (the table treats
each source line as its own wrapped block, so an embedded newline would read as a second,
unrelated detail) — it is the line a bug report needs, and DIAG-01's log file has it in
full when the pane clips it.

The rule underneath every sentence is **say where the fix is**: this machine
(re-authenticate, switch context) or the cluster (a webhook, RBAC). A reader who cannot
tell retries the wrong one, which is precisely what the original feedback did. And the
retry sentence — "kubecom keeps retrying" — is honest *here* only because the browse watch
loop really does re-List on a backoff; D200 pt 4 forbids copying it to a surface that has
no such loop.

The rendering deliberately does not scroll. The pane is not a viewer: it wraps, it fills
its height, and text past the last row is dropped with the headline first. A notice long
enough to be cut is a notice whose tail belongs in the log file.
