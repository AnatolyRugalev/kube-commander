## Why the fallback was the bug and is still the right behaviour

`ShortHelpContext` ends with `if !ok { actions = shortHelpActions }`, and there is a test
pinning it: `HelpContext(99)` returns the focus-agnostic set rather than nothing. That test is
right and stays. The mistake was that one line served two populations that need opposite
treatment.

An out-of-range integer is a caller's error, arrives at runtime, and has exactly one good
answer: render *something* the reader can use, since an empty hint line is a blank promise and
a panic is worse. A declared-but-uncurated context is an author's error, arrives at compile
time, and has exactly one good answer too — refuse to ship. Both were getting the first answer.

Separating them needed no change to the fallback at all, only a way to enumerate the declared
set. That is what `helpContextCount` buys, and it is why D223 pt 2 spells out that the two
failures are different: a future leg reading the fallback in isolation would reasonably
conclude the completeness question is already handled.

## The reachability half is the one that catches D218 pt 1's actual sentence

D218 pt 1 says "a new capturing surface with no case ships a plausible wrong hint". Note *no
case* — the missing thing is in `hintContext()`, in the root package, not in the keymap's map.
A completeness test over `contextShortHelpActions` alone would not have caught the bug as
written: an author who declares `HelpFoo` and curates its set, but forgets the arm in the
switch, has a green tree and a surface still showing the browse hint.

So the second test drives the model into each of the thirteen states through the real gestures
and asserts `hintContext()` returns the context it was reached by. The mutation is the proof:
replacing `case m.forwardsPanel:` with `case false:` — a plain deletion of the arm — leaves the
keymap test green and fails this one with `this state resolves to HelpTable, want
HelpForwards`. That is the bug D218 described, reproduced, and it is a *routing* failure as
much as a hint one: the same precedence list orders `handleAction`, so a shadowed hint arm is
a strong hint that keys are shadowed too. D223 pt 3 says so explicitly, because the cheap way
to make this test pass is to reorder the table, and that fixes nothing.

It is deliberately the only test in `hint_test.go` that must be edited when a context is added.
The per-context tests above it assert *which* keys each set offers — the interesting, curated
question — and none of them would notice a fourteenth surface. The table is the coverage.

## What was not built: an exhaustive-switch linter

`golangci-lint` ships `exhaustive`, which checks `switch` statements over enum-like types, and
the obvious move was to enable it and delete both tests. Three things ruled it out. The switch
in `hintContext` is a **tagless** `switch { case cond: }` over model state, not a switch on a
`HelpContext` value, so `exhaustive` cannot see it at all — it is the wrong shape for the very
place the bug lives. `contextShortHelpActions` is a map, and the linter's map-literal check
(`check: map`) would cover half of what the keymap test does but says nothing about a set that
resolves to fewer bindings than it lists (an action nothing binds), which is the other assertion
there. And enabling a new linter is a repo-wide gate change with its own diff across every
existing switch — a bigger, less reversible leg than the one this was.

The `[helpContextCount]string` array for `helpContextNames` is the one place the compiler does
help: it is sized by the sentinel, so a context declared past the array's bounds with a named
index would not compile. That is free and worth having, but it only covers names, not sets —
Go will happily leave an interior element as `""`, which is why the name check is in the test
too.
