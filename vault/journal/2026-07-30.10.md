## What was actually wrong

The leg found a real defect, and found it the way the board note predicted. `migrate_test.go`
asserted a legacy palette looked like this:

```yaml
themes:
  - name: dark
    colors:
      - name: bg
        rgb: "#000000"
```

The 2020 writer never emitted that. `theme.ColorToProto` stored
`fmt.Sprintf("%06x", c.Color.Hex())` — a **bare** hex string — and `ProtoToColor` prepended the
`#` itself on read (`tcell.GetColor("#" + t.Rgb)`). So a real file says `rgb: 002b36`, and the
2020 themes in `master:app/ui/theme/themes/*.go` confirm it at the source.

Nothing caught this for three milestones, and the reason is worth naming: **the migration
ignores the palette tree**, so a fixture can misdescribe the format it claims to be testing and
still pass. That is the general hazard of a fixture asserted from memory — it only fails when
the code reads the part you got wrong, and here the code deliberately reads none of it. The
test's *pass* was never evidence about the format. Which is precisely why M5-05's job was to
stop typing fixtures rather than to type a better one.

## Generating the fixture instead of writing it

`master:config/config.go` fixes the pipeline in five lines: `protojson.Marshal(config)` then
`yaml.JSONToYAML` then `WriteFile`. To reproduce it I copied `master:pb/config.pb.go` (the
generated 632-line descriptor) into a scratch module requiring `google.golang.org/protobuf` and
`sigs.k8s.io/yaml`, built a `pb.Config` mirroring what the app itself writes, and ran the two
calls. The output is committed unedited — no comments, no reordering — because the moment a
human touches it, it stops being what the writer produces.

Four shape facts fell out that are not obvious and are now D180 pt 1:

- **Keys are sorted alphabetically.** `yaml.JSONToYAML` goes JSON → `interface{}` →
  `yaml.Marshal`, and yaml.v2 orders map keys. So `currentTheme` precedes `menu` precedes
  `themes` at the top level, and inside a style `attrs`, `bg`, `fg`, `name`. Nobody would type
  a file that way, which is a decent tell for a hand-written fixture.
- **Zero values are absent.** protojson omits unpopulated fields by default, so a cluster-scoped
  menu entry has no `namespaced` key at all — its absence *is* `false`. Every existing test that
  wrote `namespaced: true` was accidentally right; one that wrote `namespaced: false` would have
  been describing a file that cannot exist.
- **`rgb` is a bare hex string; `xterm` is a bare number.** They are a protobuf `oneof`, so
  exactly one appears per color.
- **`attrs` holds enum names** (`UNDERLINE`, `REVERSE`), not integers — protojson's default.

The scratch module is not committed. D180 pt 2 says explicitly not to vendor the legacy `pb`
package to make regeneration convenient: D3/D14 deleted that codegen deliberately, and a test
fixture is not a reason to bring protobuf and a generated file back into a tree that currently
depends on neither. `testdata/README.md` carries the recipe instead — about eight lines of
instructions in place of a thousand lines of dependency.

## The guard that keeps the fixture honest

A generated fixture is only evidence while it stays generated, and nothing stops a future leg
from hand-patching it. So `TestLegacyFixtureCoversTheProtoSchema` parses field declarations out
of the committed proto and compares them with every mapping key in the YAML, **in both
directions**:

- a YAML key that is not a declared field → the fixture is not a real legacy file;
- a declared field that never appears in the YAML → that part of the legacy shape is untested.

The second half is the one I would not have thought to want, and it is the half that makes the
fixture a coverage statement rather than a sample. It currently forces all fifteen fields to be
exercised, including the ones the migration ignores.

Two details made it work. The regex matches `[repeated] <type> <name> = <n>;` and so naturally
excludes what should be excluded: enum values (`NONE = 0;`) have no type token, `option
go_package = "…";` has no numeric tag, and `oneof value {` has no `=` at all — correctly, since
`value` is a oneof name and never appears as a JSON key. And the comparison is name-for-name
only because protojson's JSON name equals the proto field name for every field in this schema
(all single-word except `currentTheme`, which is already lowerCamel); a snake_case field added
later would break that equality, so the test now *reports* a snake_case field rather than
silently comparing the wrong strings.

## Proving "parsed and ignored" rather than asserting it

The board asked for evidence that the lenient parse ignores the palette tree instead of failing
(principle 3). "It didn't error" is weak — it would also hold if the tree were silently
influencing the result. So the test proves it by difference: migrate the fixture, migrate the
fixture with the whole `themes:` block cut off, and require the two `Config` values to be
`DeepEqual`. The only thing that may differ is the note's palette caveat, and the test asserts
that too — present with the tree, absent without it.

It also asserts the fixture *still contains* palette detail (`rgb: 002b36`, `xterm: 240`,
`UNDERLINE`) before drawing any conclusion, so regenerating the fixture without palettes fails
loudly instead of turning the test into a tautology. Cutting at `themes:` is safe for a
non-obvious reason that is itself one of the shape facts above: sorted keys put `themes` last.

## Two things that were verified but produced no code

**The theme mapping now runs against the real shape.** D179's five 2020 built-ins
(`base16`/`monokai`/`paraiso`/`solarized`/`twilight`) were each covered by a one-line YAML
string; they are now each substituted into the full fixture, so the palette tree and the menu
are present while the mapping is exercised. `monokai` carries, `solarized` aliases,
the other three land on v1's default — same expectations, real input.

**Why the legacy `themes:` key means the user hand-wrote it.** Grepping master for
`UpdateConfig` shows only two writers: `resourceMenu.saveItems` (which sets `menu`) and
`theme/manager.NextTheme`/`PrevTheme` (which set `currentTheme`). Nothing ever wrote `themes`.
So a palette tree in a real file was authored by hand — which sharpens D179 pt 1 from "we can't
migrate palettes" to "the only user affected is one who deliberately wrote a palette, and what
they want is a v1 feature, not a migration". That is in the new human task, and the durable half
is in `vault/knowledge/legacy-architecture.md`, which had a one-line mention of the config
format and now describes the file.

## Why the exit criterion stays unticked

The criterion says "a **real** legacy config file". A file generated by the 2020 writer is
strong evidence about the format and no evidence at all about what a human accumulated over
months, so ticking it here would be exactly the D79 failure. Hence the human task — and its
most useful question is one the sandbox structurally cannot ask: a legacy file that fails to
parse degrades to *no migration, no config, no toast* by design (D92), which is
indistinguishable from having no legacy file. If the maintainer's real file trips that, only
they can see it. The task also says what to do if no legacy file survives: close it, and let
the criterion close on the fixture **while recording that it closed that way** rather than
ticking it silently.
