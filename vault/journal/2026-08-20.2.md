- Did: Folded in `2026-08-15-search-single-enter.md`, the S05 high-priority finding
  that reaching a hit in the cluster search costs two enters. STORY-06k split on
  pickup, smallest first: this slice is the enter collapse, 06k-2 is the result
  preview (its feedback file stays with it, D69). The cause was SEARCH-05's mode
  (D235): the first enter only moved focus from the query field to the result list,
  and only the second opened anything. **`nav.drillIn` now always opens the
  highlighted hit** — query line or list, and nothing at all with no hits — so one
  press reaches a result, and the top-ranked hit (already the highlighted row) is
  what a bare enter opens. The mode survives, because it is what makes `hjkl`,
  `g`/`G` and the page chords navigate; what changed is how it is entered: **every
  cursor action routes through a new `enterResults`** which hands the keyboard over
  on the first movement over the list and then performs the move. So the reader who
  presses ↓ to pick a different hit has already committed by doing it — the mode
  costs no keystroke of its own, needs nothing new in the hint (`HelpSearch` is
  unchanged), and the down arrow keeps meaning "down the list" exactly as it did.
  `enterResults` is inert with no hits, so focus never lands on a list with no rows,
  and `nav.back` is untouched — it is now the only action in this view that reads
  the focus. The component's `commit` test helper hands over with `nav.up` (nothing
  above the top hit, so the focus is the only thing that changes), which keeps every
  test that starts *on* the results asserting the same cursor as before; the same
  idiom updates the three app-level routing tests. README's cluster-search section
  names both gestures.
- Decisions: **D282** — in the cluster search `enter` opens a hit whatever the focus,
  a movement over the list is what commits into it, the hand-off refuses an empty
  list, and `nav.back` is unchanged. Supersedes D235's commit-then-open half.
