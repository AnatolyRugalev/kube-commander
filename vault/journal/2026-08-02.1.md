## Why this leg is a decision and a stopwatch, not an optimisation

The feedback asked for something real and asked for it carefully — it named the design it
was pushing against (M4-04a's teardown, D157's same-context no-op), named the risk
(a retained watch firing into a dead view is exactly the bug the teardown prevents),
proposed "warm but quiesced", and asked that the resolution be **recorded rather than
quietly made**. Two previous legs deferred it, correctly, on the submitter's own
instruction: finish the context-switch dogfood first so there is a known-good teardown
baseline. That instruction gates the *teardown change*. It does not gate deciding the
shape, and it does not gate measuring — so those are what this leg did, and the deferral
now has an end condition attached to it rather than being repeated a third time.

D196's load-bearing move is **where the retention lives**. The feedback framed the choice
as "keep the old cluster warm vs. tear it down", which reads as a change to the shell's
lifecycle and therefore as a weakening of the property the dogfood is about to check. It
does not have to be: `ClusterConnector` already outlives every switch by construction
(D155 pt 2) and the shell already treats it as a factory that hands back a `Cluster`. A
one-entry cache *inside* `cmd/kubecom`'s `contextConnector` makes `ConnectCluster` faster
while the shell continues to reset everything and hold exactly one cluster — the teardown
is untouched, the "nothing leaks" property is untouched, and there is no retained watch to
misfire because the shell owns every watch and cancels them all. That is the whole reason
the CTX-WARM slices can be written now without contradicting M4-03. A future leg that
instead teaches the shell to hold a second `Cluster` is contradicting D196, not
implementing it, which is precisely the kind of drift a `Dn` exists to make loud.

## The measurement is not a formality — the win may already be banked

Reading the connect path before writing the stopwatch turned up something that should
change how CTX-WARM-02/03 are approached, and it is why D196 pt 3 is a gate rather than a
note:

- **`kube.Connect` does no network I/O.** `RESTConfig` is a kubeconfig read;
  `NewClients` builds the clientset, dynamic client and cached discovery client, and its
  own doc says construction is local — connection errors surface later, on first request.
  The RESTMapper is a static seed ahead of a *deferred* discovery mapper (D8/M1-02), so it
  does not warm at construction either. Whatever a switch costs, "reconnecting" in the
  TCP/TLS sense is not obviously part of it.
- **Discovery is already cached on disk, per host, for 6 h** (`internal/kube/cache.go`,
  kubectl's own TTL). So a switch back inside a session re-reads files, not the API server.
  The remaining discovery cost is the walk plus the menu reconcile, not a round-trip.
- **client-go caches transports and credentials process-wide.** Two `rest.Config`s for the
  same cluster share a transport (and an exec-credential authenticator) out of client-go's
  own caches, so even the first request after a switch back is not starting from nothing.

Which means the honest prior is that the dominant cost of a switch back may be neither of
the two things the feedback proposed retaining — and building a retention cache on that
assumption could add a lifetime-management problem for a saving in the noise. Hence: log
the three numbers, get them from a real cluster, and let them decide. If `connect=` comes
back at a few hundred microseconds, CTX-WARM-02 should be *closed*, not built, and the
interesting number becomes `discovery=`.

## What is timed, and what deliberately is not

The stopwatch starts inside the connect Cmd (so it measures the off-loop work where it
actually happens, not when its message is delivered) and stops when the discovery pass that
switch started has reconciled the menu — the moment the new cluster is usable. Two
exclusions are deliberate:

- **The watch re-arm is not in the total.** It starts when the reader drills into a
  resource, so folding it in would be timing their reading speed, not the switch.
- **A launch-time discovery pass reports nothing.** The stopwatch is zero unless a switch
  set it, so the log stays silent until someone actually switches — a line that appeared
  when nobody switched would misrepresent what the number measures.

A superseded switch also never reports, and that falls out of the existing generation guard
(D156 pt 2) rather than needing a rule: the dropped connect message never reaches the code
that starts the stopwatch. `TestSupersededSwitchReportsOnlyTheSurvivingOne` pins it anyway,
because it is the kind of correctness that survives by accident until someone reorders the
handler.
