## What a live apiserver caught that eleven days of fakes did not

The two tests are deliberately different shapes, because the two halves of "a denied/broken
API group is isolated" fail differently.

**Denied** was the easy half and behaved exactly as designed: a user with `get/list/watch` on
pods and nothing else lists pods fine, gets a `KindForbidden` on secrets, and still receives
the *full* discovery result — secrets included. That last point is the interesting one and is
now pinned: discovery answers "what exists", not "what you may read", so the menu offers a
Secrets row that this user cannot open, and the failure arrives when they open it. Hiding
kinds by permission would need a `SelfSubjectAccessReview` per kind per namespace, which is
exactly the eager-per-type-count pattern D119 already rejected for a much cheaper feature.

**Broken** was the half that found the bug. The test registers an `APIService` for
`v1beta1.metrics.k8s.io` whose backing `kube-system/metrics-server` Service does not exist —
the metrics-server outage that blanked the 2020 menu (#87, #76) — and then asserts the pass
degrades to a partial result. The isolation half passed: `Err` nil, every healthy kind still
there, the resource count unchanged. The *reporting* half did not:

```
res.Failed = []      # on a cluster where metrics.k8s.io/v1beta1 is demonstrably broken
```

Chasing it down through client-go, with the control plane in front of me rather than a fake:

| call | result |
| --- | --- |
| `APIService` status | `Available=False  ServiceNotFound` — the cluster knows |
| `ServerGroups()` | `metrics.k8s.io` present, `Versions: []` |
| `ServerResourcesForGroupVersion("metrics.k8s.io/v1beta1")` | `stale GroupVersion discovery` |
| raw `DiscoveryClient.ServerGroupsAndResources()` | `*ErrGroupDiscoveryFailed` ✓ |
| **cached** `ServerPreferredResources()` — what kubecom calls | `22 lists, err=<nil>` ✗ |

The mechanism: modern apiservers answer *aggregated* discovery, where a down group is one
entry with **no versions**, its failure carried in a separate stale-GV map. client-go hands
that map only to a client implementing `AggregatedDiscoveryInterface`
(`GroupsAndMaybeResources`). The **on-disk cached** client kubecom reads through (M1-04) does
not implement it — client-go's *memory* cache does — so `ServerPreferredResources` takes the
fallback branch, walks `ServerGroups()`, finds no versions under the broken group, and
reports nothing. The group does not fail; it disappears.

Two consequences beyond the missing field. The TUI cannot tell the user which group is
unavailable — it can only show a menu that quietly lacks a kind. And **DIAG-01's per-group
discovery logging, added on 2026-07-29 precisely so failures stop vanishing, never fires** on
any cluster that speaks aggregated discovery. That is also a live lead for CRD-01, whose
whole symptom is a CRD that will not open and an error nobody can find.

It is unfixable where it looks fixable: by the time `discoverResources` has the return value,
the failure is already gone. The fix has to change *which client the pass reads through*, and
the memory-cached client that would preserve it gives up D8's promise that a warm start
reconciles the menu with no network round-trip. That is a real trade with a decision at the
end of it, not a tail-end of a test leg — hence **DISC-01** on the board, and D186 pt 2
stating what the fixing leg may not silently assume.

## The assertion this leg retracted

The test was written asserting the right thing — that `Failed` names the broken group — and it
failed, twice, for 124 s each time before I stopped believing the test was wrong. Two ways to
land green from there, and only one of them is honest:

- Assert nothing about `Failed`. Green, and the defect stays invisible until someone else
  re-derives it from scratch.
- Assert the defect, loudly, as a tripwire that fails the moment it is fixed.

It ships as the second. `TestEnvtestBrokenAPIGroupIsIsolated` ends with an assertion that
`Failed` is *empty*, a comment explaining exactly why that is wrong, and an error message
that tells the leg which breaks it what to do:

```
DISC-01 appears fixed: metrics.k8s.io/v1beta1 now reports as failed (…) —
replace this tripwire with the positive assertion
```

A pinned defect that shouts when it heals costs one test failure at exactly the moment
someone is already in the file, and it means the repository cannot quietly regress into
believing the reporting works. Pinning current behavior silently, with no explanation, is the
version of this that would have been a mistake.

## Notes for the next envtest leg

- `startControlPlane(t)` in `envtest_test.go` is the bootstrap: it skips on the gate, starts
  the plane, registers teardown, and hands back the `*envtest.Environment` (needed for
  `AddUser`) with the admin config. One plane per test on purpose — startup is ~4 s and these
  tests wreck cluster-global state deliberately.
- `clientsFor(t, cfg)` redirects `XDG_CACHE_HOME`/`HOME` into the test's temp dir before
  building `Clients`, so the **on-disk discovery cache** stays out of the developer's real
  one and two clients in one test never share a document. Without that redirect these tests
  are flaky by construction, and the flake would look like an apiserver problem.
- Call `Clients.Invalidate()` before every re-read of discovery after changing the cluster.
  The 6 h TTL is otherwise perfectly happy to serve you the pre-breakage document.
- Poll for the breakage, do not sleep for it: `ServerResourcesForGroupVersion` on the broken
  GV is the signal that the aggregator has noticed (a second or two). Poll for RBAC too — the
  authorizer reads through an informer, so a fresh grant lands a beat after the write.
