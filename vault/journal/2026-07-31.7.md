## The claim this slice was written to test, and the one it found

The board note predicted the slice would be about type-checking: "a real server
type-checks `spec.unschedulable`, `spec.suspend` and the pod-template annotation map".
It does — a string in `spec.unschedulable` is a 422 (`KindInvalid`), message *"json:
cannot unmarshal string into Go struct field NodeSpec.spec.unschedulable of type bool"*.

But that is not a gap in the coverage, because the hermetic suite already catches a
builder that quotes its bool: `TestUnschedulablePatch` asserts the exact bytes, and the
fake-backed Cordon test reads the field back with `NestedBool` and fails on the accessor
error. I checked, by making the mutation and running the hermetic suite alone. So the
type-check subtest is not there to catch that bug. It is there as the **premise** of the
subtest after it — without it, "the server dropped the field" and "the server validates
nothing" are the same observation, and the finding below would rest on a server that
never checks anything.

What the fake genuinely cannot show is the other direction. An *unknown* field is not
refused:

```
W0731 06:32:04 warnings.go:70] unknown field "spec.suspend"
```

— a warning, a 200, and an unchanged `resourceVersion`. `c.Suspend(ctx, deployments,
ref)` returns `nil`. The action reports success; nothing happened. That is true of all
five actions in this group, because the leniency is a property of merge-patch decoding
and not of any one field.

The fake, having no schema, does the opposite: it stores `spec.suspend: true` on the
Deployment, and a hermetic test could "prove" the suspend worked. Both answers are
wrong, in opposite directions, which is exactly the shape of gap these envtest slices
exist to close.

## Why that is a decision and not a footnote

The UI's actions are kind-gated (`kindIn("CronJob")`, `kindIn("Node")`, …) through
D107's registry, and until now that read as ergonomics: don't clutter a Pod's menu with
Cordon. It is not ergonomics. It is the only thing standing between a user and a
confirmation dialog for an operation the server will accept, discard, and report as
successful. D188 writes that down as a constraint, because the plausible future leg —
"offer every action on every kind and let the server sort it out", or a command palette
that dispatches by name — reads reasonable right up until it silently lies to the user.

Both current routes already consult the predicate (the menu via `rowActionTitles`, a
direct key via `rowActionApplies`), so this leg changed no UI code. D188 is a guard on
the next route, not a fix for a bug that exists today.

## Two doc comments that were wrong about a server

`Uncordon` and `Resume` both send an explicit `false` rather than `null`, and both doc
comments justified it the same way: "an explicit false keeps the field present". Against
a real server that is true of exactly one of them.

| field | Go type | after setting it false |
| --- | --- | --- |
| `NodeSpec.Unschedulable` | `bool` + `omitempty` | the key is **gone** from the stored object |
| `CronJobSpec.Suspend` | `*bool` | `suspend: false`, present |

So an uncordoned node round-trips through `omitempty` and comes back with no
`spec.unschedulable` at all. The behavior is correct either way — absent and false read
identically to the scheduler — and the reason to send `false` rather than `null` still
stands (null means *delete this key*, a different request the schema need not accept,
and `false` is what kubectl sends). Only the stated consequence was wrong. Both comments
now say what the server does, and the test asserts the *meaning* (read typed) rather
than the key's presence, so it does not encode either spelling.

This is the kind of thing that reads as pedantry until a later test asserts "present and
false", passes against the fake, and fails the first time anyone runs it live.

## A restart is the generation bump

`RolloutRestart` stamps `spec.template.metadata.annotations`, and the annotation is the
mechanism, not the effect: mutating the pod template is what a controller observes.
So the subtest asserts `metadata.generation` moved, not just that the key is there —
mutation 2 below is what that catches, and it is a mistake with an unusually plausible
shape (the object's own `metadata.annotations` is one nesting level shorter to write).

The sibling-annotation assertion is the other half. A merge patch into an annotations map
adds one key and leaves the rest; a patch that replaced the map would silently drop
sidecar-injection, config-hash and checksum annotations — the things a real pod template
carries and a test fixture does not. `kubecom.test/owner` is set through the typed client
before the restart so the witness exists.

## The two ways it was watched fail

1. **Quote the bool** in `unschedulablePatch` (`"%t"`) → the cordon subtest fails on the
   422 with the server's own unmarshal message, and the type-check subtest fails on its
   trailing "and the value the action actually sends is accepted" check. Both messages
   name the type, which is the point of keeping that second check: it is what says the
   refusal was about the value and not about the request.
2. **Stamp the annotation on the object instead of the template** (`{"metadata":
   {"annotations":…}}`) → `pod template annotations = map[kubecom.test/owner:ops], want
   "kubectl.kubernetes.io/restartedAt"`, and the statefulset/daemonset subtest fails for
   both kinds. The object is annotated and no pod ever restarts — a bug that looks like
   success in `kubectl get -o yaml` unless you know which `annotations` you are reading.

The wrong-kind subtest is written so its failure reads as what it would mean: if
`Suspend` on a Deployment ever starts returning an error, the message says D188's premise
is gone rather than that the test is broken.

## Cost

Seven subtests over one control plane (the c-1 rule), ~4 s, of which nearly all is plane
startup — the patches are ~10 ms each. The gated suite is now eight tests in 39 s, still
a per-leg command. Note for whoever runs it next: `setup-envtest` is not on `PATH` in
this sandbox even though the assets are, so `make test-envtest` fails at the
`$(setup-envtest use -p path)` substitution; the binary is at `~/go/bin/setup-envtest`
and the assets at `~/.local/share/kubebuilder-envtest/k8s/1.31.0-linux-amd64`, which can
be passed as `KUBEBUILDER_ASSETS` directly. M1-INT-d, which puts this suite in CI, is
where that gets fixed properly rather than worked around.
