## The bug that only rendering could find

The board's pre-flight list said "the changelog filters produce sensible notes". The cheap
reading of that is to open `.goreleaser.yml`, see

```yaml
    exclude:
      - '^docs:'
      - '^test:'
      - '^chore:'
```

and tick it: those are the three noise types, spelled correctly. The expensive reading is to
render the notes, which needs a tag, which is the one thing this leg must not push. The way
through is a **local** tag: `git tag v1.0.0-rc.1 && goreleaser release --skip=publish`, read
`dist/CHANGELOG.md`, `git tag -d` it. Nothing leaves the machine.

The output was 373 lines and began:

```
## Changelog
* 27430dce… Revert "chore(board): claim M0-02"
* 2e033922… build(release): M0-06 goreleaser skeleton …
* 97b4120e… chore(board): claim DIAG-01
* 93923097… chore(board): claim FB-confirm-yn-keys
… ~180 more claim lines …
```

Every commit in this repository is *scoped* — `chore(board):`, `docs(screencast):`,
`test(config):` — and `^chore:` does not match `chore(board):`. The filters had matched
essentially nothing since M0-06 wrote them. `sort: asc` then sorts by subject, which is what
puts the alphabetically-early `chore` block at the very top, so the first thing a reader of
kubecom's first release notes would have seen is 180 lines of the agent claiming board items.

Two things make this worth a decision rather than a fix. First, it is **invisible from the
config**: a filter that matches nothing looks exactly like a filter that works, and there is
no error, no warning, and no test that can tell them apart without the git log in front of
it. Second, the run that would have revealed it is the tag push — permanently cached by the
module proxy, impossible to retry (D173 pt 1). The notes are attached to a GitHub release and
*are* editable after the fact, so this was never going to be unrecoverable; but "we will
notice and hand-edit" is not a gate, and the same class of mistake in the archives or the
ldflags would be.

Hence D185 pt 1 states the general rule — **render the notes, do not read the config** — and
`TestChangelogFiltersDropTheNoise` pins it against real subjects lifted from this history,
including the two `Revert "wip(M0-02)…"` commits and a `dogfood M3:` one, since invented
examples are exactly what would have missed the scope in the first place.

## What is left after the filters, and what that says about the release

143 features, 3 fixes, 1 perf. The 3 is not an error: 22 `fix:` commits exist in this repo,
and 19 of them are on `master` before the `0.7.6` tag. The rewrite has fixed a great deal —
the whole data-race/focus/redraw class the 2020 build suffered from — but it fixed it *by
construction*, so the work is spelled `feat:`, and the bug reports it closes (#76, #86, #87,
#68) are closed by whole subsystems rather than by patches. A reader scanning the notes for
"what was broken" will find almost nothing, which is the honest shape of a ground-up rewrite.

Two smaller judgments went into the same block:

- **`feedback:` and `dogfood …` commits are excluded.** These are the maintainer dropping a
  report into `vault/feedback/` (D69) or a dogfood result into `vault/human-tasks/` (D79).
  The change that answers one is its own `feat:`/`fix:` commit, so keeping both spellings
  would list every issue twice — once as reported, once as fixed — and the report is written
  in the maintainer's voice, not the release's.
- **`abbrev: -1`.** Each line was carrying a 40-character SHA ahead of the only part anyone
  reads. goreleaser leaves a double space where the hash was, which is cosmetic and the
  lesser of the two.

## The range problem, which is not a problem

`v1.0.0`'s notes will span **all 373 commits since `0.7.6`**, because goreleaser derives the
range from `git describe` and the 2020 tags are reachable from `v1`. Worth writing down
because the tempting fixes are both wrong:

- Hardcoding `GORELEASER_PREVIOUS_TAG` in `release.yml` fixes the first release and silently
  breaks every one after it.
- Rewriting history to detach the rewrite from the 2020 tags violates the hard rules and
  would orphan `master`, which D14 keeps as the permanent 2020 reference.

The notes are *correct*: everything since the last release is, in fact, everything since the
last release. And the release body is the one published artifact that stays editable, so the
human task says so and moves on. The 2020 tags are also unprefixed (`0.7.6`, not `v0.7.6`),
which is why they are invisible to Go's module proxy and why `v1.0.0` will be the first
version `go install …@latest` can ever resolve.

## Docker: the one thing this leg could not re-verify

`goreleaser release --snapshot --clean` fails here today at the `dockers_v2` step, retrying
until it gives up. The cause is not the config: the buildkit container the docker-container
driver runs does not trust the sandbox proxy's CA, so it cannot even fetch the base image's
manifest —

```
ERROR: failed to do request: Head "https://gcr.io/v2/distroless/static/manifests/latest":
tls: failed to verify certificate: x509: certificate signed by unknown authority
```

— while the daemon itself pulls the same image fine. `--driver-opt` has no way to mount a CA
bundle into that container, so the honest options were to spend the leg on sandbox plumbing
or to say what was and was not verified. What was: the Dockerfile builds and the image runs on
the default builder, with `kubecom version` reporting the real commit and build date from
inside it, so the layout and the ldflags still hold. What was not: the multi-arch index and
the SBOM attestation, which need the docker-container driver. M5-08 verified those yesterday,
CI runs `docker/setup-buildx-action` on a runner with normal trust, and this leg's diff does
not touch the Docker config at all — so the risk is carried, named, and listed in the tag
human task's step-1 checks rather than papered over.
