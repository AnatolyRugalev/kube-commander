## Why the diagnosis is one call and not three

AUTH-01…03 each landed a piece in the kube layer, and the shell could in principle have called
all three: name the stanza, re-run it, ask for a remediation. It must not, and the reason is
not tidiness. `Diagnose` spawns a process and `SuggestedRemediation` matches provider stderr —
two things the TUI package is specifically not allowed to do (D213 pt 1), and two things that
would then have to be repeated, identically, by every future surface that wants the same
answer (AUTH-05's confirm prompt is the next one). `DiagnoseExecPlugin` makes the composition
the kube layer's, so the shell asks one question.

The one design choice inside it worth recording: a diagnosis that could not be **attempted**
returns the zero report *and* an error, never a report holding a `Plugin` with an unfilled
`ExecPluginDiagnosis`. That struct's zero value has `ExitCode: 0` and therefore does not
`Failed()`, and `authFailureCause`'s first branch renders exactly that as "running it again
just now worked". A half-report would print a sentence claiming the plugin is fine, sourced
from an observation that never happened. Two of the new kube tests pin the zero report on that
path for that reason.

## One re-run per selection, because the trigger repeats and the action is a subprocess

This is the part of the wiring that would have been a bug if the leg had been written to the
obvious shape ("on a plugin failure, diagnose").

The browse watch loop re-Lists on a backoff, and each failed attempt arrives as an `ErrorMsg`
through the pump. A cluster whose SSO session expired stays expired until the user does
something about it — which is the entire premise of the feature — so the trigger fires every
few seconds, indefinitely. Diagnosing on each one means an `aws eks get-token` per retry,
forever, while the pane already shows the answer from the first.

So `authDiagGen` latches the re-run to the `watchGen` it was fired for. What re-arms it is a
new selection: any drill-in, namespace re-scope, children scope or reconnect bumps `watchGen`,
which is the same signal that makes a *stale* diagnosis droppable. One field, both properties.

The accepted cost: if a diagnosis lands, the pane then recovers, and the same selection fails
again with the same plugin, the second failure shows only the kind's generic sentence. That
sentence is true, re-opening the resource re-arms the diagnosis, and the alternative — re-arming
whenever the notice clears — trades a guaranteed bound on subprocesses for a heuristic.

## The pane may have moved on, in two different ways

`watchGen` handles the reader navigating away: the answer describes a pane they left, and
writing it into the new one would be the "wrong content in the right place" failure the
generation guards exist for. That much is the standard pattern here.

The second check is the one that is easy to miss. A re-run takes seconds; the watch loop's next
re-List can succeed in that window (a user re-authenticating in another terminal is *exactly*
that scenario), and `table` clears its notice on a successful RESET. Writing a notice after
that does nothing visible — a notice is only rendered when there are no rows — so it lies
dormant on a working table, and then appears out of nowhere the next time the resource happens
to be empty, describing a credential problem that was fixed minutes ago. Hence: rows present,
or notice already cleared → drop it.

## The seam does not belong to the cluster

Every other client-shaped dependency in the shell is in the `Cluster` bundle, so that a context
switch repoints one value rather than twenty-one (D155 pt 2). This one is deliberately outside
it, beside `ctxLister`/`ctxState`/`themePersister`: what it asks about is the **kubeconfig**,
and it is handed the context name at call time from the field the switch already updates. A
diagnoser bound to a cluster would have to be rebuilt on every switch to answer a question the
switch does not change.

The half that *is* per-cluster is the in-flight run, and it is in `stopClusterAsync`'s
inventory: a plugin re-run started for the context being left must not outlive the switch. The
reflection test that walks every `context.CancelFunc` field on the model (`reset_test.go`)
covers the new cancel automatically, and the new suite adds the positive check that the context
handed to the seam is actually cancelled.

## A note on the tests: the batch a failure issues cannot be drained in order

Worth writing down, because the next leg to test a Cmd off a browse failure will hit it. The
batch the pump's `ErrorMsg` path returns is `{toast-clear Tick(5s), diagnosis, watch pump}`.
The shared `drainMsgs` helper runs leaves in order, synchronously — so it sits out the
five-second timer, and then blocks forever on a fake watch channel nobody is writing to. The
first version of this suite took 55 seconds and hung two tests.

Two small fixes, both local to the test file: `drillInto` closes the channel the fake watcher
just handed out (a sealed watch pumps a `WatchClosedMsg` immediately instead of blocking), and
`firstAuthDiagMsg` runs the leaves concurrently and returns on the first message it wants
rather than waiting for the batch. Where an end-to-end drive is not the point, the decision
under test is asserted directly on `diagnoseAuth` — which failures are diagnosed, and how often
— since that is the whole of the decision and it needs no Cmd run at all. The suite now runs in
~0.1s.
