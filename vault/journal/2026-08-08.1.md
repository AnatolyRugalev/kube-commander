## The values came off the wire, and that is the point

D236 pt 1 says the values come from the upstream *data* file rather than a port or a
screenshot, and the reason is that ports disagree with each other about accents
constantly. So this leg fetched five of them:

| Scheme | File read |
|---|---|
| Nord | `nordtheme/nord@develop:src/nord.css` (`main` 404s, as `knowledge/themes.md` warned) |
| Dracula | `dracula/dracula-theme@master:README.md`, the "Color Palette (OSS)" table |
| gruvbox | `gruvbox-community/gruvbox@master:colors/gruvbox.vim`, the `s:Color(...)` block |
| Rosé Pine | `rose-pine/neovim@main:lua/rose-pine/palette.lua` (`variants.main`) |
| Tokyo Night | `folke/tokyonight.nvim@main:lua/tokyonight/colors/{night,storm}.lua` |

Two of those needed a decision about *which file*, not just which value. The `rose-pine`
theme repo has no data file any more — it points at a site and a template — so the
machine-readable palette lives in the neovim port's `palette.lua`, which is what the
family's own repos consume. And `night.lua` overrides exactly three background values and
inherits every accent from `storm.lua`, so a leg reading only `night.lua` would have come
away with three colors and no palette; both files are cited in the constructor for that
reason.

Each constructor annotates every role with the upstream name it took (`// nord1`,
`// bright_purple`, `// highlight_med`), so a value can be re-checked against the source
without first decoding kubecom's semantic mapping — the shape `catppuccinTheme` and
`SolarizedDarkTheme` already used.

## What the ports had to decide, since a scheme has no opinion about kubecom's roles

kubecom has thirteen roles and no scheme publishes thirteen values under those names, so
each port is a mapping. Three mappings were not mechanical:

- **The status bar.** The board's brief said "second-darkest background, not its base",
  and the reason (`knowledge/themes.md`) is that the terminal's own background probably
  *is* the base, so a bar painted in it disappears. All five went one shade *above* base
  — nord1, gruvbox `dark1`, rose-pine `surface`, tokyo-night `bg_highlight`, dracula's
  "Current Line" — which is also what `monokai` and `solarized-dark` already did, while
  Catppuccin goes one shade *below* to `mantle`. Both work, so D248 pt 3 records the
  constraint as "not the base" rather than a direction. Nord is the citable case: upstream
  documents `nord1` as "a lighter background color for UI elements like status bars", so
  that one is the scheme's own answer rather than kubecom's.
- **Dracula has only one shade above its background.** The published palette lists
  Background and then Current Line/Selection, and nothing between. So `Selection` and
  `StatusBarBg` are the same value. That is not a shortcut — `solarized-dark` has done it
  since M4-11 — and `TestBuiltinThemesRenderDistinctly` is unaffected, because it asserts
  distinctness between *themes*, not between roles within one.
- **Rosé Pine's Success is `leaf`, not `pine`.** Pine is the palette's dark teal; on
  `base` it reads as barely-there, which is the wrong thing for "this workload is
  healthy". `leaf` is a genuine palette member and legible, and `iris` takes Primary so
  the two do not collide as near-identical muted cyans.

## The three guards, and why the generic tests were not enough

The suite already held the registry's *shape* — every role set, names unique, default
first, tail sorted, no two themes rendering identically. All five ports passed every one of
those the moment they compiled, which is precisely the problem: none of those tests can
tell a correct port from a plausible one, or notice that a sixth was dropped.

1. **`TestBuiltinRegistryIsTheDocumentedSet`** names the eleven. The shape tests pass just
   as happily with a palette silently removed; this one fails, and it is also what makes
   "eleven built-in palettes" a checked claim rather than a sentence in two documents.
2. **`TestBuiltinThemesAreDarkAndLegible`** turns D236 pt 3 into arithmetic: WCAG relative
   luminance ≤ 0.2 for `Selection` and `StatusBarBg`, and ≥ 4.5:1 contrast for the text
   painted on each. Until this leg the criterion was prose that nothing enforced, so a
   light palette could have joined the registry and rendered its dark text over whatever
   the terminal already is. The measured spread across all eleven is 4.86:1
   (solarized-dark, by design the lowest) to 12.5:1 (rose-pine's status bar), so the floor
   sits under the existing registry rather than being tuned to admit it.
3. **`TestPortedPalettesCarryTheirAttribution`** enforces D236 pt 1, which had no guard at
   all while the number of palettes needing one went from three to eight. It asserts over
   the *file* rather than a particular declaration's doc comment, because the Catppuccin
   family attributes once on the shared flavor type all four constructors read from — the
   right place for it — and a per-constructor check would have pushed that notice into four
   copies. It also names **Apache-2.0** for Tokyo Night specifically, which is the one
   thing D236 pt 1 singles out as not-MIT.

A fourth, `TestThemeDocsListEveryBuiltinAndCountThemRight`, is the drift guard the board
note asked for by hand ("the theme table is hand-written and lists every name — update it
in the same leg"): adding to the registry is the easy half and remembering two documents
is the half that silently does not happen. It follows the precedent of
`internal/tui/keymap/doc_test.go` and `internal/version/homebrew_test.go`.

## One test rewrite worth knowing about

The attribution guard failed on its first run — on Catppuccin, the one attribution that was
already there and already correct. `© 2021 Catppuccin` is wrapped across two lines of a doc
comment, so a literal substring search does not find it. The fix is not a narrower needle:
the test now strips `//` and collapses whitespace before matching, because a notice is
prose in a wrapped comment and will be re-wrapped somewhere else by the next edit that
touches the paragraph. A guard that fails on a reflow trains the next agent to delete it.

## Four mutations

1. Register a light palette (Latte's real values) → `TestBuiltinThemesAreDarkAndLegible`
   fails on both backgrounds by luminance. Worth noting that this fires on the *values*,
   independent of the name: the pre-existing `catppuccin-latte` check is name-specific and
   would not have caught `solarized-light` or any other.
2. Drop `NordTheme` from `builtins` → `TestBuiltinRegistryIsTheDocumentedSet` and the docs
   guard fail; every shape test still passes.
3. Rewrite Tokyo Night's notice as MIT → the attribution guard fails by name on
   `"Apache-2.0"`, which is the specific mistake D236 pt 1 was written to prevent.
4. Reflow a doc comment (the failure that actually happened) → passes, after the
   whitespace-normalising rewrite above; before it, a false failure.

## The claim a test cannot make

Whether eleven dark palettes are *distinguishable enough to be worth eleven entries in a
picker* is a taste judgement, and no human task is raised for it — deliberately. The
feedback asked for ~10 by name and named the schemes; the licences are verified; the values
are upstream's; and the maintainer sees the picker every time they press `T` while
dogfooding, so a palette that reads badly reports itself without being asked. What a task
here would buy is a re-confirmation of the request that produced the slice.
