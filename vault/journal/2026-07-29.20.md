## The restructure is the leg, and it is why the test compares two renders

Adding `WithTheme` looked like a one-line option. It is not, because an `Option` is
a `func(*Model)` applied **after** the model literal, and that literal was where
every component was constructed with `styles.Default()`. An option that sets
`m.styles` in that order changes exactly one thing: the field `app.go` reads for its
own few direct renders. The menu, table, status bar, hint bar, six pickers, viewer,
modal, welcome, search and logs views all keep the palette they were handed —
`m.styles.Theme.Name` says `monokai` and the screen stays blue. That is a silent
no-op, and a test asserting only `m.styles` would have passed on it happily.

So `NewWithKeymap` now builds a bare `Model` (keymap, sequencer, default styles,
filter input, logger), applies the options, and *then* constructs the components
from `m.styles`, leaving the existing post-construction seeding block untouched
below. `TestWithThemeReachesTheComponents` compares the rendered browse view under
two themes, which is the only assertion that can tell the difference from outside —
and it was verified to fail against the old ordering (components pinned to
`styles.Default()`) before being kept. Its second half compares the ANSI-stripped
renders for *equality*: a theme must repaint the screen, never re-lay it out.

## Why the resolution lives in the launcher

`internal/config` already imports `internal/tui/keymap`, so importing
`internal/tui/styles` would have compiled, and `Config.Theme()` would have read
nicely beside `Config.Keymap()`. Two reasons not to (D170 pt 1): the field name and
the method name collide, which is a smell worth listening to — `Keymap()` *merges*
overrides into defaults and genuinely belongs to the config, while a theme name is
just a lookup key the renderer owns; and an unknown name has to be *decided* about,
not parsed. `resolveTheme` returns the default theme **and** an error, which is the
shape the launcher's other degradations already use (menu extras, state file) and
which no `Config` method could express without inventing a warnings channel.

The toast slot is a single `*tui.ErrorMsg` with a first-writer-wins chain, so
ordering is a real decision: migration report → menu config → theme. A mistyped
palette name is the least consequential of the three *and* the most self-evident
(the colors are visibly not what was asked for), so it goes last; it is logged
unconditionally either way (D159), so it is never lost.

## Notes for M4-12b

- **The write-back must not clobber a hand-edited config.** `Config.SaveFile`
  marshals the whole struct, so the picker has to `LoadFile` the current config,
  set `Theme`, and save that — saving a fresh `&Config{Theme: name}` would delete
  the user's entire `keys:` section. There is no round-trip-preserving YAML here
  (comments in a hand-written config *will* be lost by any save; worth a line in
  the README when the picker lands).
- **`SetStyles` is unavoidable for a live pick** and is the bulk of that leg:
  eleven components cache a `styles.Styles`. Several also derive from it at
  construction (the picker's title, the table's widths), so a `SetStyles` must
  re-derive rather than just assign, and the leg is a good candidate for its own
  split if the component sweep runs long. `m.styles` and `m.help` are the shell's
  own two; the rest are the component fields listed in `Model`.
- **The picker already exists** (`picker.New(s, kind)`, as the context switcher
  uses it, D158) and `styles.Themes()` gives it its rows in a stable order with the
  default first — mark the active one the way the context picker marks the current
  context.
- **A `--theme` flag was deliberately not added.** The config field is the persisted
  setting the criterion asks for; a flag would be a second source of truth to
  reconcile with the picker's write-back, and nobody asked for it.
