## Two mechanisms, and why the leg fixed the smaller one

The feedback says the error is "not just showing an error message cleanly, but visibly
distorting the surrounding UI". That sentence is doing more work than it looks like: it
distinguishes *the message is ugly* from *the screen is wrong*, and the second one has two
causes that a leg could easily conflate.

**The one I fixed.** The browse notice quotes a credential plugin's stderr (`authStderrLines`,
AUTH-04a) and an API server's error text (`serverDetail`). `table.noticeBody` wraps each
source line with `ansi.Wordwrap`, truncates with `ansi.Truncate` and pads with lipgloss's
`Width` — three functions that agree, all measuring with `ansi.StringWidth`, and all wrong in
the same direction: a control character is **zero cells** by that measure and is emitted
anyway. I ran the real render path over eight payloads before writing anything, and the pane
happily produced a body line containing `downloading...\rdone, but auth failed` at a computed
width of exactly 40. The terminal draws that as the tail repainting from column 0 — over the
pane's left border. `\b` is the same bug mirrored: the frame's right border lands short.
`\x1b[2J` erases the screen the frame is drawn on. An SGR sequence repaints the pane in the
plugin's colors and, cut by the wrap before its reset, leaves it painted.

**The one I did not.** `plugin/pkg/client/auth/exec/exec.go` in client-go v0.31.4:
`stderr: os.Stderr` at line 195, `cmd.Stderr = a.stderr` at 438. Every credential refresh runs
the plugin as a subprocess of *this* process, with fd 2 pointed at the terminal bubbletea is
holding. Anything the plugin prints — an AWS SSO expiry banner, a progress spinner, a stack
trace — is painted onto the alt screen at wherever the cursor happens to be, and stays there
until bubbletea repaints those particular lines. That is what "distorting the surrounding UI"
describes far better than a mangled notice does, and it needs no control characters at all.

I fixed the first because it is contained, testable and needed regardless, and because the
second is a genuinely separate change with a failure mode I do not want sharing a diff with
anything: pointing fd 2 somewhere else is how you lose a panic trace. It wants the suspends
(`$EDITOR`, `aws sso login`, exec — where the reader *must* see a subprocess's stderr) handled
deliberately, and it wants its own tests.

## The comment that was hiding it

`kube/authexec.go` has said since AUTH-01 that the plugin's stderr "goes to the process's
os.Stderr, which under the alt-screen the user never sees", and `tui/authdiag.go` repeats it
as the premise for the whole diagnosis mechanism: we re-run the plugin *because* its own
output is invisible. The first half is true and load-bearing — kubecom cannot read that stream
back, so a re-run is the only way to get the text — and the second half is false. The alt
screen is the same terminal. The user sees it, in the worst possible way: as text over the
panes with no frame and no explanation.

So the sentence was true about the thing it was written to justify and wrong about everything
else, which is why it survived three legs of AUTH work and a board sweep. This is the same
shape BOARD-02b-3 found in LOGS: prose written by the leg that *closed* something, accurate in
the vocabulary of what it closed, silent about the gap next door. Both comments now say the
narrow true thing and point at AUTH-07; D232 pt 3 supersedes D195 pt 3 explicitly, because the
premise it stated is exactly what a future leg would re-derive from.

## Why the render and not the store

`table.SetNotice` was the obvious place to sanitize — one function, every notice, done. It is
the wrong one, and the reason is three files away: `restoreReauthNotice` puts the browse pane
back after a re-auth offer is answered, and it only does so if `m.table.Notice()` still equals
the string the offer wrote. Sanitizing on the way in makes the stored text differ from what
`authFailure` composed, so that comparison fails — for precisely the notices that carry a
plugin's stderr, which is every notice this feature exists for. The pane would keep telling
the reader kubecom is asking them a question that is no longer on screen.

The store keeps what the embedder composed; the view is what must be safe. `safetext.Line` is
idempotent (there is a test) so a seam sanitizing text another seam already cleaned is free,
which is what makes "do it at every render seam" affordable rather than a rule people skip.

## One regression, caught by an existing test, worth keeping

`statusbar.SetError` flattened with `strings.Fields`, and I first wrote the new version as
`Fields(safetext.Line(text))`. `Line` drops a newline — it is a control character, and a
function that promises one line cannot honor a second — so `"watch pods:\nconnection refused"`
became one token, `watch pods:connection`. `TestSetErrorFlattensToSingleLine` failed on the
exact string, which is a good argument for tests that assert the output rather than the shape.
The fix is `Block`, which cleans *inside* each line and leaves the separators for `Fields` to
fold, and it is why the package has two functions instead of one.
