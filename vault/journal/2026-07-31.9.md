## Why not a job in ci.yml

The board note asked for "a separate job, so a control-plane download failure never reads
as a code failure". That is the smaller half of the reason. The larger one is that ci.yml
is not just the branch gate any more: release.yml calls it as a reusable workflow so a
`v*` tag is verified by exactly the gate a branch push is (M5-03/D173 pt 1). An envtest
job inside it would put a ~50 MB download from
`storage.googleapis.com/kubebuilder-tools` on the critical path of the one push in this
project that cannot be retried or taken back. The download is reliable; it is not as
reliable as `go build`, and the asymmetry of the consequence is the whole argument.

Same reasoning in the other direction for `make check`: D17 says green means exactly that
command, and it means it in a sandbox with no network as much as on a runner. A gate that
sometimes needs to download a control plane is a different promise.

## The failure mode this job introduces

A CI job that runs a gated suite has a failure mode the suite alone does not:

```
$ go test ./internal/kube/...        # gate unset
ok   github.com/AnatolyRugalev/kube-commander/internal/kube   0.4s
```

Every `TestEnvtest*` skips, the package passes, the job is green, and nothing was tested.
Drop `KUBECOM_TEST_ENVTEST=1` from the recipe, rename `envtestGateEnv` on the Go side,
point the workflow at `make check` by mistake — all three land as a *passing* build. That
is precisely the rot the job exists to prevent, wearing the job's own colours.

Every other way this can break is loud, which is why the guard covers only this one: a
failed download exits non-zero, and a wrong `KUBEBUILDER_ASSETS` fails `env.Start()` with
a real error. So `TestEnvtestSuiteRunsInCI` is hermetic and lives in `make check`, and it
asserts the four links in the chain rather than any behavior:

1. the `test-envtest` recipe sets `envtestGateEnv + "=1"` — written against the Go
   constant, so a rename on either side fails here;
2. `check` does not depend on `test-envtest` (D17/D18);
3. some workflow runs `make test-envtest` **on push**, not only `workflow_dispatch`;
4. and that workflow is not `ci.yml` (D190 pt 1).

It counts the gated tests to say what is at stake — "9 live tests run nowhere
automatically" — rather than failing abstractly.

## Watched fail, five ways

Each mutation is a plausible edit, not a contrived one:

1. **Drop `KUBECOM_TEST_ENVTEST=1` from the recipe** → *"the test-envtest recipe does not
   set KUBECOM_TEST_ENVTEST=1; the suite would skip and CI would still be green"*, with the
   recipe printed.
2. **`check: build test vet lint test-envtest`** (the "make CI run everything" edit) →
   *"`check` depends on test-envtest; the canonical gate must not download a control plane"*.
3. **Workflow runs `make check` instead** → *"no workflow … runs "make test-envtest" on
   push — the gated envtest suite (9 live tests) runs nowhere automatically"*.
4. **Trigger reduced to `workflow_dispatch`** → *"runs "make test-envtest" but not on push,
   so the suite still only runs when someone remembers to"*.
5. **Folded into ci.yml instead** (delete envtest.yml, append the step to ci.yml) → the
   D190 message naming the tag gate.

## Two things about the toolchain that cost time

**`setup-envtest` is not where the assets are.** The tool goes to `$(go env GOPATH)/bin`,
which is on `PATH` only if someone put it there; the assets go to
`~/.local/share/kubebuilder-envtest`. A fresh sandbox can have one and not the other, and
the old recipe's `KUBEBUILDER_ASSETS="$(setup-envtest use -p path …)"` turned "the tool is
missing" into "assets are the empty string", which surfaces much later as an
`env.Start()` failure about a missing binary. Three legs in a row worked around it by
exporting the path by hand (see 2026-07-31.7). The target now checks, in order: a preset
`KUBEBUILDER_ASSETS` wins, then `PATH`, then `GOPATH/bin`, then a hard error naming the
`go install` line. It prints the assets directory it settled on, because "which control
plane did that run actually use" is the first question when a live test misbehaves.

**`@release-0.19` is a branch.** `stack.md` has said since M1-INT-a to pin the tool there
rather than `@latest`, and for a human that is right — it tracks controller-runtime
v0.19.4, which is what this module depends on. But a branch re-resolves on every install,
so CI pinned to it would drift on a morning nobody touched the repo. The workflow pins the
pseudo-version that branch currently points at
(`v0.0.0-20250308055145-5fe7bb3edc86`), the same way golangci-lint and goreleaser are
pinned exactly, with a comment that it moves *with* controller-runtime and never alone.
Verified by installing it into a throwaway `GOPATH`/`GOMODCACHE` so the module cache could
not answer for the proxy.

## What is not in this job

**No asset cache.** `actions/cache` over `~/.local/share/kubebuilder-envtest` would save
most of the ~50 MB download, at the price of a cache key to keep in step with
`ENVTEST_K8S_VERSION` and a stale-cache failure mode that is confusing exactly when the
job is otherwise red. The whole job is ~2 minutes; add the cache if that ever matters.

**Linux only.** The gated tests exercise apiserver behavior, not OS-specific code, and
`make check` already runs the ubuntu/macOS matrix D7 asks for. Darwin control-plane
binaries exist, so a macOS row is a two-line change if a leg ever needs one.

**No `-race`.** The gated suite runs at the default settings, like `make check`. Worth
considering later for the watch tests specifically, which are the ones with goroutines
worth racing; it roughly doubles their runtime, so it belongs in its own leg with a
reason.
