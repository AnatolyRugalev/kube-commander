# 2026-07-20 — FB-errors-layout: surface errors inside the fixed layout (status-bar toast)

- Agent: claude (Opus 4.8)
- Milestone: M2
- Feedback: `vault/feedback/2026-07-20-errors-break-tui-layout.md` (Priority: high) —
  drained and deleted this leg. It reported that errors disrupt the TUI layout
  (viewport scrolls, panes misalign) and asked that errors surface *within* the
  fixed layout.
- Did: Added a transient, single-line error surface to the status bar and wired it
  up. Root cause found while investigating: the top-level `Update` had **no**
  `case ErrorMsg`, so the errors already produced by `selectResource` (watch start)
  and `handleNamespacesLoaded` (ns list) fell through to `return m, nil` and were
  dropped silently; `handleWatchMsg` likewise swallowed watch ERRORs. Now all three
  route through a new `surfaceError` → `statusbar.SetError`, which flattens the text
  to one line (`strings.Fields`) and clips it to the bar width before styling, so a
  multi-line/over-wide error can never grow the bar or scroll the panes. The toast
  takes the whole line (help hint dropped) and auto-clears after 5s via a
  generation-guarded `errorClearMsg` (mirrors `seqGen`/`watchGen`), so a newer error
  keeps its full display window. No stdout/stderr writes involved (honors D71).
- Decisions: D74 (errors surface only inside the fixed layout — transient,
  single-line, generation-guarded status-bar toast; the root `Update` must handle
  `ErrorMsg`; future error producers reuse this, not a new out-of-layout render).
