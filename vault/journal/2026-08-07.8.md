## Why the table's answer could not be reused, and what that cost

The board's brief for this leg had already worked out that D239 does not transfer, and it
was right, but the reason is worth restating in terms of what a consumer *can* know. The
table's `/` filter is a substring by construction: the query is the text, so `matchOffsets`
re-derives the spans at paint time from the query alone and the row never has to carry
anything. A cluster hit has two ways of being a hit that break that:

- **fuzzy** (D153): `wbp` matches `web-pod` as a subsequence, and the three runes it
  matched are not `strings.Index`-able from `wbp`. A view re-running a substring search
  would mark nothing at all, on exactly the results whose presence most needs explaining.
- **label selector** (D151): `-l app=web` matches an object whose *labels* say so. The name
  on screen contains nothing the query mentions. A view that re-derived spans here would
  correctly mark nothing, but only by accident — it would also mark nothing for the fuzzy
  case, and the two are not the same answer.

So the marks have to come from the scorer, which is the choice the board's note preferred
and D246 pt 1 records. The cost is a field on a struct that until now carried only identity
and a score, and one more pass over each emitted hit's name.

## The marks and the score describe the same occurrence, which is a stronger claim than it looks

`MatchSpans` does not mark every occurrence of the needle. It marks the one the score was
computed from — for a substring, `substringScore`'s best-scoring occurrence (which is why
that function now returns its offset rather than only its score); for a subsequence, the
*tightened* window `scatteredScore` charges for its gaps, not the forward-greedy one.

That is a real constraint and not a stylistic preference, because the ranking is visible.
The results are sorted by score with the best first, so a reader looking at why one row
outranks another is looking at the marks. `api` in `xapiy-api-0` scores on the second
occurrence — it follows a separator, which is worth 200 — and marking the first would tell
them the row ranked where it did for a reason that is not the reason. There is a test for
exactly this (`TestMatchSpansMarkTheScoredOccurrence`) and it asserts *both* halves: that
the span is the second occurrence, and that the second occurrence is the one that scores.
Either alone is satisfiable by an implementation that has quietly stopped agreeing with
itself.

The scattered case has the same shape one level down. `scatteredScore`'s two-pass walk
exists because forward-greedy alone reads `a…b…ab.c` as a match spread over the whole name
when there is a tight `ab.c` at the end (D153's backtrack). `scatteredOffsets` replicates
*the backward pass*, so the runes it reports are the tight window. A mutation that made it
report the forward pass's positions instead is caught by the table case in `TestMatchSpans`
that pins `abc` against `a{20×z}b{20×z}ab.c` — the same fixture the scoring test uses,
which is the point: the two now fail together or not at all.

## Four mutations

1. `substringScore` keeps the first occurrence instead of the best → 1 failure
   (`TestMatchSpansMarkTheScoredOccurrence`).
2. `scatteredOffsets` reports the forward pass's positions → 1 failure (`TestMatchSpans`,
   the tightened-window case).
3. `labelSpans` drops the offset (spans left in name space) → 5 failures; the rendered one
   is the legible one, because the marks land on the **kind column** — `Pod` painted in the
   match hue on a row matching `api`, which is what a coordinate-space bug looks like on
   screen.
4. The delegate ignores `row.spans` → the two rendering tests fail while every span test
   still passes, which is the split worth having: the offsets being right and the offsets
   being painted are separate claims and they break separately.

## The one thing a test here cannot say

Whether two marks and a cursor bar are comfortable *together* on a ranked list is a
legibility judgement, and this leg does not raise a human task for it — deliberately.
D239 pt 3 already made that call against the table, on the same argument (a match cuts a
styled cell rather than replacing it, and `styles.Match` uses the Warn hue precisely so a
highlight is never read as a cursor), and it has been in the running binary since. Reusing
a settled decision is not the same as making an unverified one, and raising a task to
re-confirm D239 in a second surface would be asking the maintainer to re-answer a question
they have answered. If it reads badly here it will read badly in the table too, and that is
one report, not two.
