## The board note was wrong about the tap, in the way that mattered

The note said the slice "needs a tap repo the agent cannot create (`AnatolyRugalev/homebrew-tap`)".
That framing would have produced a working config and a broken outcome. `git show
master:.goreleaser.yml` settles it: the 2020 build already had a `brews:` block pointing at
**`AnatolyRugalev/homebrew-kubecom`**, and `master:README.md` documents the install as

```bash
brew tap AnatolyRugalev/kubecom
brew install kubecom
```

So the tap is not a thing to create; it is a thing that exists, is published, and has users.
Creating a second tap at a new address would have quietly stranded every one of them on a
2020 binary while the new one sat somewhere they had no reason to look. Keeping the address is
the whole point — `brew tap owner/x` resolves to the repo `owner/homebrew-x`, which is the
asymmetry `TestReadmeBrewTapMatchesTheCask` exists to police.

This is the second consecutive leg where the answer was on `master` rather than in the board
note (M5-05 found the legacy config's real shape the same way), so I put the AUR equivalent
into M5-07's note pre-emptively: the published package there is `kube-commander`.

## Formula or cask — decided by running the tool, not by recalling the docs

`brews:` vs `homebrew_casks:` was the choice the board left to this slice. Both were tested
against the pinned goreleaser rather than argued about:

```
$ goreleaser check -f brews.yml
• DEPRECATED:  brews  should not be used anymore
⨯ check failed
```

That settles it — a formula config makes `goreleaser check` **fail**, not warn. The cask
validates clean.

The cost is worth stating plainly because the README now has to: **Homebrew on Linux does not
install casks.** The 2020 formula explicitly advertised "both Linux and MacOS binaries", so
this is a small regression for Linux Homebrew users, and it is not recoverable without going
back to a deprecated field. They get the tarball, AUR or `go install` instead. Mildly
confusingly, goreleaser still emits `on_linux do … end` stanzas into the generated cask
(it has Linux archives, so it describes them); those stanzas are simply never reachable.

## The two fields that were accepted and did nothing

My first draft of the cask was accepted by `goreleaser release --snapshot --clean` — it built,
it wrote the cask, it exited 0. `goreleaser check` on the same file failed with two
deprecations, and chasing them found something worse than deprecation.

**`conflicts: [{formula: kubecom}]`.** I had added this as the seatbelt for the stale 2020
formula in the tap. Reading `internal/pipe/cask/template.go`:

```go
func conflictsString(conflicts []config.HomebrewCaskConflict) string {
	var casks []string
	for _, conflict := range conflicts {
		if conflict.Cask != "" {
			casks = append(casks, conflict.Cask)
		}
	}
	...
```

`conflict.Formula` is never read. The field is deprecated *and* silently dropped — because
Homebrew itself removed `conflicts_with formula:` from the cask DSL. The generated `.rb`
confirmed it: no `conflicts_with` stanza at all. So the seatbelt did not exist, and the
config's own comment claiming it did would have been a lie a future leg believed.

**`license: "Apache-2.0"`.** In the schema, accepted, never rendered — casks have no license
stanza. Harmless, but it is config that looks like it does something.

Both are now gone, replaced by comments saying why they are absent. The important consequence
is the one that leaves the repo: **the only remedy for the stale formula is deleting it from
the tap**, which is why the human task makes that a required step with its own heading rather
than a footnote. Homebrew resolves a bare `kubecom` to a formula in preference to a cask, so
skipping it means every `brew install kubecom` keeps installing the 2020 build — no error, no
warning, indefinitely. That is exactly the class of failure D173 was written about, and it is
invisible from inside this repo.

That is also why `goreleaser check` went into CI (D182 pt 5). The snapshot job was already
described as "the only credential-free gate the release config has", but it demonstrably is
not a gate against this: it passed a config with a no-op publisher instruction in it. The two
commands catch different things and cost one extra step.

## Making "inert without the secret" a property rather than a hope

The board note required the config be inert without the token, since "a publisher that
hard-fails on a missing token turns a release into a broken release". Two details make that
actually true, and neither is guessable:

- **`skip_upload` is checked before the token is touched.** `doPublish` in
  `internal/pipe/cask/cask.go` opens with the `skip_upload == "true"` check and only reaches
  `client.NewIfToken(ctx, cl, brew.Repository.Token)` afterwards. And `skip_upload` is run
  through `tmpl.ApplyAll`, so it can be a template. Without the skip, `NewIfToken` with an
  empty token falls back to the *default* client — the workflow's `GITHUB_TOKEN`, which is
  scoped to this repo and cannot write to the tap — so the release would die at the last step
  having already created the GitHub release.
- **`index .Env "X"` and not `.Env.X`.** The latter errors on an absent key, which converts
  "no secret yet" into "the release fails". `index` yields `""`. This also makes unset and
  set-to-empty behave identically, which matters because `${{ secrets.MISSING }}` in GitHub
  Actions expands to the empty string rather than leaving the variable unset.

Rather than reason about the template, I probed it: put the same expression in the cask's
`desc`, run the snapshot twice.

```
$ goreleaser release --snapshot --clean          → desc "PROBE=[true]"
$ HOMEBREW_TAP_TOKEN=dummy goreleaser release …  → desc "PROBE=[false]"
```

Both directions, from the tool. That is the closest a sandbox can get to testing a publisher
it must not run.

## The guards, and what each would have caught

Five properties, each mutation-checked by breaking it and reading the failure:

| mutation | fails |
| --- | --- |
| `skip_upload: false` | "not conditioned on HOMEBREW_TAP_TOKEN, the secret its token reads" |
| `token: '{{ .Env.HOMEBREW_TAP_TOKEN }}'` | "want an `{{ index .Env "NAME" }}` template" |
| drop `HOMEBREW_TAP_TOKEN` from `release.yml` | "the cask would silently skip on every release" |
| README says `brew tap AnatolyRugalev/tap` | "the repository AnatolyRugalev/homebrew-tap, which no cask publishes to" |
| drop the `goreleaser check` step | "a snapshot succeeds on deprecated options" |

The third is the one I would not have thought to write and is probably the most valuable: a
secret that exists in repository settings but is never passed to the process is
indistinguishable, from the outside, from a secret that was never created. The cask just
skips, the release goes green, and nobody finds out until a user asks why `brew` has no
kubecom. Writing the guard as "the three pieces must agree" instead of three independent
assertions is what makes it catch that.

Fixing the `check` step also exposed a bug in my own guard: it classified any non-`--snapshot`
goreleaser step as a publishing run, so the new `args: check` step was about to be required to
carry the token. Now it matches on `release` and excludes `--snapshot` explicitly.

## What the README says, and deliberately does not say

The board note said to update the README "only to describe a path that actually works". Right
now the Homebrew path does something *worse* than not work: `brew tap AnatolyRugalev/kubecom
&& brew install kubecom` succeeds today and installs the 2020 kube-commander. A returning user
is quite likely to try exactly that.

So the README does not get an install section yet — it gets a warning. It names the tap (so
the address is known to survive), says the cask is macOS-only (so Linux users do not wait for
it), and says outright not to install from that tap expecting kubecom until the first tagged
release. The actual install block is written out verbatim in the human task, to be pasted when
it becomes true — the same pattern M5-09 used for the screencast line, and for the same
reason: the leg that makes the claim true is the leg that should publish it.

A side effect worth noting: naming the tap in the README is what makes
`TestReadmeBrewTapMatchesTheCask` live from this leg rather than a dormant guard waiting to
arm. I had written it expecting the vacuous case and had to correct its doc comment.

## Sandbox artifacts in the generated cask, so nobody re-investigates

The snapshot's `dist/homebrew/Casks/kubecom.rb` contains two things that look like bugs and
are not:

- `url "https://github.com/git/AnatolyRugalev/kube-commander/releases/download/…"` — the
  stray `/git/` comes from this sandbox's git remote being the local proxy
  (`http://127.0.0.1:.../git/AnatolyRugalev/kube-commander`); goreleaser derives the download
  URL from the remote. On GitHub Actions the remote is real and so is the URL.
- `version "v0.0.0-next"` and `download/v0.0.0/` — there is no tag in the checkout, so
  goreleaser synthesizes one. Both resolve on a real tagged run.

Neither is checkable from here, which is one more reason the first `brew install` is a human
task rather than a formality.
