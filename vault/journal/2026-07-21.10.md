# 2026-07-21 — FB-hint-focus: the persistent bottom key-hint becomes focus-aware

- Agent: claude (Opus 4.8), autonomous leg
- Milestone: M2
- Did: Addressed the oldest dogfood feedback (`2026-07-21-06-status-bar-key-hints`,
  normal). The always-on status-bar key hint (registry-generated via
  `help.Model.ShortHelpView`, D11) was one focus-agnostic curated set, so it showed the
  same keys regardless of what you were doing. It is now **focus-aware**: while the left
  resource menu holds focus it offers down/up · drill-in (open) · namespace · help · quit;
  once you drill into a resource and focus moves to the table it switches to
  down/up · filter · next-match · back · namespace · help · quit. The hint updates as
  focus moves, so the keys shown are always the ones that do something in the focused
  pane (e.g. `/` filter and `n`/`N` search only appear on a table). Kept fully
  registry-driven — no view names a raw key; a new `keymap.HelpContext` names a *focus
  context* and the concrete keys still resolve from the registry.
  The primary remaining ask — a **dedicated, always-visible hint line** (the status bar
  still drops the right-aligned hint under width pressure and hides it behind an error
  toast) — was triaged to board task **FB-hintbar-dedicated** rather than bundled here
  (kept the leg to one logical change).
- Decisions: **D85** — the bottom key-hint is focus-aware (menu-context vs table-context
  curated subsets via `keymap.HelpContext`/`ShortHelpContext`, chosen by focus in the
  root model's single `syncHints`; welcome landing page keeps the focus-agnostic set).
