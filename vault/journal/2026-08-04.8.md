## Why the run is a leg and the offer is another one

AUTH-05 reads like one thing ("offer to run it") and is two, in the same way AUTH-04 was: the
halves fail differently. Everything in this leg is about *what a subprocess may do* — which
argv, which environment, how many times, what happens to the request that failed. Everything
in 05b is about *how a person is asked* — a modal kind, a stash, a routing arm, a decline path,
the hint line, and copy that currently tells the reader to open another terminal and must stop.
Landing them together would have meant one diff where a mistake in either half looks like a
mistake in the other, and a ~450-line diff at that.

Bottom-up (D52) puts the runner first because the offer calls it. The uncomfortable-looking
consequence is that this leg ships code nothing reaches — but that is the safest possible state
for the only place kubecom executes a command it composed: the mechanism exists, is tested, and
**cannot fire**, because no code path arms it. `golangci-lint`'s `unused` is satisfied by the
tests, so the tree stays green without a placeholder caller that would need removing later.

## The environment is the plugin's, and that is not a detail

The obvious implementation of "run `aws sso login --profile acme-prod`" is `exec.Command` with
the process environment. It is wrong for the case the AUTH line exists to serve.

`ExecPlugin.environ` exists because client-go runs the credential plugin with the process
environment *plus* the stanza's `env:` overrides, and a stanza is allowed to redirect where the
AWS CLI reads its configuration from — `AWS_CONFIG_FILE`, `AWS_SHARED_CREDENTIALS_FILE`,
`AWS_PROFILE`. A kubeconfig that does this authenticates against that file. Run the login
without the override and it resolves `--profile acme-prod` in the *user's default* config: it
either fails with "profile not found" (confusing, since the profile plainly exists) or, worse,
succeeds against a different account and writes a session the plugin will never read — a
re-authentication that reports success and fixes nothing.

So the merge is the kube layer's, reusing the same private `environ` the diagnostic re-run uses,
and `RemediationCommand` returns the whole environment rather than a delta: the caller hands it
to `Cmd.Env` as-is and cannot accidentally append to `os.Environ()` twice.

## The approval is consumed by the run, not by the outcome

`runReauth` clears the stash as it issues the suspend, not when the outcome lands. Both are
defensible; only one is safe.

The failure mode being closed is a login the reader abandons — ctrl-C in the browser flow, or an
`aws` that exits non-zero. If the stash survived until an outcome, every path that could
re-issue a run (a second confirm, a retry arm added later, a message replayed) would find a
still-armed remediation and could start a second subprocess without a second question. Clearing
at the point of firing makes "one approval, one run" a property of the code shape rather than of
every future caller's care, which is what D195 pt 4 actually asks for.

The cost is that a reader whose login failed must be offered it again to retry, and re-arming
needs a fresh diagnosis, which needs a fresh watch generation. That is exactly what the success
path's watch restart provides — and on the failure path the watch loop's own backoff keeps
failing, which is what will re-arm it once 05b opens the offer from a landed diagnosis.

## Retrying the request is enough, and I checked rather than assumed

The board note said "retry the failed request rather than the whole launch", which raises the
question a reconnect would have answered by brute force: does a client whose credential plugin
already failed *keep* failing, cached, until it is rebuilt?

It does not. In client-go v0.31's `plugin/pkg/client/auth/exec/exec.go`, `getCreds` returns the
cached credential only when one exists and has not expired, and `refreshCredsLocked` assigns
`a.cachedCreds` only after a successful plugin run — a failure stores nothing. So the next
request through the *same* client runs the plugin again and picks up whatever the login wrote.
Restarting the watch is therefore a complete recovery, and the `Cluster` bundle is never
rebuilt. (Recorded in `vault/knowledge/stack.md` beside the other exec-plugin gotchas, because
the same fact explains why an unauthenticated cluster emits a failure per watch retry — the
behaviour AUTH-04b's latch exists for.)

The restart has a second property worth keeping in mind for 05b: it bumps `watchGen`, which is
what re-arms the AUTH-04b diagnosis latch. A login that exits 0 without actually fixing the
credentials (the wrong profile, an SSO session for another account) therefore produces a *new*
diagnosis on the next failure rather than a pane that silently keeps its old notice.

## stderr is teed because the terminal is repainted a frame later

`tea.Exec` re-captures the terminal the moment `Run` returns, so anything the command printed is
gone before the reader can read it. That is fine for `$EDITOR`, whose whole output is a screen
the user was just editing, and not fine for a login that failed: "exit status 1" with no reason
is precisely the nameless auth error the feedback complained about, one layer down.

So `reauthCommand.Run` tees stderr into a 4 KiB `capWriter` while still handing the real stream
to the command — the reader sees the flow live, and the toast can quote its first line
afterwards. Two small properties, both tested: the writer keeps the **head** rather than the
tail (a CLI leads with its complaint and trails with a usage dump), and it reports every write
as fully accepted even when full, because a short write is an error to `io.MultiWriter` and
would propagate out of `Run` as a *failed login* that actually succeeded.
